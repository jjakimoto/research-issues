Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents

📰 Latest · 2026-09-11 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-11

Source: arxiv · 2026-09-10
Link: https://arxiv.org/abs/2609.11060

Microsoft shows that letting an asynchronous post-task memory curator make read-only probes into the live environment before writing records nearly doubles GitHub Copilot's CLBench pass rate (39% to 73%) while halving task-agent cost — a drop-in upgrade that changes no task-time interface.

Executive summary

Production agent platforms are adding persistent memory, but post-task curators that see only completed trajectories can memorize wrong answers, overgeneralize partial evidence, or keep stale schema knowledge. The authors add 'environment-probing curation': after a task closes, the curator agent gets a least-privilege, read-only subset of the environment tools and follows a propose-probe-commit loop to verify, scope, or refresh candidate memories before writing. In a GitHub Copilot SDK harness, probing lifts CLBench pass rate from 39% to 73% and pass-discounted reward from 8.60 to 22.60 while cutting SQL queries per question from 8.8 to 4.7 and task-agent cost from $3.38 to $1.68.

Problem: the retrospective evidence boundary

Existing post-task curators (Mem0, Claude Managed Agents Dreams, ACE, ReasoningBank, ReMe) reason only over existing records, completed trajectories, grades and usage signals. The paper argues this evidence boundary is fundamentally incomplete: no amount of reflection can recover states the task policy never visited, or tell whether a trajectory-derived rule survived environment drift. Deferring verification to task time forces the next agent to burn scarce tool calls rechecking uncertain memories.

  • Five named failure modes of trajectory-only lemmas: memorizing an instance answer instead of a procedure, inheriting an inefficient path, asserting an unverifiable scope, leaving blind spots in unvisited regions, going stale as the world changes
  • Concrete CLBench examples: a record preserving an incorrect aggregation, a record giving only a broad domain map without the needed relation, and a record retaining the removed attrs_g3 field name after schema drift

Method: propose-probe-commit curation

Tasks arrive as an online stream in an environment that may silently evolve; each task gets a fresh session and model weights stay fixed. The task agent has read-only memory_read; only the asynchronous curator agent holds memory_create/update/delete. A non-writing distiller first compresses the raw trajectory into a summary with no feedback or tools. Environment probing changes exactly one thing: after task closure the curator additionally gets a safe read-only subset of the environment tools plus two prompt lines telling it to probe when a record is uncertain.

  • Six probe uses: separate incidental answer from reusable relation; compare observed path against a shorter one; test a claimed relation on another slice; check a procedure's preconditions; inspect states the trajectory omitted; re-query when drift is suspected
  • Probes cannot mutate the environment, enter the trajectory, consume the task agent's budget, or reveal future tasks/labels; if no safe read surface exists the curator falls back to trajectory-only curation
  • Records carry category, confidence, applicability scope, lemma, provenance, utility and usage metadata
  • Deployment claim: no retraining; task agent, retriever, record schema, and production write authority are unchanged — only the curator gains read-only connector/MCP access

Setup: CLBench and adapted APEX in a Copilot harness

Four systems are compared in a production-like GitHub Copilot harness built on its SDK. CLBench uses a 40-question drift schedule (hidden SQLite schema migrates after question 20, with renamed fields and soft deletes) and a 30-question no-drift schedule for cross-model comparison. Adapted APEX adds 90 management-consulting tasks across six document worlds requiring PDF/XLSX/DOCX/PPTX discovery and MCP-style tools. Five paired seeded runs per configuration, reported with 95% Student-t intervals.

  • Metric: pass-discounted reward r_i = p_i(1 - q_i/B), with B = 15 SQL calls (CLBench) and B = 100 Archipelago tool calls (APEX); strict pass requires every rubric criterion
  • Memory-management calls excluded from q_i; task-agent cost excludes the separately tracked distillation/curation phase

Results: better answers with fewer tool calls

Every memory configuration beats no-memory on both correctness and reward, and queries and cost fall at the same time. Full ICL proves prior trajectories carry signal but its context grows with the stream (5.42M input tokens); indexed memory needs 2.13M and probed memory only 1.69M. On the drift schedule probing already leads trajectory-only memory at the migration boundary (0.541 vs 0.486 cumulative reward) and finishes at 0.565 vs 0.500, with no-memory at 0.215.

  • Cross-model, no drift: probing reaches the highest mean reward on both Sonnet 4.6 (0.748) and Opus 4.7 (0.721), with lifts of +0.421 and +0.263 over paired baselines
  • Qualitative shift: trajectory-only memory stores an answer-anchored warning about AVG(items_g2.prc_usd) producing ~52.96 vs the correct 96.23; the probing curator instead stores an executable join/filter/grain recipe on ref_id, and refreshes stale 'attrs_g3' to 'product_attributes_g3'
  • Matched CLBench trajectory: no memory 7 queries and fails, trajectory-only 9 queries and passes, probing passes in 2; hard APEX task: 96 calls and failure vs 11 (memory) vs 6 (probing)

Why it matters

The design isolates the improvement to write-time evidence quality rather than added task-agent capacity — the task-time interface, retriever and CRUD lifecycle are all held fixed, so the delta is attributable to better records. For anyone shipping agent memory on Copilot Studio, Claude Managed Agents, Mem0 or Zep, this is a low-authority, auditable retrofit.

  • Gains persist across three model families (GPT-5.4, Sonnet 4.6, Opus 4.7)
  • Probing's extra benefit is bigger on the weaker model (+0.075 on Sonnet vs +0.025 on Opus)

Key findings

  • On the CLBench 40-question drift schedule, environment probing raises strict pass rate from 39% to 73% and total pass-discounted reward from 8.60 to 22.60, versus 70% / 20.00 for trajectory-only memory.
  • Probing simultaneously cuts SQL queries per question from 8.8 to 4.7 and task-agent cost from $3.38 to $1.68, using only 1.69M input tokens against 5.42M for Full ICL.
  • On the no-drift 30-question schedule, probing gives the highest mean reward on both models tested — 0.748 on Sonnet 4.6 (+0.421 lift) and 0.721 on Opus 4.7 (+0.263).
  • Across the six adapted APEX worlds all 18 memory-versus-baseline reward gains are positive; probing has the best reward gain per task-agent dollar in five of six worlds.
  • APEX task-agent tool calls drop from baseline means of 30.0-71.6 to 13.9-28.4; in world 941eba66 cost falls from $54.30 to $7-$9 per run and input tokens from 53.92M to 6.56-7.67M.
  • Probing's advantage tracks the remaining evidence gap: +1.77 reward in APEX world 2a87e5cb and +1.09 in 2f84c98b, but -0.04 in 941eba66 where trajectories already supported actionable records.

Notable quotes

A trajectory is a single, partial, and often mistake-laden observation of the environment.
Memory therefore makes the agent both more likely to pass and less likely to spend its budget rediscovering the schema, encodings, and tool conventions already encountered earlier in the stream.
Indexed records therefore preserve reusable schemas, relations, file maps, and procedures without carrying the full interaction history.
Read-only world tools let the curator check lessons before they enter long-lived memory without expanding task-time capabilities.

Limitations

  • Uncertainty intervals overlap on the subgroup analysis, so the authors explicitly treat 'probing helps most when the evidence gap is large' as a mechanism interpretation rather than an established effect; CLBench confidence intervals are wide.
  • Evaluation is limited to two benchmarks inside a single GitHub Copilot SDK harness, so generalization to other production stacks is untested.
  • Probing requires a safe read-only surface and adds a separately tracked curation-phase cost that is excluded from the headline task-agent cost figures.

Open questions

  • How much does the curation-phase compute cost, and at what point does it erase the task-agent savings the paper reports?
  • Does the benefit hold under faster or adversarial environment drift, and how should probing budgets be allocated when many records are simultaneously stale?
  • Can probing be extended safely beyond read-only tools without giving an asynchronous curator production authority?
