When Context Gets Root: Privilege Escalation in LLM Harnesses

📰 Latest · 2026-08-29 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-29

Source: arxiv · 2026-08-27
Link: https://arxiv.org/abs/2608.27299

A repository you point a coding agent at can get its own text promoted from tool output to a user message or a system prompt simply by inducing a normal harness workflow (delegate to a subagent, save a goal, schedule a task, install a custom subagent) — and once promoted, both the working model and the model-based permission reviewer treat attacker text as your authorization. On the three harnesses with automatic permission review (Claude Code, Codex, Qwen Code), auto/"Approve for me" mode blocked 0 of 13 escalated objectives while blocking all 13 of the tool-level prompt-injection baselines.

Executive summary

The paper (Nanjing University + Honor Device, cs.CR/cs.SE) names and evaluates "instruction privilege escalation" (IPE): agent harnesses rebuild the model-facing context on every invocation, and that rebuild can present content at a HIGHER instruction level than where it originally entered. Attacker-controlled repository text enters at the tool level, then the harness itself re-presents it as a user message (subagent delegation, persistent goals, scheduled tasks, skill bodies) or as a system-effective prompt (installed custom-subagent configuration, skill metadata). Because provenance is dropped during reconstruction, the instruction hierarchy the models were trained on and the automatic permission reviewer that infers "who authorized this" both fail — while behaving exactly as designed. Across 6 coding-agent harnesses and 13 attack objectives, tool-to-user escalation achieved 13/13 objectives on every harness under full access AND under automatic permission review, whereas three published tool-level attacks achieved 0/13 on 4 of 6 harnesses and 0/13 everywhere under review.

What "root" means here: instruction level, not OS privilege

The paper's privilege model is the model-facing instruction hierarchy, not filesystem or process privilege. Section 5.1 normalizes OpenAI Chat Completions, OpenAI Responses, Anthropic Messages and Google Gemini message types into three ordered levels, tool < user < system-effective. Protocol packaging does not confer privilege: an Anthropic tool_result block sits inside a user message on the wire but is still tool level. Section 5.2 separates the ORIGIN level of content — determined empirically from captured requests, session histories and prompt-assembly source — from the per-step harness-assigned level. Escalation is defined as a chain of context-construction operations ending with harness-assigned level > origin level.

  • Table 2 tool level: ordinary repo files returned by read/search/shell tools.
  • Table 2 USER level: CLAUDE.md in Claude Code, AGENTS.md in Codex, GEMINI.md in Gemini CLI, and an invoked skill body.
  • Table 2 SYSTEM-EFFECTIVE level: QWEN.md in Qwen, AGENTS.md in Kimi and OpenCode, installed custom-subagent configuration, installed skill metadata.
  • Escalation is defined as privilege gain alone and does not by itself require execution or harm.

The trust boundary that breaks: harness-side context reconstruction

Section 4 argues the failure is structural, not a model bug. Providers deliberately train models to weight system/user text above tool text, and automatic permission review (Auto PR) leans on the same signal from the other side: it reads the working agent's transcript to infer who authorized an action. Both therefore assume role labels faithfully reflect provenance. When a harness delegates, resumes a goal, fires a scheduled task, or loads a custom subagent, it carries content forward WITHOUT its origin label — so escalation is already complete before either defense evaluates anything.

  • Section 3's motivating case: read directly as tool content the main agent refuses ("I did not start it"); routed through delegation the subagent runs the same visible backdoor.
  • Distinct from prompt injection: the malicious text is not trying to win at its original level.
  • Distinct from role confusion (ChatInject, Phantom, CoT Forgery): no forged chat-template markers — the harness genuinely places the content at the higher level.
  • Auto PR implementations differ in what they see: Codex includes assistant messages and can Read files; Claude Code's reviewed transcript excludes the working agent's assistant message and cannot inspect scripts further.

Threat model: every component behaves exactly as configured

Victim V = (H, M_w, M_r): harness, working model, optional reviewer model. All components are uncompromised — the harness runs its configured tools, sandbox and permission policy, and the models honor the instruction hierarchy. The attacker controls only workspace artifacts that first enter through a file-read or search tool, i.e. at tool level, and does NOT control the user request, the harness, either model, tool permissions, sandbox policy or approval policy, has no initial shell access, and never interacts with the human user.

  • Two self-imposed constraints make the result stronger: every attack must originate at tool level, and malicious behavior must stay visible to the model as plain-text Python with no compilation or obfuscation.
  • So the paper is not measuring whether models can spot bad code — it measures whether they act on it once the harness relabels the request.
  • Induction strategies differ by model: a direct delegation directive in README.md works on GPT, DeepSeek and Qwen; an indirect variant is used for models that scrutinize README directives.

Harnesses, versions, and the 13 objectives

Six harnesses at pinned versions were paired with six models: Claude Code 2.1.210 / Opus 4.8, Codex 0.138.0 / GPT-5.5, Gemini CLI 0.50.0 / Gemini 3.1 Pro Preview, Qwen Code 0.21.4 / Qwen3.7 Max, Kimi 0.36.0 / Kimi 3, OpenCode 1.18.1 / DeepSeek-V4-Pro-0813. All attacks originate from attacker-controlled repository content encountered while the agent sets up and launches a benign TODO application. Each case is capped at 10 attempts, with a detector confirming success.

  • Confidentiality: local service secret exfiltration, session material exfiltration, phishing email, remote host data exfiltration.
  • Integrity: Git proxy hijacking, malicious CA installation, downloaded binary execution.
  • Availability: application database deletion, local toolchain deletion, integrity-monitor termination, recurring botnet job.
  • RCE: command-and-control shell, SSH authorized-key backdoor.
  • Tool-to-system escalation installs a custom subagent under the same name as a built-in one, in a 'direct' variant (malicious logic in the subagent system prompt) and a 'hidden-script' variant (system prompt only references an external script).

Results: permission modes did not hold

Tool-level baselines mostly fail: MCPTox-style poisoning, CoT Forgery and ChatInject achieve 0/13 on Claude Code, Codex and Kimi under full access; Gemini CLI is the outlier at 7/4/3. Under Auto PR every baseline is 0/13. Tool-to-user escalation then achieves 13/13 on all six harnesses under full access and 13/13 on all three Auto PR harnesses; mean success-after-escalation across the nine harness-regime configurations is 97.3%, with per-attempt attack success 31.7%-100%. Tool-to-system escalation installs 46.2%-100% of the time and, in the hidden-script variant, completes all 13 objectives under both regimes at a mean 80.3% per attempt.

  • Escalation is close to one-shot on Codex: 1.00 execution attempts and 1.00 escalations per objective, 100% attack success in BOTH regimes.
  • Reviewer failure is explicit: a Codex reviewer correctly recognizes that a script downloads an external program, chmods it and runs it, and approves it anyway because it appears user-requested.
  • Model-side caution arrives too late: a Claude Code subagent executes the database-deletion script and only afterward warns that it deleted the database.
  • Claude Code resists the DIRECT tool-to-system variant (0/13 in both regimes) yet the hidden-script variant gets 13/13 on it.
  • Codex Auto PR is the only reviewer shown to claw anything back: hidden-script success drops 27.8 points versus full access because it inspects newly inserted function calls.
  • Auto PR blind spots: Claude Code scheduled-task content reaches the working agent but is omitted from the Auto PR context; Codex removes goal content before reviewing subsequent actions.
  • Four agent-accessible persistent-goal / scheduled-task paths each reach 13/13.

Mitigations and disclosure: what the paper does NOT say

This is the weakest part of the paper for an operator. There is no mitigations section, no countermeasure evaluation, no responsible-disclosure or vendor-notification statement, no ethics statement, and no artifact-availability statement. Section 10 is a single paragraph clarifying that 'system-effective' is an analytical category, and Section 11 closes with the negative result rather than a fix. The only remedy the paper implies is the one its root-cause analysis identifies: preserve an origin-level tag across delegation, goal resumption, scheduled-task delivery, subagent installation and skill loading, and make the reviewer's authorization inference depend on that tag rather than the message role it happens to see.

  • No claim that any vendor was notified or has patched; harness versions are pinned and are all 2026-era builds.
  • Auto PR is evaluated as an existing defense and shown to fail; it is not proposed as a mitigation.
  • Nothing is said about tool allowlists, sandboxing or network isolation as mitigations — the threat model places them outside the attacker's control and never varies them.

Key findings

  • The trust boundary that breaks is INSIDE the harness, at context assembly — not at the model. No forged role markers, no jailbreak, no obfuscation: the harness genuinely re-presents tool-origin text at user or system-effective level and drops the provenance both defenses depend on.
  • Permission modes did not hold. Auto PR blocked all three tool-level baseline attacks at 0/13 each, but allowed 13/13 escalated objectives on all three harnesses that support it; tool-to-user escalation still hit 100% per-attempt success on Codex under review.
  • Reviewer failures are not risk-misjudgement failures. The reviewer repeatedly rates the action high risk and approves it anyway, because the reconstructed transcript shows attacker-derived text under a user role.
  • All six harnesses fell at pinned 2026 versions, and four distinct context-reconstruction mechanisms escalate: subagent delegation, persistent goals, scheduled tasks, and custom-subagent installation; skills escalate on both paths at once.
  • The file-level map matters operationally: CLAUDE.md, Codex AGENTS.md, GEMINI.md and an invoked skill body are USER level; QWEN.md, AGENTS.md in Kimi and OpenCode, installed custom-subagent configuration and installed skill metadata are SYSTEM-EFFECTIVE.
  • Concealment beats explicitness at the system level: stating malicious intent in a custom subagent's system prompt gets 55/117 objective-configuration combinations (Claude Code refuses all 13), while moving the payload behind a referenced script gets 13/13 on every harness and regime at a mean 80.3% per attempt.

Notable quotes

Because the reconstruction drops the original provenance, the defenses cannot distinguish the elevated content from genuine user instructions.
Auto PR correctly identifies the action as high risk, yet still authorizes it.
A structured tool result remains at the tool level even when an API carries it inside a user message.
Overall, tool-to-user escalation achieves all 13 attack objectives, with attack success rates ranging from 31.7% to 100%.

Limitations

  • No mitigations section, no countermeasure implemented or evaluated, and no responsible-disclosure or vendor-notification statement — the operator-facing fix has to be inferred from the root-cause analysis, and it is unknown whether any of the pinned harness versions have since changed.
  • Only two permission regimes are studied (unrestricted execution and model-based Auto PR). Human-in-the-loop approval, tool allowlists, sandboxing and network egress restrictions are placed outside the attacker's control and never varied, so the paper says nothing about whether a tight allowlist or no-network sandbox would have contained the same objectives.
  • Small, attempt-capped samples (10 attempts per case; 13-21 attempts per harness in Table 10), one model per harness, one scenario family (a benign TODO app), self-reported detector results with no independent replication, and an internal inconsistency in Section 8.4 (prose says 70.0% where Table 10 reports 72.2%).

Open questions

  • Would an explicit provenance tag carried through delegation, goal resumption, scheduled-task delivery and subagent loading — and consumed by the permission reviewer — actually stop this, and at what cost in agent usefulness? The paper never builds or tests it.
  • Would coarse non-model controls that the threat model held fixed — deny-by-default tool allowlists, no-network sandboxes, blocking subagent-config writes — have contained the 13 objectives even with escalation succeeding?
  • Does the same escalation occur through MCP servers, hooks, and web/email ingestion rather than only repository files read by a local tool?
