SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

📚 Foundations · 2026-09-01 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-01

Theme: Repository-scale coding-agent evaluation and interfaces
SWE-bench defines real repository repair as an execution-grounded benchmark, while SWE-agent shows that the commands, observations, editing primitives, and guardrails exposed to an agent materially affect its measured capability. The pair makes clear that coding-agent progress depends on both credible tasks and carefully evaluated interfaces—not model scaling alone.
Source: arxiv
Link: https://arxiv.org/abs/2405.15793

Establishes agent-computer interface design as a major control surface for repository-scale coding agents and evaluates it on real GitHub issue resolution.

Executive summary

SWE-agent frames the interface between a language model and its computer as an agent-computer interface (ACI) whose commands, feedback, guardrails, and context management can materially change software-engineering performance without modifying model weights. Its specialized repository navigation, bounded file viewer, integrated editor, lint feedback, and compressed history raise GPT-4 Turbo performance to 12.47% resolved on the full SWE-bench test set and 18.00% on SWE-bench Lite. Ablations and trajectory analysis show that compact operations and concise feedback improve results, while ineffective search, cumbersome editing, and accumulating edit failures remain important bottlenecks.

Problem and ACI framing

The paper argues that interfaces designed for human users, such as a raw Linux shell, do not necessarily suit language-model agents. It defines the ACI as both the available action space and the mechanism that communicates environment state and interaction history back to the model.

  • The study holds the underlying language model fixed and treats interface design as the intervention.
  • Its four design principles are simple actions, compact and efficient operations, informative but concise feedback, and guardrails that help agents recover from errors.
  • The design process combines manual trajectory inspection with a configuration sweep on development examples.

SWE-agent interface

SWE-agent implements a ReAct-style loop over a Linux environment augmented with purpose-built commands for repository navigation and editing. The interface limits verbose output, keeps the current file state visible, rejects selected syntax-breaking edits, and compresses old observations so the model retains action history without repeatedly consuming stale file content.

  • find_file, search_file, and search_dir summarize repository search results and reject searches producing more than 50 matches in favor of a more specific query.
  • The file viewer displays at most 100 lines with paths, line numbers, file length, and omitted-line indicators.
  • The edit command replaces a selected line range, immediately redisplays the result, and uses lint checks to discard invalid edits.
  • Observations older than the latest five are collapsed to one-line records, while malformed model responses receive corrective feedback.

Evaluation design

The main evaluation uses SWE-bench, comprising 2,294 issue-resolution tasks from 12 popular Python repositories, with ablations on the 300-instance SWE-bench Lite subset. The paper compares interactive SWE-agent against non-interactive retrieval-augmented generation and a shell-only interactive agent, using GPT-4 Turbo and Claude 3 Opus under a $4 per-instance budget; a patch is resolved only if all evaluation tests pass.

  • The primary metric is pass@1, reported as percent resolved.
  • Average API inference cost is reported over successfully resolved instances.
  • HumanEvalFix provides a separate short-form debugging evaluation across programming languages.
  • The configuration search varies file-viewer window size, observation history, and decoding temperature.

Benchmark and ablation results

SWE-agent with GPT-4 Turbo resolves 286 of 2,294 full SWE-bench tasks (12.47%) and 54 of 300 SWE-bench Lite tasks (18.00%), compared with 11.00% for the shell-only agent on Lite. The component ablations show that the result depends strongly on interface design rather than interactivity alone: removing the dedicated editor, using iterative search, showing entire files, or retaining full observation history all reduce performance.

  • On SWE-bench Lite, SWE-agent improves from the shell-only agent's 11.00% to 18.00%, a 64% relative increase.
  • Removing the dedicated editor lowers Lite resolution from 18.0% to 10.3%; retaining editing but removing linting lowers it to 15.0%.
  • Iterative result-by-result search scores 12.0%, worse than summarized search at 18.0% and even no dedicated search at 15.7%.
  • A 100-line file window scores 18.0%, compared with 14.3% for 30 lines and 12.7% for the entire file.
  • On HumanEvalFix, SWE-agent with GPT-4 Turbo reaches 87.7% pass@1 for Python, 89.7% for JavaScript, and 87.9% for Java.

Agent behavior, significance, and failure modes

Trajectory analysis finds a recurring workflow: agents first reproduce or localize the issue, then alternate editing with execution feedback. Successful episodes tend to finish earlier and more cheaply, while unresolved trajectories are dominated by incorrect or overly specific implementations rather than merely running out of interaction budget.

  • Of the GPT-4 Turbo trajectories, 1,185 of 2,294 (51.7%) contain at least one failed edit.
  • An editing attempt has a 90.5% eventual-success rate overall, but this falls to 57.2% after one failed edit.
  • Successful GPT-4 episodes have a median cost of $1.21 and 12 steps, versus a mean of $2.52 and 21 steps for unsuccessful episodes.
  • Incorrect or overly specific implementations account for about 52.0% of unresolved SWE-bench Lite instances; running out of budget accounts for 23.4%.
  • The findings make repository-scale agent evaluation partly an interface-evaluation problem: the same model can exhibit materially different capability under different commands, observations, and safeguards.

Key findings

  • Agent-computer interfaces can substantially improve coding-agent performance without changing the language model's weights.
  • Purpose-built, bounded repository search and editing operations outperform workflows assembled from generic shell commands.
  • Immediate state feedback, lint guardrails, and compressed history each contribute measurable gains.
  • SWE-agent with GPT-4 Turbo resolves 12.47% of full SWE-bench and 18.00% of SWE-bench Lite, versus 11.00% for the shell-only Lite baseline.
  • Trajectory evidence suggests that implementation correctness and recovery from editing mistakes are larger constraints than simply increasing token or cost budgets.

Notable quotes

Ultimately, a well-designed ACI should help the LM agent understand the state of the application given previous changes, manage history to avoid unnecessary context from prior observations, and provide actions that models can use efficiently and reliably.
Building in guardrails, such as a code syntax checker that automatically detects mistakes, can help agents recognize and quickly correct errors.
Recurring problem-solving patterns emerge when LMs are equipped with a useful, intuitive ACI.
Second, in this work, the ACI development process and case studies are done manually.

Limitations

  • The final interface has a deliberately small toolkit and omits potentially useful capabilities such as web browsing, static or dynamic analysis, spectrum-based fault localization, and fuzzing-based test generation.
  • ACI components and case studies were developed manually from observed trajectories rather than through an automated interface-design procedure.
  • The study is restricted to programmatic tasks, so whether its ACI principles transfer to other digital-work domains remains unresolved.

Open questions

  • Can agents automatically inspect failures and optimize their own ACI while producing reliable, incremental gains over long horizons?
  • How much additional resolution performance comes from integrating static analysis, dynamic analysis, fault localization, or automated test generation into the interface?
  • Which ACI principles transfer beyond software engineering, and how should search, state presentation, and feedback change for other digital tasks?
