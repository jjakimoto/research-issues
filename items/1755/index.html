    Where Does Exactly-Once Live? Model, Harness, and Tool-Contract Effects on Duplicate Side Effects in LLM Agents

    ← Go backExplorationBench: Measuring AI Systems’ Exploration in…NextAlphaDiverse: Post-Training Local Quantitative Research… →
    📰 Latest · 2026-09-25 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-25

    Source: arxiv · 2026-09-24
    Link: https://arxiv.org/abs/2609.29095

    Exactly-once behavior is not solely a model capability: strong models handle immediately verifiable lost acknowledgements, but late commits and redelivery require stable idempotency semantics in the tool contract. Coding and autonomous-research agents should pin one key per intent, expose status and timing guarantees, avoid invisible retries, and surface unresolved outcomes.

    Executive summary

    The paper introduces Limbo, a deterministic benchmark that injects ambiguous write failures into six simulated services and grades 25,930 agent episodes against a ground-truth effect ledger. It proves that verification alone cannot guarantee exactly-once execution when a timed-out request may commit later, then experimentally separates the contributions of models, harnesses, and tool contracts. Models dominate when read-back resolves uncertainty; stable idempotency keys dominate for late commits and redelivery, while the choice among three production harnesses contributes almost nothing to duplicate risk.

    Retry ambiguity and the impossibility result

    A timeout or server error is compatible with several hidden states: a write may be absent, committed with its response lost, still in flight, partially committed, or duplicated. Before an in-flight effect becomes visible, these states can be observation-equivalent, so immediate read-back cannot guarantee the outcome.

    • If a policy must finish an absent-write world within time T, a late commit delayed beyond T plus visibility lag forces the same observations through the retry and can cause duplication.
    • A known processing bound permits safe waiting, but few APIs document such bounds and any finite assumption leaves an unbounded delay tail.
    • Reissuing with the same idempotency key is exactly-once across the modeled failure states when the service executes each key at most once and resumes interrupted keyed batches.

    Limbo benchmark design

    Limbo contains six services—social, billing, tickets, mail, data, and deployment—plus twelve parameterized workflows and service-boundary fault injection. A deterministic effect ledger ensures that a duplicate remains a failure even if later compensated.

    • Faults include lost acknowledgements, misleading HTTP 500 responses, late commits, partial batches, transport redelivery, transient 503s, rate limits, outages, and schema drift.
    • The study covers nine models, a minimal scaffold, GitHub Copilot CLI 1.0.86, Hermes Agent 0.20.6, Codex CLI 0.139, two contract variants, and fifteen recovery conditions.
    • Thirty-one scripted validity tests check observation-equivalent pairs, consistency lag, partial batches, key replay, redelivery, escalation, and ledger grading.

    Models solve only observable ambiguity

    Six frontier models nearly solve faults whose committed effect is immediately visible, duplicating 0.5% of lost-acknowledgement writes and 8% of misleading-500 writes. The same group duplicates 56% of late commits and 74% of redeliveries because verification either occurs before the effect lands or is never prompted by an error.

    • For resolvable faults, the model explains 53% of explained duplicate variance; for late commits and redelivery, the contract explains 81% and the model only 8%.
    • Removing the explicit exactly-once instruction raises duplicates from 12% to 22% on resolvable faults and from 58% to 71% on late commits, but barely changes redelivery.

    Tool contracts and stable keys

    The keys-everywhere counterfactual extends Stripe-style idempotency semantics to every non-idempotent write. Models use a key in 98% of faulted episodes when offered one, and a contract-aware guard closes most of the remaining gap by attaching keys automatically.

    • Keys everywhere reduce late-commit duplicates from 61% to 9% and redelivery duplicates from 74% to 7%; with the guard, rates become 7% and 0%.
    • Across 432 late-commit retries that reused the original key, none duplicated.
    • Eventually consistent read paths produce 13.4% duplicates versus 0.8% for strongly consistent paths when agents verify.
    • With no read-back path, frontier agents escalate in 87% of committed-fault episodes, making an apparently useful but stale read path more dangerous than none.

    Waiting, guards, and harnesses

    Waiting works only when the in-flight bound is known and short. Under a fixed 90-second delay, waiting 120 seconds reaches 99% exactly-once success. Under delays ranging from 40 seconds to two hours, an hour-long wait reaches only 84% at 49.9 simulated minutes per episode; keys with the guard reach 94% at 1.5 minutes.

    • Transparent SDK retries reduce exactly-once success from 72% to 50% because the model never sees the ambiguous first result.
    • A guard can induce complacency: for gpt-6-sol on late commits, its verification promise increases duplicates from 50% to 71%.
    • Harness choice has little effect on reliability, although a Codex CLI episode uses about 153,000 tokens versus roughly 12,000 for the minimal scaffold.
    • Among 1,279 duplicate-producing episodes, 90% end with status completed and 80% list no uncertain operation.

    Key findings

    • Frontier-model reasoning works when observations resolve a failure but remains inadequate for in-flight commits and successful redelivery.
    • Tool-contract design explains 81% of explained variance for unresolvable faults and 88% in the harness experiment.
    • Stable idempotency keys outperform long waits: keys plus the guard achieve 94% exactly-once success at 1.5 minutes under heavy-tailed delays.
    • Production harness identity explains 0% of duplicate variance on unresolvable faults.
    • Agent self-reports are unsafe reliability evidence: 90% of duplicate-producing episodes are reported as completed.

    Notable quotes

    The benchmark does not reward caution for its own sake.
    Agents use keys when offered; they cannot use keys that do not exist.
    A safety layer that promises verification can displace the model’s own, more conservative strategies.

    Limitations

    • All services and failures are simulated, the operator answers truthfully when available, and tasks are shorter than full production workflows.
    • All models were reached through one gateway with provider-default settings.
    • Only three production harnesses were studied, and several analyses were exploratory additions after preregistration.

    Open questions

    • Do these failure rates and contract effects reproduce on real APIs and longer coding or autonomous-research workflows?
    • Can learned or cost-aware verification policies reduce latency while preserving explicit guarantees under bounded uncertainty?
    • How should agent protocols standardize stable intent identifiers, idempotency keys, status queries, and visibility bounds?
