    MASAI: Modular Architecture for Software-engineering AI Agents

    ← Go backEureka: Human-Level Reward Design via Coding Large Language…NextCodePlan: Repository-level Coding using LLMs and Planning →
    📚 Foundations · 2026-09-28 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-28

    Theme: Planning and modularity for repository-scale coding
    Repository-level coding requires more than generating an isolated patch. CodePlan uses dependency-aware planning to propagate edits through a codebase, while MASAI separates testing, reproduction, localization, repair, and ranking into specialized modules; both make context selection and executable feedback first-class architectural components.
    Source: arxiv
    Link: https://arxiv.org/abs/2406.11638

    A foundational repository-scale coding-agent architecture that decomposes issue resolution into role-specialized sub-agents connected by explicit information handoffs.

    Executive summary

    MASAI decomposes repository-level issue resolution into five LLM-powered modules: Test Template Generator, Issue Reproducer, Edit Localizer, Fixer, and Ranker. It assigns ReAct to repository exploration and localization, CoT to patch generation and ranking, and uses generated reproduction tests to rank five candidate patches. On the paper's 300-task SWE-bench Lite evaluation, MASAI ties CodeR at 28.33% resolution while reporting 75.00% localization and an average cost of $1.96 per issue.

    Modular problem formulation

    Rather than use one long agent trajectory, MASAI models each sub-agent through an Input–Strategy–Output specification and composes the system by passing outputs downstream. The five roles separate repository-specific test discovery, issue reproduction, fault localization, candidate repair generation, and evidence-based ranking.

    • The Test Template Generator discovers how to write and execute a valid repository-specific test.
    • The Issue Reproducer converts the issue into a test whose status should change after a correct fix.
    • The Edit Localizer identifies files, classes, and functions to modify.
    • The Fixer samples multiple candidate patches, and the Ranker orders them using reproduction-test evidence.

    Repository interaction and patch construction

    Repository-facing sub-agents receive a compact action space: READ, EDIT, ADD, WRITE, LIST, COMMAND, and DONE. READ returns lazy structural representations, while the Fixer emits minimal pre/post rewrites; exact matching falls back to fuzzy span matching, and syntactically invalid edits are rejected.

    • Repository navigation is isolated from patch synthesis so each stage can use a task-specific strategy.
    • Sub-agents communicate through structured outputs rather than pairwise or group conversations.
    • Approximate code lookup and shell access support multi-hop localization when issue descriptions are vague.

    Experimental setup

    The evaluation uses SWE-bench Lite: 300 predominantly bug-fixing tasks from 11 open-source Python repositories, with hidden issue-specific tests. All five roles use GPT-4o; exploratory ReAct loops are capped at 25 steps, the Test Template Generator gets up to three retries, and the Fixer samples five candidates at temperature 0.5.

    • Issue Reproducer, Edit Localizer, and Ranker use temperature 0.
    • The reported average cost is $1.96 per issue, and total experimental cost is estimated below $10,000.
    • The evaluation measures resolution, file-level localization recall, and whether the generated patch applies successfully.

    Results and architectural evidence

    MASAI reports 28.33% resolution, tying CodeR for the highest Table 1 result, alongside 75.00% localization. The Edit Localizer exceeds the reported localization rates of SWE-agent and no-hints OpenDevin, while the patch-selection ablation shows that diversity helps only when a generated reproduction test supplies ranking evidence.

    • Oracle success rises from 23.33% with one Fixer sample to 35.00% with five samples.
    • With five samples, random selection reaches 22.28%, an LLM without test evidence reaches 23.33%, and MASAI's test-informed Ranker reaches 28.33%.
    • MASAI localizes 75% of tasks versus 61% for SWE-agent and 63% for OpenDevin without hints.
    • Table 1 reports 95.33% edit application for MASAI, although Section 4.6 inconsistently states 96.33%.

    Key findings

    • Explicit role decomposition lets repository exploration, testing, localization, repair, and ranking use independently chosen strategies and bounded contexts.
    • MASAI ties CodeR's 28.33% SWE-bench Lite resolution while using only the repository and issue description rather than expert hints or pre-specified test commands.
    • Five-way patch sampling increases oracle coverage substantially, but generated reproduction-test evidence is necessary to select candidates effectively.
    • A dedicated ReAct localizer reaches 75% file-level localization, supporting the value of separating search from repair.
    • Repository-specific test-template discovery and minimal-rewrite fuzzy patching address two practical failure points: executing tests and applying model-generated edits.

    Notable quotes

    Instead of treating this as one long chain of reasoning and actions, we propose modularizing the problem into sub-problems and delegating them to different sub-agents.
    The sub-agents are composed by passing the output from one sub-agent to the input of another sub-agent.
    MASAI exploits the above observations through its modularity by (1) leveraging a CoT sampling strategy for Fixer and (2) instantiating independent sub-agents for test generation and repair.
    Due to the time and cost constraints, we have instantiated all sub-agents with GPT-4o.

    Limitations

    • Evaluation is confined to SWE-bench Lite, whose 300 tasks come from 11 Python repositories and cover only issues that can be validated with tests.
    • Every sub-agent uses GPT-4o, so the study does not directly compare models or heterogeneous per-role model assignments under a fixed architecture.
    • The benchmark issue descriptions are English-only; the paper also warns that shell-capable agents can cause unintended side effects and introduce security vulnerabilities.

    Open questions

    • Does the modular architecture generalize to broader software-engineering tasks, repositories, and issues that cannot be validated solely through tests?
    • What per-role mixture of frontier LLMs and smaller language models gives the best cost-performance trade-off under a fixed MASAI strategy?
    • How should repository-scale coding agents be sandboxed, reviewed, and evaluated across languages without sacrificing autonomy?
