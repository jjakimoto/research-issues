RepoCoder: Repository-Level Code Completion Through Iterative Retrieval and Generation

📚 Foundations · 2026-09-13
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-13

Theme: Repository-Aware, Self-Correcting Coding Agents
These works establish three complementary mechanisms for improving coding agents without updating model weights: persistent verbal reflection across trials, iterative repository retrieval using provisional code as query expansion, and execution-feedback debugging. Their results also expose the central failure mode: incorrect tests, noisy retrieval, or unsupported self-assessment can turn additional iterations into regressions.
Source: arxiv
Link: https://arxiv.org/abs/2303.12570

RepoCoder is a foundational blueprint for repository-aware coding agents because it uses a model’s provisional completion to iteratively improve retrieval of relevant cross-file context.

Executive summary

RepoCoder combines a fixed repository retriever with a pre-trained code language model, feeding each provisional completion back into the next retrieval query to narrow the gap between an unfinished prefix and its intended continuation. The paper also introduces RepoEval, covering line, API-invocation, and function-body completion, with unit-test-based evaluation for functions. Across GPT-3.5-Turbo and three CodeGen sizes, RepoCoder improves substantially over in-file completion and two or more iterations consistently outperform one-shot retrieval-augmented generation, although later iterations can be unstable.

Problem and motivation

Repository-level completion requires information scattered across files, but the unfinished code alone can be a poor search query because it may omit the API names, arguments, or patterns present in the intended continuation. Existing static-analysis and heuristic systems are less flexible across arbitrary completion lengths, while repository-specific model training is expensive and does not readily generalize to unseen repositories.

  • The target is completion at line, API-invocation, and function-body granularity.
  • A one-shot retrieval query built only from the prefix can miss the repository evidence needed for the target continuation.
  • The motivating example shows an initially plausible but incorrect API call becoming useful as a query that retrieves the correct API signature.

Iterative retrieval-generation method

The repository is divided into overlapping code snippets with a sliding window. The first iteration retrieves snippets using the last window of unfinished code; later iterations query with the last Sw−Ss lines of the prefix concatenated with the first Ss lines of the preceding prediction, then regenerate from the retrieved snippets and original prefix. The retriever and generator remain frozen throughout.

  • The main experiments use token-set Jaccard similarity as a sparse bag-of-words retriever.
  • Retrieved snippets include their file paths and are combined with the unfinished target file in the generation prompt.
  • For line and API completion, generated length, window size, and stride are 100 tokens, 20 lines, and 10 lines; for function bodies they are 500 tokens, 50 lines, and 10 lines.
  • The maximum number of retrieved snippets is 10, with total prompt-plus-output limits of 4,096 tokens for GPT-3.5-Turbo and 2,048 for CodeGen.

RepoEval benchmark and evaluation

RepoEval uses Python repositories created after January 1, 2022 and archived as of January 2023. Eight repositories contribute 1,600 line-completion and 1,600 in-repository API-invocation samples, while six smaller repositories contribute 373 function bodies of 3–30 lines whose correctness can be checked with repository unit tests.

  • Line and API outputs are scored with Exact Match and Levenshtein-based Edit Similarity.
  • Function bodies are executed against corresponding tests and scored by Pass Rate.
  • Repository selection requires an open-source license, more than 100 stars, more than 80% Python files, and explicit unit tests.
  • The benchmark records repository, file path, line numbers, and ground-truth completion for each sample.

Main results

RepoCoder improves in-file completion across every tested generator and both token-level tasks. For GPT-3.5-Turbo, two iterations raise line Exact Match from 40.56% to 56.81% and API Exact Match from 34.06% to 49.19%; on function bodies, Pass Rate rises from 23.32% to 42.63%. Two or more iterations consistently beat the one-iteration RAG baseline, while the best iteration varies by model and task.

  • Across line and API completion, the paper reports absolute gains over in-file completion exceeding 10 points in Exact Match and 8 points in Edit Similarity.
  • CodeGen-Mono-350M with repository retrieval becomes comparable to GPT-3.5-Turbo using only in-file context.
  • On the eligible API subset, a second iteration raises ground-truth invocation recall from 86.04% to 90.34% for GPT-3.5-Turbo.
  • A UniXcoder dense retriever gives broadly comparable results to the simpler sparse retriever.

Significance and failure analysis

The study establishes generation-assisted query expansion as a simple way for coding agents to exploit whole-repository context without retraining or mandatory static analysis. Its analysis shows that useful evidence commonly comes from files in the same directory or with similar imports or names, but iterations can also regress when retrieved examples contain incompatible API parameters or when generated query tails introduce noise.

  • Retrieval quality is strongly associated with completion quality, especially when snippets contain analogous statements or target-API usage examples.
  • Each additional iteration both fixes some previous failures and breaks some previous successes, motivating adaptive stopping rather than a fixed large iteration count.
  • Exact Match incorrectly rejects some functionally correct alternatives, supporting broader use of executable tests.
  • Performance gains tend to be smaller in repositories with little duplicated code.

Key findings

  • Using a provisional model completion as query expansion substantially improves repository retrieval and downstream completion without updating either model.
  • Two or more retrieval-generation iterations consistently outperform one-shot RAG across all four tested generators on line and API completion.
  • GPT-3.5-Turbo function-body Pass Rate improves from 23.32% with in-file context to 42.63% after two RepoCoder iterations.
  • The 350M-parameter CodeGen model augmented by RepoCoder is comparable to GPT-3.5-Turbo using only in-file completion.
  • Simple Jaccard retrieval performs comparably to dense UniXcoder retrieval in the reported experiments.
  • Later iterations are not monotonically beneficial because misleading examples and noisy generated query text can replace previously useful context.

Notable quotes

This highlights the importance of considering the actual functionality of the code, rather than solely relying on exact matching, and suggests incorporating unit tests to assess code correctness.

Limitations

  • Similarity-based retrieval yields smaller gains in repositories with little code duplication and can surface misleading API examples with incompatible parameters.
  • The optimal iteration count is unknown: later iterations can regress, and the paper does not establish a reliable automatic stopping criterion.
  • The evaluation explores limited prompt designs and retrievers, predates newer code models, and does not systematically benchmark confidential commercial systems; extra iterations also create unresolved real-time latency costs.

Open questions

  • Can a learned confidence or retrieval-quality signal stop iteration before useful context is displaced by noisy predictions?
  • Which semantic, graph-based, or hybrid retrieval methods work best when repositories contain little duplicated code?
  • How do accuracy, latency, and cost trade off with current long-context code models under executable, repository-scale evaluation?
