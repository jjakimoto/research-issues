    An Empirical Study of Harness Design for Coding Agents

    Source: arxiv · 2026-09-17
    Link: https://arxiv.org/abs/2609.20804

    The first component-level ablation of a coding harness: across 176 matched settings on SWE-Bench Verified and Terminal-Bench 2.1, context management, planning, and the action space each help only conditionally — on how tight the context window is, how capable the model is, and how shell-centric the task is. It gives harness builders concrete rules (stage cheap elision before LLM summarization; drop the recall tool; give bash-weak models predefined tools and bash-capable models a bare shell) instead of one-size-fits-all defaults.

    Executive summary

    The authors build a lightweight LangGraph ReAct harness whose execution loop is fixed while three components vary: planning (a persistent update_plan scaffold), the action space (eight predefined workspace tools vs. bash-only), and context management (five tiers combining elision M1, recoverable external storage M2, and LLM summarization M3). They run four models — Nemotron-3 30B/120B/550B and Mistral-Medium-3.5-128B — on SWE-Bench Verified (500 tasks) and Terminal-Bench 2.1 (89 tasks) across 32k/64k/96k/128k context budgets, for 176 settings, with paired McNemar tests and Benjamini-Hochberg FDR control. Context management's value comes almost entirely from preventing context-overflow termination and fades as the window grows; T4 (elide first, summarize only if still over) is the cheapest at comparable accuracy; the recall tool is almost never invoked and buys nothing. Planning flips from an accuracy scaffold for the weakest model to a cost saver for strong ones, and the predefined tool set scaffolds bash-weak models while bash-only lets strong models write bigger edits in fewer calls.

    Problem: harnesses are evaluated as monoliths

    Prior work compares whole agent systems, so a performance difference cannot be attributed to planning, tool design, or context management. The paper cites a cross-harness evaluation where Claude-Opus-4.5 does best with OpenHands while Claude-Sonnet-4.5 does best with SWE-Agent — evidence that harness preference is model-dependent but no explanation of why. The research question is whether harness components are generally useful or conditionally useful on model capability, task type, and resource budget.

    • Execution loop, permission handling, post-edit diagnostics and stuck detection are held fixed as a common substrate.
    • Only three components are varied, chosen because prior systems treat them as complementary requirements of long-horizon agents.
    • No prior work jointly sweeps an explicit context-window axis and a within-family model-scale axis.

    Harness design: the three varied components

    Planning injects a persistent plan (maintained via update_plan) into model input each turn without storing it in history. The action space is either read_file/write_file/edit_file/list_files/glob_files/grep_text/web_fetch/bash or bash alone. Context management composes three mechanisms under a soft and a hard token threshold: M1 elision replaces stale tool-observation bodies with stubs, M2 stores originals externally behind a recall_event tool, M3 folds old messages into a running summary produced by a separate tool-free call to the same model.

    • T0 = none (terminates on overflow), T1 = M1, T2 = M1+M2, T3 = M3, T4 = M1+M2+M3 staged (elide at soft threshold, summarize only if still above hard threshold).
    • Preamble plus a token-budgeted recent window of at least two turns always stays verbatim; only the middle region is compacted.
    • Web search is excluded because SWE-Bench tasks come from public GitHub issues and search could leak the ground-truth patch.
    • Fixed safety gates: workspace path guard against symlink escapes, read-before-write with content hashing, allow/ask/deny permission layer; tool errors return as observations so a failed action never crashes the loop.

    Experimental setup

    Models are served locally with SGLang in BF16, temperature 0, top-p 0.95, 16,384 output tokens per turn, max 300 steps per task. The harness runs on LangGraph with Harbor owning each task container and verifier. Soft/hard context thresholds are 0.6 and 0.85 of the usable window, the verbatim recent window is budgeted at 0.3 (floor of two turns), tool results truncate at 24k characters, and up to eight read-only tools run in parallel per step.

    • 20 context-management settings (5 tiers x 4 budgets) + 2 component ablations = 22 settings per model-benchmark pair; 4 models x 2 benchmarks = 176 settings.
    • Planning and action-space ablations are run only at T4/128k.
    • Stuck detection: reminder after 5 identical (or 5 identical failing) tool calls, terminate after 8 consecutive identical failing calls.
    • OpenRouter pricing per 1M input/output tokens: $0.05/$0.20 (30B), $0.08/$0.45 (120B), $0.50/$2.20 (550B), $1.50/$7.50 (Mistral-Medium-3.5).

    Results: context management is an overflow insurance policy

    The managed-vs-T0 success gap shrinks monotonically as the window grows on both benchmarks, tracking the decline in T0 window-overflow failures. Every managed tier overflows on exactly zero tasks at every budget. The gap is dramatic at 32k — e.g. Nemotron-3 550B goes from 6.40% (T0) to 58.40% (T3) on SWE-Bench, and Mistral from 12.60% to 66.20% (T2) — but at 128k T0 is already within a few points of the managed tiers for most models. T4 has the lowest mean cost per task at every window budget and the lowest average peak-context ratio, because early cheap elision avoids costly LLM summarization calls.

    • Recall (M2) is a no-op: over 32 matched T1-vs-T2 comparisons, T2 wins 15, loses 14, ties 3.
    • Among the 64 T2/T4 settings, 36 never call recall_event; median invocation rate is zero; the 16 planning and action-space settings at T4/128k record no recall calls at all.
    • At 32k, unmanaged SWE-Bench runs have median lengths of 20-30 turns and mostly die in the Localize phase; managed tiers push medians to roughly 50-180 turns.
    • At 128k, tiers are nearly indistinguishable behaviorally: median lengths 39-42 turns (30B) and 70-74 turns (550B).

    Results: planning and action space are capability-conditional

    Planning rescues the weakest model and trims the strongest ones. Without planning, Nemotron-3 30B collapses to 13.60% SR on SWE-Bench (vs 25.20% with planning) and its median trajectory falls from 40 to 5 turns. For strong models planning mainly cuts redundant post-edit verification: median SWE-Bench trajectories drop from 108 to 74 turns for 550B and 68 to 53 for Mistral. On the action space, removing predefined tools costs 30B 15.0 points on SWE-Bench and 10.1 on Terminal-Bench, but gains 550B on both (69.40% vs 65.80% SR on SWE-Bench at less than half the cost, $1.11 vs $2.33). Mistral shows the crossover is also task-type-dependent: the full tool set wins on SWE-Bench (68.60% vs 45.40%) while bash-only wins on Terminal-Bench (43.82% vs 37.08%).

    • Planning cost effects on Terminal-Bench: -26% for 120B, -3.6% for 550B, about -40% for Mistral, but +75% for 30B.
    • With planning off, 68.6% of 30B SWE-Bench runs end without an edit and 58.4% stall in Localize, versus 27.8% and 10.4% with planning.
    • Bash-only breaks 30B: 66% of its Terminal-Bench bash-only trajectories terminate on out-of-interface tool emissions, cutting the average trajectory from 71 to 15 turns.
    • 32.8% of Mistral's bash-only SWE-Bench runs end without editing any file, versus 1.2% with the full tool set.

    Significance: harness design as a conditional systems problem

    Trajectory-level annotation (LLM judge with human validation) ties each aggregate effect to a distinct behavioral change: context management changes how long a trajectory survives, planning changes where it stops, and the action space changes the granularity at which code is written. The authors argue components should be selected per target model, task type, and budget rather than adopted as defaults, and offer the modular harness as a framework for evaluating future components.

    • Bash-only shifts Terminal-Bench file writing toward coarse create-or-replace actions and cuts re-patching of already-edited files across all four models.
    • For 550B on Terminal-Bench, bash-only shortens the median trajectory from 47 to 31 actions while raising the Write-code action share from 16% to 27%.
    • Practical read for harness builders: stage elision before summarization, skip lossless recall, gate planning and tool richness on model capability.

    Key findings

    • Context management's benefit is almost entirely overflow prevention: at 32k it lifts Nemotron-3 550B on SWE-Bench from 6.40% (T0) to 58.40% (T3) and Mistral from 12.60% to 66.20%, but by 128k T0 (59.80% / 67.40%) is nearly level with the managed tiers. Every managed tier overflows on zero tasks at every budget.
    • T4 (elide first, summarize only above the hard threshold) has the lowest mean cost per task at every window budget and the lowest average peak-context ratio, with success comparable to T1-T3 — the cheapest point of the accuracy-cost frontier in 7 of 8 model-benchmark panels.
    • Lossless recall is dead weight: across 32 matched T1-vs-T2 comparisons T2 wins 15 / loses 14 / ties 3, 36 of the 64 T2/T4 settings never call recall_event, and the 16 planning/action-space settings at T4/128k make zero recall calls.
    • Planning is load-bearing only for the weakest model: removing it drops Nemotron-3 30B from 25.20% to 13.60% SR on SWE-Bench and its median trajectory from 40 to 5 turns, with runs ending without an edit rising from 27.8% to 68.6%.
    • For strong models planning is a cost lever, not an accuracy lever: median SWE-Bench trajectories shrink from 108 to 74 turns (550B) and 68 to 53 turns (Mistral), mostly by cutting post-edit verification; Terminal-Bench cost falls about 26% (120B) and about 40% (Mistral) but rises 75% for 30B.
    • Action space crosses over with capability and task type: predefined tools give 30B +15.0 points on SWE-Bench and +10.1 on Terminal-Bench, while bash-only gives 550B 69.40% vs 65.80% SR on SWE-Bench at $1.11 vs $2.33; Mistral prefers tools on SWE-Bench (68.60% vs 45.40%) but bash on Terminal-Bench (43.82% vs 37.08%).

    Notable quotes

    Thus, context management is valuable largely because it prevents premature truncation when the window binds; as more unmanaged trajectories fit within the window, its marginal accuracy benefit shrinks and becomes more model-dependent.
    On Terminal-Bench, 66% of bash-only trajectories terminate after such out-of-interface emissions, shortening the average trajectory from 71 to 15 turns.
    Disabling planning reduces the median SWE-Bench trajectory length from 40 to 5 turns.
    Across all four models, bash-only reduces repeated patching of already edited files, from 3.3 to 0.4 re-patches for Nemotron-3 30B, 2.8 to 2.2 for 120B, 4.6 to 1.5 for 550B, and 3.0 to 1.3 for Mistral.

    Limitations

    • Results estimate the effect of these specific implementations, not a universally optimal harness: planning is one prompt plus one update mechanism, context management one threshold-based policy, and the action-space change is bundled (tool availability, interface prompts, file-state tracking, and post-edit diagnostics vary together).
    • Coverage and power are limited: planning and action space are ablated only at T4/128k, each setting is run once per task, and Terminal-Bench's 89 tasks leave many contrasts non-significant under the paired McNemar test.
    • External validity is bounded by three Nemotron-3 sizes plus one Mistral model and two benchmarks, with SWE-Bench Verified being Python-only; model size is an imperfect proxy for capability.

    Open questions

    • Do the planning and action-space effects persist under other tier/budget combinations, which would require a full factorial study?
    • Where exactly does the tools-vs-bash crossover sit for other model families and for non-Python or non-software-engineering task types?
    • Can recall-style lossless storage be made useful — e.g. by training models to invoke it — or is elision plus summarization simply the right lossy default?
