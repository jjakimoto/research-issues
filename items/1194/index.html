Repo2Skill-Evo: Repository Skills Go Stale in Silence

📰 Latest · 2026-08-30 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-30

Source: arxiv · 2026-08-22
Link: https://arxiv.org/abs/2608.21964

If you keep a SKILL.md / CLAUDE.md next to a fast-moving repo, this benchmark shows it rots invisibly at every release and no frontier agent can reliably clean it up: across 57 repos and 105 official release transitions, every transition invalidated part of the skill set (median 92 stale lines), and the best agent reached only 69.7% avg@3 macro F1 at removing stale content without over-editing. Treat repo skills as versioned artifacts pinned to a release, not write-once documentation.

Executive summary

Repo2Skill-Evo (ByteDance / Peking University / Beijing Jiaotong University) names and measures 'silent staleness': a repository-grounded agent skill stays loadable and retrievable after a release while its guidance quietly stops matching the code, and nothing raises an error. The authors distill a fixed, provenance-traced V1 skill set for each of 105 official release transitions across 57 public GitHub repos (1,158 skills, 12,217 manually verified stale V1 lines), then ask an agent to update it given only the V1 skill set and the official V1-to-V2 patch. Scoring is patch-grounded and line-level rather than execution-based, plus a complementary five-dimension LLM judge. Six frontier agents span 29.9%-69.7% avg@3 macro F1, failing in two opposite ways - missing affected skill files entirely, or editing far beyond what the patch justifies.

The problem: skills decay with no error signal

A repository skill is useful precisely because it encodes version-specific procedural knowledge - which APIs to call, which scripts to run, which conventions the current release expects. That same specificity ties its correctness to one repository state. After a release the skill remains loadable and retrievable while continuing to hand the agent obsolete guidance, and unlike a code-comment mismatch it is executed rather than merely read.

  • Distinct from code migration: the maintained object is the agent-facing guidance derived from the repo, not the repo code.
  • Distinct from runtime skill repair (which needs an observed execution failure) - silent staleness produces no error log to react to.
  • Motivated by real practice: SKILL.md as an emerging cross-agent format, and PyTorch shipping repo-local skills for dispatch-macro migration, Metal kernels, AOTInductor debugging and docstring maintenance.
  • Related systems cited on other lifecycle stages: SkillGuard (environment-contract violations), SkillOps (typed contracts), Library Drift (retrieval degradation), SkillHone (iterative revision).

Benchmark construction: 57 repos, 105 release transitions, expert-frozen V1 skills

Construction completes before any maintenance model is evaluated. Repo2Skill distills the V1 skill set with a staged analyze/logic/materials/draft/validate/finish loop that builds a symbol index and logs the source paths and symbols behind each claim. A grounding gate rejects candidates whose fraction of unverifiable path/symbol references exceeds a threshold; semantic correctness is left to a human expert. For each transition, two frontier models each produce one candidate from the pre-release repo only; an expert picks the stronger, revises and verifies it, and freezes it before gold labels are built. All maintenance agents then share that identical V1 skill set.

  • 105 official release transitions from 57 public GitHub repositories; 1,158 individual skills across the corpus.
  • Each instance records repo, V1 and V2 tags, base/target commit hashes, and the public source diff, so every instance is auditable upstream.
  • Corpus skews to the fast-moving AI/ML ecosystem: 33 transitions from agent/RAG frameworks, 32 training and inference infra, 17 data and classic ML, 16 compiler/kernel/systems, 7 general-purpose libraries.
  • Transitions with an empty gold obsolete set are excluded - deliberately a staleness-positive challenge set, so it measures difficulty, not prevalence.
  • Named examples: flask-2.2.5-2.3.0, DeepSpeed-0.17.6-0.18.0, peft-v0.15.0-v0.16.0, datasets-3.0.0-4.0.0, milvus-v2.5.10-v2.5.15, langchain-core 1.0.7 to 1.1.0.

What counts as stale, and how it is scored (not execution-grounded)

For each transition the authors build a gold obsolete set: the V1 skill lines the official patch directly shows to be invalid under V2. A script first surfaces candidates by matching symbols, paths, commands and config keys referenced in the skill set against changed patch lines; every final line is then manually verified against direct patch evidence. The headline metric is purely diff-based - the response set is the V1 lines on the deletion side of the skill diff, so it captures deletions and revisions but deliberately ignores newly added lines, because a valid V2 replacement admits many phrasings. There is no downstream execution or test-passing check anywhere in the metric.

  • Recall = stale coverage; Precision = edit restraint; F1 their harmonic mean, macro-averaged over transitions. avg@3 = mean over three runs; best@3 = per-transition max.
  • 12,217 gold stale lines total; 5 to 375 per transition; median 92, mean 116.4, quartiles 46/92/156. Only 7 transitions have fewer than 20 stale lines; 48 have at least 100.
  • Five obsolescence categories: API/interface change, signature or default change, file or entry-point change, command or configuration change, behavioral contract change - plus dependent examples, table rows and script lines transitively invalidated.
  • Worked example: flask 2.2.5 to 2.3.0 removes the environment-mode surface, so the app-env-config skill's reference-table rows, prose using app.config[ENV], and script lines setting FLASK_ENV or reading app.env all become stale.
  • Complementary NL Judge scores five 0-2 dimensions (API correctness, file consistency, info retention, prompt adherence, current-state prose) summing to 0-10, with structurally invalid skill sets form-gated to zero.
  • Agent scaffold is deliberately minimal: six generic tools, no task-specific localization or repair module, fixed 50-turn budget with remaining budget reported to the agent.

Results: 29.9%-69.7% avg@3 macro F1, with two opposite failure modes

Six agents x 105 transitions x 3 runs = 1,890 runs. Claude-opus-4.6 leads at 69.7% avg@3 macro F1 with the most balanced recall/precision (70.4 / 75.7); GLM-5.1 follows at 64.3%; the other four fall below 60%. GPT-5.4 has the highest recall of any model (74.6%) but the lowest precision (55.7%) - it edits a removal load of 2.84x the gold target with a 44.3% off-target edit rate. The bottom three fail the other way: high precision but recall of 40.4%, 31.9% and 22.6%, driven by affected-file coverage of just 0.74, 0.53 and 0.51.

  • Model ordering survives repository-clustered bootstrap: the three adjacent gaps among the top four all have 95% CIs excluding zero.
  • best@3 tops out at 76.1% - repeated attempts buy 6.4 points for the leader and 9.6-16.1 for the rest, i.e. capability without reliability. Per-transition run-to-run F1 std dev runs 6.1 to 14.7.
  • Affected-file coverage correlates with F1 at r=0.650 and recall at r=0.701 across 1,890 runs. Full-coverage runs average 67.3% F1 vs 41.0% for partial coverage.
  • Removal load is the other lever: runs with load in [0.75,1.25) average 77.3% F1 vs 25.0% below 0.5; runs at or above 1.25 reach 80.8% recall but only 44.7% precision.
  • Both LLM judges independently rank the same top tier as the patch-grounded metric. Every model emitted structurally invalid skill sets in 7-26 of its 315 runs.
  • Difficulty is broad, not a long tail: only 20 of 105 transitions reach Easy (>=0.65), 60 are Medium, 25 are Hard (<0.40).
  • Training and inference infrastructure is the hardest domain (46.4% mean F1); data and classic ML is easiest at 57.8%.

Ablations: localization helps but does not solve it; and the skills were worth maintaining

An oracle ablation on the hardest-20 subset appends only the gold-affected skill roots and file paths to the prompt - no patch hunks, no line numbers, no labels. Mean avg@3 macro F1 rises from 32.8% to 45.0% (+12.2 points, 95% paired bootstrap CI [+6.8,+17.8]) and recall improves for every model, yet the best model still only reaches 62.3% on that subset. A separate motivating study confirms the skills are worth keeping current at all.

  • Oracle gains are largest for the weakest localizers (+20.8, +17.6, +12.9 F1) and smallest for the leader (+8.7), consistent with localization being their binding constraint.
  • Utility study: GPT-5.4, 10 randomly sampled repos, 2x2 over source and skill access, 3 runs per cell, hidden per-repo rubric scored 0-10 by hand.
  • Skill-only lifts mean utility 5.88 to 8.68 (+2.80), essentially matching source-only (8.64); source+skill reaches 9.01.
  • Gains concentrate where the model knows least: +3.98 in the low-baseline half vs +1.61 in the high-baseline half.
  • Skills are far cheaper than source access for the same utility: 51,821 mean tokens and 3.9 iterations (skill-only) vs 272,620 tokens and 10.8 iterations (source-only).

Why this matters if you maintain your own skill files

The practical reading for anyone shipping SKILL.md / CLAUDE.md / agent playbooks alongside a fast-moving codebase: the failure mode is not that the skill breaks loudly, it is that it keeps working syntactically while lying. The numbers say you cannot currently hand skill maintenance to an agent and walk away - the best frontier agent leaves roughly 30% of patch-verified stale guidance in place and still makes about a quarter of its edits outside what the patch justifies.

  • Pin the release: record the version tag and the source paths/symbols behind each claim, as Repo2Skill's provenance metadata does - that is what makes patch-to-skill localization tractable at all.
  • Localization first: coverage of affected skill files was the single strongest correlate of maintenance quality (r=0.650 with F1). A CI step mapping a release diff to the skill files touching those symbols recovers most of the oracle's gain.
  • Watch for over-editing too: the highest-recall model was only third overall because 44.3% of its edits fell outside the justified set - wholesale regeneration destroys still-valid repo knowledge.
  • Budget matters: three of six models exhausted the 50-turn budget in 14.6%-68.6% of runs, so partial, half-updated skill sets are a realistic production outcome.

Key findings

  • Every one of the 105 selected release transitions invalidated part of its V1 skill set: 12,217 patch-verified stale skill lines in total, median 92 per transition (range 5-375), across 1,158 skills in 57 repositories.
  • Six frontier agents span only 29.9%-69.7% avg@3 macro F1 on patch-grounded stale-content removal; Claude-opus-4.6 leads at 69.7% (70.4 recall / 75.7 precision), MiniMax-M2.5 trails at 29.9%.
  • Detection is patch-grounded and line-level, NOT execution-grounded: a manually verified gold obsolete set of V1 lines is matched against the deletion side of the skill diff, with an LLM judge only as a complementary final-state check.
  • Two opposite failure modes: GPT-5.4 gets the best recall (74.6%) but edits 2.84x the gold volume with 44.3% off-target edits, while Kimi/Doubao/MiniMax localize only 0.51-0.74 of affected skill files and remove just 22.6-40.4% of stale content.
  • Affected-file coverage is the strongest single correlate of quality (r=0.650 with F1, r=0.701 with recall); full-coverage runs average 67.3% F1 versus 41.0% for partial-coverage runs.
  • Oracle file localization on the hardest-20 subset lifts mean F1 from 32.8% to 45.0% (+12.2, CI [+6.8,+17.8]) but the best model still only reaches 62.3% - localization alone does not fix within-file evidence tracing or edit selection.
  • The skills are demonstrably worth maintaining: skill-only access lifted artifact utility from 5.88 to 8.68, matching full source access (8.64) at roughly one-fifth the tokens (51,821 vs 272,620).
  • Difficulty is systemic, not tail-driven: only 20 of 105 transitions score >=0.65 mean F1; 85 fall below that, and 25 fall below 0.40.

Notable quotes

Because no explicit signal marks this mismatch, the outdated guidance may continue to be retrieved and followed.
It is not merely reviewed by human maintainers but can also be retrieved and executed by autonomous agents.
High precision in this regime does not imply successful maintenance; it coexists with substantial under-editing.
File-level localization is therefore important but insufficient: agents must still identify the affected claims within each file and select the appropriate edits.

Limitations

  • The corpus is a curated staleness-positive challenge set - transitions with an empty gold obsolete set were excluded - so it measures maintenance difficulty on releases known to break skills, and says nothing about how often releases break skills in the wild.
  • Evaluation stops at patch-grounded maintenance fidelity plus an LLM judge: the maintained skill sets are never re-run on downstream repository tasks, so the actual utility recovered by maintenance is unmeasured.
  • The headline metric scores only the V1 deletion side and ignores newly added lines, and the gold set rests on manual line-level annotation; contamination is not ruled out, since the repositories may appear in model pretraining.

Open questions

  • How prevalent is silent staleness across ordinary releases, and can a cheap detector flag which releases actually invalidate a skill set before a human looks?
  • Does maintaining a skill set recover its downstream task utility, or can a skill score well on patch-grounded removal while still misguiding an agent?
  • Since oracle file paths close only about a third of the gap, what scaffolding - symbol-level provenance links, patch-hunk-to-claim retrieval, verifier loops - fixes within-file evidence tracing and edit selection?
