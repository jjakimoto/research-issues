    CRAFT: Customizing LLMs by Creating and Retrieving from Specialized Toolsets

    ← Go backTroVE: Inducing Verifiable and Efficient Toolboxes for…NextMarket impact and trading profile of large trading orders in… →
    📚 Foundations · 2026-09-19
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-19

    Theme: Induced executable skill libraries
    CRAFT and TroVE replace static, expert-written tool APIs with libraries synthesized from solved tasks. CRAFT emphasizes offline validation, abstraction, deduplication, and retrieval; TroVE grows and prunes a toolbox online using executable agreement, simplicity, reuse, and human verification efficiency.
    Source: arxiv
    Link: https://arxiv.org/abs/2309.17428

    A foundational design for converting task examples into validated, deduplicated executable functions that agents can retrieve and reuse instead of regenerating every solution from scratch.

    Executive summary

    CRAFT builds task-specialized executable toolsets offline and retrieves relevant functions at inference time, adapting off-the-shelf LLMs without fine-tuning. Its pipeline combines diversity-oriented problem sampling, GPT-4 code generation, abstraction, validation, deduplication, and multi-view retrieval over problems, function names, and docstrings. Experiments across visual question answering, tabular processing, and algebra show large gains, although the approach is restricted to code-solvable tasks and depends strongly on the backbone model's tool-use ability.

    Problem and design

    General-purpose API collections often omit specialized operations, while prior tool-creation methods produce either one broadly applied tool or query-specific code with limited reuse. CRAFT instead constructs a large task-specific library whose entries are small executable functions, then injects retrieved tools into the model's prompt.

    • The approach is training-free and plug-and-play for the downstream backbone model.
    • The authors estimate total toolset-construction cost at approximately $2,500.
    • Atomic executable functions make behavior inspectable and allow complex solutions to compose multiple tools.

    Tool creation and verification

    CRAFT iteratively samples diverse problems by adding those least similar to the current set under SimCSE embeddings. GPT-4 generates Python solutions; only correct executions survive. It then abstracts specific identifiers and embedded textual constants into generic variables and arguments, assigns function names and docstrings, validates each abstraction on its originating problem, and deduplicates tools sharing a function name and argument count by selecting the most generally applicable version.

    • Each sampling iteration adds 100 least-similar problems.
    • The VQA library starts from 2,000 sampled problems: 1,000 initially and 1,000 across ten later epochs.
    • TabMWP and MATH each use 500 sampled problems: 200 initially and 300 across three later epochs.

    Multi-view retrieval and execution

    For a target question, the backbone predicts useful function names and docstrings. CRAFT independently retrieves by similarity to the target problem, predicted function name, and predicted docstring, ranks tools by occurrence across the three lists, selects up to the three most frequent, and removes tools appearing only once. Retrieved function code is added to the prompt and executed with the generated solution.

    • Retrieval uses k=10 for problem matching, k=5 for function-name matching, and k=10 for docstring matching.
    • If every candidate appears in only one retrieval view, CRAFT returns no specialized tool and the model generates code directly.
    • The function-name view was the most consequential ablation on the VQA benchmarks.

    Empirical results

    With GPT-3.5-Turbo, CRAFT produced VQA soft-accuracy gains over the vanilla ViperGPT baseline of 10.4 points on GQA, 18.0 on OK-VQA, and 15.2 on A-OKVQA. It also reached 68.1 accuracy on MATH algebra. On TabMWP, CRAFT scored 88.4, narrowly below the BM25 retrieval baseline's 89.2, which the authors attribute to that dataset's relatively simple patterns.

    • CRAFT achieved the strongest scores in Table 2 on all six VQA metrics and on MATH algebra.
    • With GPT-4, CRAFT remained ahead of ViperGPT on all three VQA datasets, though by smaller margins than with GPT-3.5-Turbo.
    • Removing abstraction reduced GPT-3.5 GQA soft accuracy from 45.4 to 37.1.

    Scaling, library structure, and scope

    Soft accuracy rose consistently as the VQA library expanded through 0, 261, 337, and 525 tools, with the largest gain occurring between zero and 261 tools. The resulting libraries had low reported average cyclomatic complexity, but varied substantially in diversity: mathematical tools formed many more detected classes relative to library size than tabular tools.

    • VQA: 525 tools, 195 detected classes, average cyclomatic complexity 2.64.
    • Tabular processing: 181 tools, 23 classes, average complexity 2.07.
    • Mathematical reasoning: 282 tools, 234 classes, average complexity 1.34.

    Key findings

    • Validation and deduplication turn generated solutions into a reusable library rather than an unverified cache of demonstrations.
    • Retrieval works best when the target problem, proposed API name, and proposed docstring jointly vote on candidates; removing any view hurts performance.
    • Specialized tools substantially improved all reported VQA measures and MATH algebra, while simple BM25 retrieval remained slightly better on TabMWP.
    • Performance increased as the VQA toolset grew, and CRAFT continued to help when GPT-4 replaced GPT-3.5-Turbo.
    • The libraries contained low-complexity functions, but their measured diversity depended strongly on the task.

    Notable quotes

    The validation step ensures the correctness of the created tools.
    After retrieval, the code snippets of tools are added to the prompt of LLMs for code generation to solve a given question.
    The results in Figure 3 show a consistent increase in soft accuracy as the toolset expands across 3 datasets, demonstrating the scalability and potential of CRAFT.
    This indicates that CRAFT is only suitable for tasks that can be solved via writing code solutions.

    Limitations

    • CRAFT's creation procedure is based on executable code, so the paper limits its applicability to tasks that can be solved by writing code solutions.
    • Effectiveness depends heavily on the backbone's tool-manipulation ability; the authors report near-random pilot performance for some open-source models.

    Open questions

    • Can pseudocode or another representation extend reusable tool creation to tasks that cannot be expressed as executable code?
    • How can reliable tool manipulation be elicited in open-source backbone models?
    • Does performance continue improving beyond the tested 525-tool VQA library, and how should validation and retrieval scale while preserving tool quality?
