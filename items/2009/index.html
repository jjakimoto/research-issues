    Correct Code, Broken Contributions? SWE-CC: Benchmarking Repository Policy Compliance for Coding Agents

    ← Go backAgent Skill Evolution: How Revisions Affect Coding AgentsNextIn 'AgentDiscover' (arXiv 2610.05334), the kernel-builder… →
    📰 Latest · 2026-10-06 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-06

    Source: arxiv · 2026-10-05
    Link: https://arxiv.org/abs/2610.06193

    Coding agents whose patches pass SWE-bench tests still break about 36-48% of each repository's own contribution rules, such as commit format, PR metadata and AI-disclosure. About half of those violations happen in the agent's process, not in the patch, so grading only the patch misses them. Telling agents to read the CONTRIBUTING docs barely helps, because most agents never fetch them. Handing agents a pre-extracted rules file raises compliance by about 9 points and leaves functional resolve rate unchanged.

    Executive summary

    SWE-CC turns the contributor documentation of the 12 SWE-bench Verified repositories into 823 mandatory, atomic, machine-checkable policies. Each policy is compiled into a deterministic Python checker (written by Claude Opus 5 and audited by humans) that grades both the agent's execution trajectory and its final commit and PR text. No LLM judge is used. On 500 SWE-bench Verified tasks extended to require a real git commit plus a PR description, the authors tested four models (GPT-5.6 Luna, Gemini 3.7 Flash, DeepSeek V4 Flash, Kimi K2.5) under two scaffolds (mini-SWE-agent, OpenHands). The agents resolve 74.6-94.4% of issues but comply with only 51.8-63.8% of triggered policies when they must find the docs themselves. A pre-extracted rules file raises compliance by about 8.75 points on average (best 71.2%) with no loss in resolve rate. In resolved runs, 50.3% of violations occur in the trajectory, where patch-only evaluation cannot see them. This is an arXiv preprint (v1, cs.SE) and has not been peer reviewed.

    Problem: passing tests is not the same as a mergeable contribution

    Existing SWE benchmarks score only test execution. Mature projects also publish repository-specific rules on code style, commits, tests, docs and AI use, and maintainers increasingly complain about non-compliant AI pull requests. The motivating example is a SWE-bench-resolved Django patch that passes the full suite but uses self.assertTrue(all(...)), while Django's docs require assertIs for Boolean assertions. Earlier non-functional benchmarks also grade only the final patch and inject the rules into context. SWE-CC instead audits the whole workflow and, in its Native setting, makes the agent find the policies itself.

    • Closest prior benchmarks: SWE-NFI (92 policies from literature, patch quality), SWE-Gate (303 from code-review history), RepoComplianceBench (455, AI-declaration only), SWE-SHIELD (1,787, LLM-as-a-judge).
    • SWE-CC is the only one in the comparison table that audits agent behavior and requires the agent to retrieve policies itself, and it uses executable checkers.
    • Formally, each checker f_k(trajectory, output) returns pass, fail, or not-applicable.

    Benchmark construction pipeline

    For each repository, Claude Opus 5 (high reasoning effort, running in Claude Code, Aug-Sep 2026) did five steps. (1) Built a source manifest from the pinned developer docs, plus off-navigation files fetched as raw text: PR templates, pre-commit config, and CLAUDE.md, AGENTS.md or copilot-instructions.md files. (2) Extracted atomic rules, each with a precondition and a required behaviour. (3) Classified them with written rubrics by evidence type, contributor scope, and must versus should. (4) Compiled each 'must' rule into a checker: a precondition that selects targets (each commit, changed file or command) and a post-condition that returns Satisfied, Violated or Undetermined. (5) Validated the checkers. One author reviewed the manifest and the extraction at checkpoints.

    • 1,759 atomic rules were extracted. 989 are in scope (observable in a patch-plus-trajectory harness) and 823 are mandatory. The 166 in-scope 'should' rules get no checker.
    • Evidence types of the 823: 684 read the final output, 66 compare pre- and post-patch states (differential), and 73 need the trajectory.
    • Each checker ships with authored satisfied, violated and not-applicable cases: 2,603 cases in total, and 767 of 823 checkers (93%) have all three.
    • 294 checks are exact and 529 approximate (64%). For example, Django's past-tense commit-subject rule uses a list of -ed endings plus 118 irregular verbs. On 3,661 Django commits it agrees with a human reader 99.6% of the time.
    • Human audit: 150 checks (18%), stratified sample, two raters, 94.0% raw agreement, Cohen's kappa 0.72. The weighted mean accept rate is 87.2% (95% CI 82.1-92.3); 83.7% when both raters must accept. Most rejections involve preconditions that select too much.
    • Policies per project range from 2 (seaborn) to 167 (matplotlib). Only 12 of 823 (1.5%) have a similar policy in another project, and some conflict: Django requires an issue number in commit messages, Flask prohibits one.
    • Grading uses no model and takes 120-215 ms per run on an M4 Pro MacBook. Ownership modes (created / touched / enclosing) ensure agents are graded only on code they wrote or edited.

    Evaluation setup

    The 500 SWE-bench Verified tasks are extended into full contributions. The agent must make a real git commit and write a PR description as text. There is no remote and no real PR object. Two policy-provision settings are compared. In Native, the agent gets the docs URL and is told to read it before starting. In Consolidated, the atomic policies are mounted as a local CONTRIBUTING_RULES.md file that the agent is told to read. The setup totals 8,000 runs: 4 models x 2 scaffolds x 2 settings x 500 tasks.

    • Scaffolds: mini-SWE-agent and OpenHands (SDK commit 43376f1, browser enabled so the agent can fetch docs). Stock system prompts are kept; only the task prompt changes.
    • Models: GPT-5.6 Luna, Gemini 3.7 Flash, DeepSeek V4 Flash 0731, Kimi K2.5. Claude Code, Codex and Claude models were not evaluated as agents. Claude Opus 5 was used only to build and pre-review the benchmark.
    • Metrics: Triggering Rate (share of the repo's policies whose precondition fires), Compliance Rate (passed / triggered; withheld policies are excluded) and Resolve Rate (standard SWE-bench).
    • Sanity check: three of four models' Native mini-SWE-agent resolve rates are within 5 points of the Vals AI leaderboard. GPT-5.6 Luna is 14.4 points lower (78.6 vs 93.0), which the authors attribute to using the default model class instead of the Responses API.

    Results: widespread non-compliance, half of it in the trajectory

    Across all configurations, compliance is far below functional success. In resolved runs an execution triggers 22.6 policies on average and violates 7.7 (34.1%); Consolidated lowers that to 6.6. 50.3% of violations in resolved runs occur in the trajectory (for example, running the test suite before committing), not in the final patch. Supplying the rules raises compliance for every model, and resolve rate moves by no more than 2 points.

    • Best compliance: DeepSeek V4 Flash on OpenHands, 63.8% Native and 71.2% Consolidated. It also has the best resolve rate (94.4%).
    • Largest gain from Consolidated: GPT-5.6 Luna, +15.8 points on mini-SWE-agent and +12.2 on OpenHands. Smallest: Kimi K2.5 on mini-SWE-agent, +1.0.
    • OpenHands beats mini-SWE-agent slightly on average compliance (58.2 vs 55.7 Native; 67.0 vs 64.4 Consolidated).
    • Using only the 294 exact checks changes compliance rates by at most 4.7 points, and the Consolidated gains get larger (e.g., Gemini on mini-SWE-agent goes from +11.4 to +18.3).
    • Link between functional success and compliance: the paper does not compute a correlation. At the model level, the highest resolver (DeepSeek) also complies most. But Kimi K2.5, the lowest resolver, out-complies GPT-5.6 Luna, and Consolidated raises compliance while resolve rate stays flat. That suggests the two are largely independent.

    Where agents fail: policy categories and retrieval

    Compliance varies sharply by governance domain. Style rules are mostly followed by default. AI-disclosure rules are almost universally triggered and almost universally broken. In the Native setting most agents never even try to fetch the guidelines.

    • AI-assisted contribution policy: 92-96% triggering and the lowest compliance, 15.3% Native on mini-SWE-agent and 20.6% on OpenHands, rising only to 26.6% and 30.7% with the rules supplied. This happens even though OpenHands' stock prompt already asks for AI disclosure.
    • Git and commit conventions improve most with consolidated rules: 59.9 to 87.0 (mini-SWE-agent) and 63.4 to 90.1 (OpenHands).
    • Language and framework style is already 84% compliant Native, with about +1-2 points from consolidated rules.
    • Native retrieval: on average 71.1% of runs never try to fetch the docs (attempt rate 28.9%), and only 12.6% actually get policy text into context. Gemini 3.7 Flash (2.8-10% attempts) and Kimi K2.5 (3.6%) almost never try. GPT-5.6 Luna on OpenHands tries in 75.6% of runs.
    • Consolidated: 91.6% of runs open the rules file and 99.6% of its content reaches context, yet compliance stays at about 56-71%. The authors conclude that failures come from both retrieval and reasoning.

    Significance for people building with coding agents

    Repository governance is project-specific and often conflicts across projects, so generic 'good style' priors are not enough. Agents rarely go looking for contribution docs on their own, so the rules have to be placed in the agent's context in a pre-digested, atomic form, similar to AGENTS.md or CLAUDE.md. Even then, deterministic checks over the trajectory and the commit/PR artifacts are needed, because roughly a third of rules are still broken. SWE-CC's precondition/post-condition checker design, released at github.com/dangtruong01/swe-cc-arxiv, is a usable pattern for pre-commit or CI compliance gates on agent output.

    • Mandatory AI-disclosure rules already exist in 11 of the 12 projects, and agents almost never satisfy them.
    • Report compliance rate together with triggering rate: an agent that does less (a one-line commit with no PR text) can score 100% compliance on only 6 triggered policies.

    Key findings

    • Agents resolve 74.6-94.4% of SWE-bench Verified issues but comply with only 51.8-63.8% of triggered repository policies in the Native setting. The best case, DeepSeek V4 Flash on OpenHands with consolidated rules, still violates about 29% (71.2% compliance).
    • In functionally resolved runs, agents violate a mean of 7.7 of 22.6 triggered policies (34.1%) per execution, and 50.3% of these violations are in the trajectory. Patch-only evaluation cannot detect them.
    • Giving agents the pre-extracted rules file raises compliance by about 8.75 points on average (up to +15.8 for GPT-5.6 Luna on mini-SWE-agent), and resolve rate changes by at most 2 points.
    • AI-assisted contribution policies (e.g., disclose AI tool use) trigger in about 92-96% of runs but have the lowest compliance: 15.3-20.6% Native and at most 30.7% with rules supplied.
    • In the Native setting, 71.1% of runs never try to fetch the contribution docs and only 12.6% retrieve policy text. Gemini 3.7 Flash and Kimi K2.5 try in under 10% of runs.
    • Restricting to the 294 exact (non-heuristic) checks changes compliance by at most 4.7 points, so the main conclusions do not depend on the approximate checkers.

    Notable quotes

    An evaluation that inspects the final patch alone misses these violations, and SWE-CC captures them by checking the trajectory.
    Because pre-trained models naturally adopt idiomatic code formatting, they satisfy these intrinsic conventions by default.
    Nevertheless, compliance remains low despite full in-context visibility, demonstrating that governance failures stem from both retrieval and reasoning processes.
    A compliance rate alone can reward an agent for doing less work, since fewer actions trigger fewer policies.

    Limitations

    • Coverage and checker fidelity: 304 of 823 policies (37%) never trigger on a bug-fix task set. In Code and quality only 27% of triggered policies can actually be graded (64% in Tests), because many need a type checker or full test run. 64% of checkers are approximate, and the human audit accepts an estimated 87% (83.7% if both raters must agree). The checkers and the automated pre-review were both produced by Claude Opus 5.
    • Scope of agents and harness: no Claude Code, Codex CLI or Claude/GPT-Codex agent setup was evaluated, only mini-SWE-agent and OpenHands with four non-Anthropic models. The harness is patch-only with a simulated text PR and no real CI or review. Prompts were modified (stock step and cost limits removed), and 18 checks require a human contributor to certify the change, which agents structurally cannot satisfy. Django makes up 46% of instances but only 9% of policies.
    • The paper is a preprint and has not been peer reviewed. Its headline violation figures are not fully consistent: 43.1% overall from the abstract, 44.7% for GPT-5.6 Luna, 34.1% per resolved execution, and 'nearly 30%' for the best configuration. They use different denominators.

    Open questions

    • Would production agents such as Claude Code or Codex, which load AGENTS.md or CLAUDE.md natively and can run hooks, close the retrieval gap and come closer to Consolidated-level compliance or better?
    • Do SWE-CC compliance rates predict real maintainer merge or reject decisions, given that the raters were not project maintainers?
    • Can running these deterministic checkers as in-loop feedback (pre-commit or self-check tools), or training against them, remove the roughly 30% of violations that remain even with the rules fully in context?
