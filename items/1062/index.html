SkillForge: Self-Distilling Agents for Project-Specific Issue Resolution

📰 Latest · 2026-08-24 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-24

Source: arxiv · 2026-08-19
Link: https://arxiv.org/abs/2608.18933

You can bootstrap a project-specific skill layer for a coding agent BEFORE any real issues arrive, by having an LLM blindly re-implement test-covered code to manufacture executable synthetic bugs, solving them, and distilling the trajectories into entity-grounded skill records keyed to file paths. The gain over the same scaffold with no skills is +5.8/+5.6 Pass@1 on SWE-bench Verified for ~1.5x amortized cost — but the skills are model-specific: reusing DeepSeek-distilled skills under GPT-5-mini erases the entire gain.

Executive summary

SkillForge (Shanghai Jiao Tong University) is a self-distillation framework that gives an SWE agent project-specific knowledge proactively, without waiting for issue history or paying per-issue test-time exploration. It traces which code segments a passing test executes, asks an LLM to blindly re-implement those segments (a strict-mask rewrite that naturally introduces realistic bugs), turns the resulting test failures into SWE-bench-format synthetic issues, has a Mini-SWE-Agent solve them, and distills the trajectories into a dual-level skill repository indexed by repository entity. Downstream, BM25 retrieves top-5 global diagnostic skills into the system prompt and local intervention skills are injected just-in-time whenever the agent touches a matching file. On SWE-bench Verified it reaches 72.2% (DeepSeek-V3.2) and 60.6% (GPT-5-mini) Pass@1, ahead of every history-driven and online self-evolving baseline tested.

The problem: cold-start project-specific knowledge

Agents deployed on a specific repository must rediscover its conventions every time — brittle modules, repo-specific API contracts, implicit execution coupling. Existing self-evolving agents acquire this knowledge REACTIVELY, and the paper argues both flavors are bounded. History-driven methods (EvoCoder, SWE-Exp, ExpeRepair, MemGovern) can only learn from issue types that already happened. Online methods (SAGE, SWE-Debate, Live-SWE-agent) pay trajectory and token cost per target issue, and the guidance only exists after the issue arrives.

  • Framed as a cold-start problem: with no accumulated knowledge a strong agent is 'reduced to a generic repository explorer'.
  • The claim is that the supervision signal for project-specific knowledge already sits in the repo's own tests and code, so it can be harvested offline.
  • Supervision comes solely from the codebase + test suite: no historical issue reports, no human-written bug descriptions.

Stage 1 — synthesizing project-specific issues by blind re-implementation

Rather than injecting handcrafted mutations, SkillForge runs each PASSING test under coverage instrumentation to get an execution trace, extracts contiguous segments with surrounding context, then uses an LLM to rank and pick the top-k critical segments. For each selected segment the LLM re-implements it WITHOUT seeing the original code — it gets only the preceding/following lines, the location and indentation, and a high-level description of the test's goal. Because the model must reconstruct behavior from its general coding priors, it naturally diverges from the repo's conventions, and that divergence is exactly the knowledge gap worth learning.

  • Validity of a synthetic issue is grounded in EXECUTION, not an LLM judge: the rewrite must actually break the repo's own tests.
  • Unlike SWE-Smith's single-function rewriting, one synthetic issue can span MULTIPLE coordinated segments exercised by the same test, capturing cross-component interaction.
  • The agent then solves each synthetic instance under the normal SWE-bench protocol; the full action trajectory is recorded for distillation.
  • 577 synthetic issues were generated for the SWE-bench Verified evaluation.

Stage 2 — what a 'skill' concretely is, and how it is grounded

A skill is a natural-language JSON record keyed to a repository entity (an api_path such as 'django/db/models/sql/compiler.py') — not code, not a test, not a patch. Before distillation, trajectories are normalized and entity-aligned: shell commands are parsed to extract accessed files and line ranges, resolved against an AST-derived structural index; files in the submission diff, golden patch and test patch are added. Global diagnostic skills hold purpose, playbook and related_apis per entity; local intervention skills hold entity-specific modification cues and pitfall warnings distilled from both successful and failed trajectories.

  • Skill = text. Grounding is threefold: the entity must exist in the AST index; the trajectory really happened; failed-trajectory lessons are anchored against the reference patch.
  • No automatic skill validation, scoring, deduplication or RETIREMENT mechanism is described — quality is checked only by a manual inspection in the Discussion.
  • Global skills answer 'where do I start looking and what else is involved'; local skills answer 'how should I edit this specific entity'.

Stage 3 — retrieval: BM25 priors plus just-in-time entity-triggered injection

Adaptation is two-stage. Macro: before the agent starts, the issue description is a BM25 query over global skills and the top-k records are prepended as project-specific priors. Micro: at every step SkillForge parses executed shell commands for file paths, and matching intervention cues are appended as an auxiliary observation. The paper contrasts this with centralized semantic-similarity memory stores — retrieval is triggered by actual code interaction, not only embedding similarity.

  • Global skills are retrieved once, semantically (BM25, top-5 by default).
  • Local skills are retrieved continuously, by file-path match on the agent's own commands — a genuinely different trigger from RAG-over-memory.
  • The hyperparameter study confirms the anti-flooding rationale: retrieving ALL relevant skills is worse than top-5 (67.5% vs 69.7%).

Setup, and how leakage is controlled

Implemented on Mini-SWE-Agent with DeepSeek-V3.2 and GPT-5-mini at temperature 0, a 250-step budget, BM25 top-5, Pass@1 averaged over three runs. Benchmarks: SWE-bench Verified (500 tasks) and the full SWE-bench Pro (731 instances, Python/JS/TS/Go). Contamination control is temporal: for each target instance the repository is rolled back to BEFORE both the golden patch and the golden test patch, and retrieval is restricted to skills from synthetic issues whose source commits PREDATE the target instance's gold commit.

  • Two controlled variants isolate the source of the knowledge: 'w/ SWE-Smith' swaps in single-function rewriting; 'w/ LLM Summary' swaps trajectory-distilled skills for static LLM repo summaries.
  • Cost is average end-to-end USD per evaluated issue with offline pre-computation amortized over the evaluated instances.
  • A second leakage check: the issue-type distributions of the synthesized issues and the real SWE-bench issues from the same repositories DO NOT OVERLAP.

Results, ablations and the transfer caveat

SkillForge hits 72.2% (DeepSeek-V3.2) and 60.6% (GPT-5-mini) Pass@1 vs 66.4%/55.0% for bare Mini-SWE-Agent, beating the strongest history-driven baseline MemGovern by +3.0/+2.6 and every online baseline. On SWE-bench Pro it reaches 34.1%/51.7% vs 28.3%/47.6%. Repository-level analysis over the seven largest repos shows gains on all seven under both backbones with no regression, whereas SWE-Exp regresses on three. The sharpest negative result is cross-model transfer: the transfer table is strictly diagonal.

  • Cost: $0.074 vs baseline $0.049 (DeepSeek) INCLUDING amortized offline synthesis, against SWE-Debate's $0.382.
  • Skill injection alone is NOT the win: 'w/ LLM Summary' actually goes DOWN for GPT-5-mini (54.4%, -0.6 vs baseline).
  • Cross-LLM: DeepSeek resolver drops 72.2% -> 65.2% on GPT-5-mini-distilled skills; GPT-5-mini drops 60.6% -> 55.0% on DeepSeek-distilled skills, i.e. back to exactly its no-skill baseline.
  • Case study (Django #11206): the no-skill agent invents an exponent-based zero heuristic and fails 0/2 FAIL_TO_PASS; the skill-guided agent is told to preserve the existing Decimal formatting pipeline and passes 2/2.

Key findings

  • A 'skill' is plain-text JSON keyed to a repository entity, never code or tests. Validity comes from execution (the synthetic issue must actually break the repo's tests) plus AST-based entity alignment — there is no LLM judge and no automatic retirement of stale skills.
  • Proactive synthetic-issue distillation beats every reactive baseline: 72.2%/60.6% Pass@1 on SWE-bench Verified (+5.8/+5.6 over Mini-SWE-Agent, p<0.05), +3.0/+2.6 over the best history-driven method, and 34.1%/51.7% on SWE-bench Pro.
  • The gain does not come from 'inject some text into the prompt'. Static LLM repository summaries give only 68.7% on DeepSeek and actually HURT GPT-5-mini (54.4%, below its 55.0% baseline).
  • Distilled skills are model-specific, not repo-universal: the transfer matrix is strictly diagonal, and GPT-5-mini using DeepSeek-distilled skills falls to exactly its no-skill baseline.
  • Both skill levels contribute, with the local/JIT one slightly more: -3.8/-3.0 without global skills, -4.4/-3.4 without local skills.
  • More retrieved skills is not better — top-5 BM25 peaks at 69.7% while full retrieval drops to 67.5%.
  • Leakage is controlled temporally (repo rolled back before both gold patch and gold TEST patch; retrieval restricted to pre-dating commits), and the synthesized-issue type distribution does not overlap the real SWE-bench distribution for the same repos.
  • Cost is modest once amortized: $0.074/issue vs $0.049 for the bare agent, versus $0.382 for the online SWE-Debate baseline.

Notable quotes

Rather than explicitly injecting handcrafted bugs, the framework asks an LLM to reimplement repository functionality under constrained context, encouraging the rewritten code to naturally exhibit implementation mistakes similar to those introduced during real software development.
This step ensures that the extracted skills are strictly grounded in the actual codebase structure, preventing the LLM from hallucinating non-existent interfaces during subsequent extraction.
These results indicate that the distilled project-specific knowledge is not universally transferable across LLMs.

Limitations

  • Test-coverage dependent: synthesis starts from passing tests under coverage instrumentation, so code rarely exercised by runnable tests yields few learning signals, and the method should degrade on poorly tested repositories.
  • Skills do not transfer across LLM backbones — swapping the resolver model can erase the entire improvement, so the skill store must be re-distilled whenever you change models.
  • Synthetic problem statements are LLM-generated and may differ from developer-written issue reports; skill quality was checked only by manual inspection, with no automated validator, no dedup/merge, and no mechanism for retiring skills as the repository evolves.
  • Gains are reported on one scaffold with two mid-tier models; the eval uses an LLM-localized test subset per snapshot rather than each repo's full suite, and amortizing offline synthesis over evaluated instances flatters the per-issue cost for repos with few issues.

Open questions

  • Does the skill store keep improving as more synthetic issues are generated, or does it saturate — and how do skills stay correct as the repository changes?
  • Can model-specificity be factored out — e.g. distilling repository facts separately from model-conditioned pitfall lessons — so one store can serve a heterogeneous fleet of backbones?
  • How well does this hold on repos with weak test suites, or on frontier models whose coding priors are already closer to the repo's conventions (the whole signal comes from the prior/repo mismatch)?
