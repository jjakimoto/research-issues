    Schrödinger's Code Repository: Have LLMs Learned SWE-bench or Memorized It?

    ← Go backActive Portfolio Management in Concentrated Equity MarketsNextGrowing Harness's model-size-invariant WebArena-Verified… →
    📰 Latest · 2026-09-27 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-27

    Source: huggingface-daily-papers · 2026-08-21
    Link: https://arxiv.org/abs/2609.27891

    The authors rename, reorder and rewrite SWE-bench Verified repos in ways that keep their behavior identical. That cuts Pass@1 by 6.0-14.4 points and multiplies input tokens by up to about 3.5x. On post-cutoff SWE-rebench tasks the same transforms leave Pass@1 unchanged, so public leaderboard scores likely overstate how agents do on unfamiliar or private codebases. Caveats: only small or mid-tier models, one bash-only scaffold, and a held-out control of just 110 tasks with one model.

    Executive summary

    SchrodingerRepo tests whether coding agents actually reason over a repository or recognise its familiar surface (names, file layout, code patterns). At evaluation time it builds a seeded, reversible view of each repo that behaves identically, through four levels: rewording the issue, renaming paths and symbols, reordering definitions within a file, and rewriting the code near the fix without changing what it does. On SWE-bench Verified with mini-swe-agent, the full transform lowered Pass@1 for all four models tested (GPT 5.1, GPT-5.4-mini, DeepSeek-v4-Flash, Gemini-3.1-Flash-Lite). Most of the extra actions went into exploring the repo. On temporally held-out SWE-rebench tasks, Pass@1 did not change, which suggests the drop on Verified comes from lost familiarity rather than harder tasks.

    Problem: static benchmark repos invite memorization

    Every SWE-bench issue is shown through one fixed version of a popular open-source repo, and that same version turns up in training, development and evaluation. A high score could therefore mean real repository reasoning or just memorized cues such as names and APIs. Before any transforms, the authors ran a human-judged recall probe. Experts split each problem statement into pieces, from broad to specific, and revealed them to the model one round at a time. The model saw only the instance ID plus the pieces revealed so far, with no files, gold patch or tests. After each round, experts checked whether the output contained task-specific details that had not yet been revealed.

    • Recall categories: no valid recall, file/symbol recall, repair-logic recall, and patch/test recall.
    • For every model evaluated, more than 65% of SWE-bench Verified instances showed clear leakage evidence, and more than 18% could be recalled down to the patch or test.
    • Fresh benchmarks (SWE-bench Live, SWE-rebench, SWE-bench Pro) are discussed as partial fixes that are limited in scale and in the kinds of issues they cover. Pro and Live were not themselves evaluated.

    Method: four seeded transformation levels that keep behavior identical

    SchrodingerRepo keeps a seeded, reversible mapping between the real repo and the view the agent sees. Commands still run in the real SWE-bench environment, and the final patch is rebuilt by diffing the final repo state against the original, so it can be graded normally.

    • Level 1 (problem statement reconstruction): an LLM generator rewords, reorders and trims the issue text, and a verifier LLM checks that every task-defining constraint is still there. A human reviews the result.
    • Level 2 (namespace mapping): repo-internal identifiers are taken from the syntax tree, excluding builtins, keywords and third-party names. They are split into sub-words and replaced consistently while keeping naming conventions, e.g. QuerySet becomes LedgerSuite. A two-way translator rewrites what the agent sees and what the agent runs; the physical repo is never changed.
    • Level 3 (reordering within files): definitions are reordered by a random ordering that respects a definition-time dependency graph (decorators, default arguments, annotations, base classes).
    • Level 4 (rewrite that keeps functionality): a constrained agent rewrites the code region tied to the fix into a form that behaves the same. A rewrite is kept only if tests that passed before still pass and the target bug still fails.
    • A fresh view is built for each run from a random seed. Three seeds were used per level and results averaged; human reviewers checked 100 random instances per level.

    Experimental setup

    All runs used mini-swe-agent with default settings (temperature 0, at most 250 actions per instance). To keep cost down, Levels 3 and 4 were applied only to the files and code regions touched by the golden patch.

    • SWE-bench Verified (500 instances): GPT-5.4-mini, GPT 5.1 and DeepSeek-v4-Flash on all levels. Gemini-3.1-Flash-Lite ran only the full setting, and only on the 300 instances with the strongest leakage evidence.
    • SWE-rebench March 2026 leaderboard split: 110 instances created after GPT-5.4-mini's release, run with GPT-5.4-mini only as a temporally held-out control.
    • SWE-QA: 144 repo-level question-answering instances (48 each from Conan, Reflex and Streamlink), run with GPT-5.4-mini and DeepSeek-v4-Flash.
    • Metrics: Pass@1 (SWE-QA uses its Average Score), average actions, and average input/output tokens. Agent actions were classified as navigate, search, read, probe, edit or test.

    Results: renaming hurts most, and the extra cost is exploration

    With all four levels on, Pass@1 fell for every model, and the authors report the drops as statistically significant. Level 1 (rewording only) had almost no effect. Level 2 (renaming) caused the largest single drop and the largest cost increase. Levels 3 and 4 had milder effects but still raised cost. In trajectories, more than 80% of the extra actions went to navigate, search, read or probe rather than edit or test. In a case study (django__django-11999), the original run went straight to django/db/models/fields/__init__.py by grepping for get_.*_display. In the transformed view it had to explore storage_engine/object_models/... before finding the equivalent render_%s_label logic, and in the end it submitted the same patch.

    • DeepSeek-v4-Flash explores a lot (31.4% of its extra actions were probes) and kept more of its Pass@1. GPT-5.4-mini reads and searches (41.8% read, 33.1% search, 3.7% probe) and lost more relative performance.
    • The authors describe a trade-off between exploration intensity and robustness.
    • The pattern carries over to SWE-QA, though with smaller effects. On held-out SWE-rebench, Pass@1 was unchanged while cost still went up, and the cost increase was larger for older, widely used repos.

    Significance for coding-agent leaderboards

    A score on one fixed version of a well-known repo mixes real reasoning with familiarity. The paper argues that repository representation should be treated as an explicit experimental variable, and that agents should be scored across many views that behave identically instead of one static benchmark artifact. Because a new view is generated for each run, it cannot leak into training data the way fixed perturbed benchmarks (e.g., RepoMirage) can. In practice, SWE-bench Verified numbers likely overstate both success rate and efficiency on private or unfamiliar codebases. Close rankings may also be fragile: in Table I, GPT-5.4-mini leads GPT 5.1 at baseline (46.8% vs 44.6%) but trails it under the full transform (35.6% vs 36.2%). That reversal is read off the table; the authors did not test it for significance.

    Key findings

    • Memorization probe: for every model evaluated, more than 65% of SWE-bench Verified instances showed clear leakage evidence, and more than 18% could be recalled at the patch or test level from little more than the instance ID and part of the issue.
    • The full SchrodingerRepo transform lowers SWE-bench Verified Pass@1 by 6.0-14.4 points: GPT-5.4-mini 46.8 to 35.6, GPT 5.1 44.6 to 36.2, DeepSeek-v4-Flash 72.8 to 66.8, and Gemini-3.1-Flash-Lite 56.7 to 42.3 (Gemini on the 300 highest-leakage instances only).
    • Renaming (Level 2) is the strongest single signal: Pass@1 drops 6.0-7.4 points and input tokens rise 108-218%. Rewording the issue alone (Level 1) changes Pass@1 by only 0-2.0 points.
    • Input tokens rise by up to 255.4% (GPT-5.4-mini) and 253.6% (DeepSeek-v4-Flash), and 81.6-83.6% of the extra actions go to exploration and localization rather than editing or testing.
    • On 110 SWE-rebench tasks created after the model's release, GPT-5.4-mini's Pass@1 is unchanged at 17.27% while actions rise 8.15% and input tokens 22.01%. This suggests the transforms remove familiarity rather than make the tasks harder.
    • The effect carries over to repo-level question answering: SWE-QA scores drop 0.75-4.64 points and actions rise 18.15-43.02%.

    Notable quotes

    For each evaluated model, more than 65% of instances exhibit clear data-leakage evidence, and more than 18% of instances can be recalled at the patch/test level.
    Because the underlying issue, execution environment, and test-defined correctness criteria remain unchanged, the observed degradation cannot be explained by changes in task semantics.
    This indicates a trade-off between exploration intensity and robustness: more exploratory agents are better able to recover missing repository context, while more conservative agents are more sensitive to representation shifts.
    We further observe that the increase in interaction cost is more pronounced in repositories that are widely used and long-standing, which are more likely to have been encountered during model pretraining or development.

    Limitations

    • Coverage is narrow. Only small or mid-tier models were tested (no frontier flagship), with a single bash-only scaffold (mini-swe-agent). Gemini ran only the full setting, on a 300-instance subset chosen for strong leakage, so its 14.4-point drop is biased upward. The held-out control that argues against 'harder tasks' is one model on 110 instances at a 17.27% solve rate.
    • The benchmarks are Python-only and the tooling is command-line only. Agents that use IDE, language-server or AST tools would need extra adaptation to see a consistent renamed view. Levels 3 and 4 are applied only to golden-patch-related files and regions, not to the whole repo.
    • Renaming to 'semantically plausible' names (e.g., QuerySet to LedgerSuite) removes real domain meaning as well as memorized cues. Some of the drop may therefore reflect lost legitimate priors rather than pure memorization. The motivation leakage probe relies on subjective, interactive human judgment.

    Open questions

    • Do frontier models (and scaffolds with retrieval or LSP tooling) show larger or smaller gaps? Does the drop grow with SWE-bench Verified score, which would indicate score inflation at the top of the leaderboard?
    • Should leaderboards report Pass@1 and token cost under per-run seeded views alongside canonical scores? How many seeds are needed to get stable rankings?
    • How much of the Level 2 drop comes from memorization of specific repos versus the loss of general, transferable knowledge of library conventions, which is legitimately useful on real repos?
