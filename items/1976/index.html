    AIM: Agentic Idea Management for Automated Research

    ← Go backA Missing Piece for Trustworthy AI Reviewers: From…NextSharpening Tax in Post-Training →
    📰 Latest · 2026-10-04 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-04

    Source: huggingface-daily-papers · 2026-09-29
    Link: https://arxiv.org/abs/2609.38445

    AIM gives you a research-loop design you can copy: an LLM re-clusters the whole idea pool each round, ranks clusters and ideas, and gives every parallel branch an explicit explore or exploit order. Solvers are scored by AutoLab's execution-based verifiers, and an LLM auditor throws out reward-hacked or trivial runs and rewrites an idea when the code that actually ran differs from it. The gains are modest, though: +1.6 pp and +4.9 pp over ScientistOne, from 3 seeds, often within the standard error. The authors ran no significance tests, all ablations are on Flash Attention alone, it uses 0.4-1.5x ScientistOne's tokens, and AdaEvolve beats it by 21 pp on the smooth Data-Select task.

    Executive summary

    The paper sorts automated-research agents into two kinds: solution-driven ones, which search over code (AIDE, AIRA, AdaEvolve, EvoX), and idea-driven ones, which search over research ideas and hand implementation to a solver (AI-Scientist-v2, DeepScientist, Arbor, ScientistOne). AIM is an idea-driven loop loosely modeled on Bayesian optimization. An Agentic Surrogate clusters and ranks ideas, an Agentic Acquisition step assigns explore/exploit actions to parallel solver branches and generates new ideas, a Solution Auditor checks that each idea matches its code, and a Resource Planner decides how many branches run per round. On 10 AutoLab tasks with Gemini-3.1-Pro-Preview as the backbone, AIM averages 67.0% on System Optimization and 55.8% on Model Development & CUDA, versus 65.4% and 50.9% for ScientistOne, and reaches ScientistOne's best Flash Attention score up to 3.1x faster in wall-clock time. A combinatorial argument says breadth over ideas pays off most when only a few of many plausible directions are competitive.

    Problem: idea-driven search has three unsolved sub-problems

    Solution-driven agents treat the executable artifact as the thing being searched, so verifier feedback edits code directly. Idea-driven agents keep natural-language ideas (title, hypothesis, experiment plan) as the search objects and delegate implementation. The objective is to maximise the best verifier score f(x)=v(g(x)) under a budget counted in experiment executions and/or wall-clock hours, where implementing and verifying an idea dominates the cost. The authors name three challenges for idea-driven search.

    • Idea management scaffold: keep an expanding idea pool plus evidence in a persistent, interpretable structure. Prior work uses lists (DeepScientist), trees (AI-Scientist-v2, Arbor) or beam retention (ScientistOne).
    • Idea selection: prior methods use fixed rules (UCB, MCTS) or bare LLM judgments with no explicit estimates.
    • Idea-solution integrity: a solver can write code that does not actually implement the chosen idea, so the score and the lessons drawn from it get attributed to the wrong idea.

    Architecture and loop topology

    The search state is S_t = (task context, idea pool, lesson memory, cluster map, ordinal ranks, idea-score history). The task context is the task description plus a research brief generated with Claude Code. The initial pool of about 10 ideas comes from ScientistOne's Ideator, filtered by its feasibility critic. Each iteration runs the LLM operators below; every one emits JSON or YAML that a validator checks. The run returns the highest-scoring audited solution.

    • Organize (Agentic Surrogate): the LLM re-clusters the WHOLE pool into 2-5 thematic clusters every iteration, so ideas from different lineages can merge and clusters can split or be renamed. Evaluated ideas act as landmarks.
    • Estimate (Agentic Surrogate): two stages of dense ordinal ranks, first clusters (using best and mean evaluated score and evidence count), then unevaluated ideas within each cluster. It deliberately avoids calibrated numeric reward predictions.
    • Dispatch (Agentic Acquisition): two LLM calls. Stage A gives each branch a cluster-level and an idea-level action from {explore, exploit}; the validator rejects plans that put everything on one cluster or all-exploit. Stage B picks a concrete unevaluated idea per branch. In iteration 1, every branch exploits the top-ranked ideas.
    • Solve: each branch is an independent Gemini Deep Solver (borrowed from ScientistOne) that may refine its code over several rounds, up to N_branch verifier calls. With N=300 and B_tot=25, that is 12 executions per branch.
    • Expand: lessons distilled from audited runs go into memory. Each branch then proposes at most 3 new ideas, one per mode: push_score, cross_pollinate (must cite exactly one sibling or lesson), fix_error, or new_idea (no parent, orthogonal direction).
    • Resource Planner: the total branch budget is fixed. Iteration 1 is pinned to 5 branches, later iterations use 3-10 each. The planner therefore controls how often the loop gets feedback and when it stops.

    Verifier grounding and the Solution Auditor

    Scores are grounded in execution. Each AutoLab task ships a containerized environment, a deliberately weak baseline, a local evaluation script, and a held-out verifier calibrated against a human reference that the agent never sees. The verifier checks functional correctness and task constraints first; a solution that fails them, or does not beat the baseline, scores 0. Runtime tasks score 0.5*log(t_baseline/t)/log(t_baseline/t_reference), clipped to [0,1], so matching the human reference earns 50 and beating it earns up to 100. Model-development tasks interpolate linearly between benchmark anchors: 14-20 dB PSNR for MM World Model and 0.38-0.48 IFEval strict accuracy for Data Select. On top of this sits an LLM judge, the Solution Auditor, which sees the task, the idea, the final code and the metrics, and decides which evidence enters the search state.

    • Auditor flags: reward_hacking (monkey-patching or reverse-engineering the evaluator), idea_mismatch, task_mismatch (e.g., an approximate answer where an exact one is required), and trivial (no-op, constants, or the verbatim baseline).
    • A run flagged trivial, task_mismatch or reward_hacking is dropped from both the history and lesson extraction, but its executions still count against the budget.
    • If idea_mismatch is the only flag, the auditor rewrites the idea to describe what the code actually does, and the score and lessons are credited to the rewritten idea. Figure 19 reports a large drop in idea-mismatch flags after rewriting, but that drop is measured by the same LLM auditor.
    • The 'without Auditor' ablation also ignores audit flags when computing the final score. That implies the headline scores of full AIM exclude auditor-flagged solutions, so they depend partly on an LLM judgment.

    Experimental setup, budgets and cost

    Ten AutoLab tasks: five CPU system-optimization tasks (Flash Attention in C, Radix Sort of 50M uint, a 32,768-point real FFT in Rust, AES-128-CTR on 256 MiB, Z-order range-count queries), two GPU model-development tasks (Moving-MNIST world model trained from scratch for 4 h and scored by PSNR on 10-step rollouts; picking 5,000 of 50,000 samples for LoRA fine-tuning of Qwen2.5-3B-Instruct, scored on IFEval), and three CUDA kernels (Huffman decode, Goldilocks NTT butterfly, ICP correspondence step). Every method uses Gemini-3.1-Pro-Preview. Baselines get at most 5 parallel workers, and all idea-driven methods receive the same research brief. Results are the mean and standard error of 3 runs per (method, task).

    • Budgets: System Optimization allows at most 300 executions and 6 h of wall-clock; Model Development 60 executions and 24 h; CUDA 60 executions and 12 h. A run stops when either budget is exhausted.
    • Token cost per run on Flash Attention: AIM makes 1740 LLM calls with 90.1M input and 2.25M output tokens; ScientistOne 1550 calls, 70.3M and 1.77M; AIRA-MCTS 121 calls, 0.9M input. On Data Select IFEval AIM uses 6222 calls and 631.6M input tokens, against 12784 calls and 1524.0M for ScientistOne.
    • The paper reports no dollar costs. Output-token counts include thinking tokens.
    • In 9 of 10 tasks AIM spends fewer tokens than ScientistOne to reach ScientistOne's best score, by up to 3.4x on Data Select IFEval. However, AIM usually needs MORE executions than baselines to reach its best score, because it explores widely in early iterations.

    Results, ablations and failure modes

    AIM has the best average in both task groups, but the margins are small and several tasks are lost. On Flash Attention it peaks at 90.5% after 3.3 h, while AdaEvolve reaches 85.3% at 5.5 h and ScientistOne 86.2% at 3.5 h. AIM matches every baseline's final score within roughly the first 1-2 h; the baselines need 2.2-5.5 h. All ablations are on Flash Attention only. With Claude Code swapped in as the solver, AIM matches or beats ScientistOne on all 5 system-optimization tasks: Flash Attention 84.5 vs 81.6, Z-order 52.2 vs 52.2.

    • Main ablations (Flash Attention; full system 90.5): without Agentic Surrogate 85.9 (-4.6), without Solution Auditor 87.6 (-2.9), fixed 5x5 schedule instead of the planner 88.1 (-2.4), no explicit explore/exploit actions 89.2 (-1.3).
    • Surrogate ablations: without Organize 89.0, without Estimate 87.9, direct numeric score estimation instead of ranks 89.3. Embedding K-means clustering in place of LLM clustering scored 83.4, worse than removing the surrogate entirely.
    • The cluster-level ranks have a mean Spearman correlation of 0.56-0.91 with later verifier outcomes (about 0.71 on average across five tasks). The correlation is not monotonic over iterations on AES128-CTR and FFT.
    • Failure modes: AdaEvolve wins Data Select IFEval (82.7 vs 61.8), which the authors attribute to a smooth, local-search-friendly landscape. DeepScientist (55.7) and AIRA-MCTS (54.5) beat AIM (53.5) on ICP, and Arbor beats it on AES128 (67.2 vs 66.4). Most baselines could not run the multi-file MM World Model task.
    • The planner usually chooses fewer than 5 parallel branches. Dispatch shifts from explore to exploit over iterations. Expand's output splits 35-41% cross-pollination, 29-32% new ideas and 24-31% score-guided refinement, with fix_error rare.

    Theory and why it matters for building an autonomous researcher

    Proposition 1: under faithful realization, spending N executions on N distinct ideas gives the maximum possible semantic coverage. Solution-driven search can match it, but only indirectly. Proposition 2: with K plausible directions of which G are epsilon-optimal, covering C directions finds a competitive one with probability 1 - C(K-G,C)/C(K,C), and C >= (K/G) ln(1/delta) is a sufficient condition. Idea breadth therefore pays off when K/G is large, as in Flash Attention, and matters little when the algorithm is essentially fixed, as in Radix Sort. Embedding diversity supports this: mean pairwise cosine distance on Flash Attention is 0.115 for AIM and 0.0153 for EvoX, while the gap shrinks on Radix Sort. The authors acknowledge AIM is a hybrid, since each branch also refines its own code locally.

    • Design lessons that carry over: ask the LLM for ordinal ranks rather than numeric predictions; let the LLM do clustering rather than embedding K-means; force an explicit explore/exploit statement per branch; rewrite ideas after the fact so credit goes to the mechanism that actually ran.
    • Evaluating whether to search over ideas or over code requires a real execution verifier; AIM's scores come from AutoLab's correctness-plus-speedup or quality metrics, not from an LLM rating the research.
    • The authors name as future work adapting the idea-vs-solution balance per task, using implementation difficulty and solver fidelity.

    Key findings

    • Averages: AIM 67.0% on System Optimization vs 65.4% for ScientistOne and 63.3% for AdaEvolve. On Model Development & CUDA, AIM 55.8% vs ScientistOne 50.9% (5-task averages). The largest single-task gain is Flash Attention: 90.5 vs 86.2 for ScientistOne.
    • Wall-clock: AIM reaches its Flash Attention best of 90.5% at 3.3 h, against 85.3% at 5.5 h for AdaEvolve and 86.2% at 3.5 h for ScientistOne. It reaches ScientistOne's best up to 3.1x faster. Counted in executions instead, AIM tends to need MORE to reach its best.
    • Ablations (Flash Attention only): removing the Agentic Surrogate costs 4.6 pp, the Auditor 2.9 pp, the dynamic planner 2.4 pp, explicit explore/exploit 1.3 pp. Embedding K-means clustering (83.4) does worse than no surrogate at all (85.9).
    • Ordinal cluster ranks correlate with later verifier outcomes at a mean Spearman of about 0.71 (range 0.56-0.91). Direct numeric score prediction (89.3) underperforms ordinal ranking (90.5).
    • The gain survives a solver swap: with Claude Code as solver, AIM matches or beats ScientistOne on all 5 system-optimization tasks (e.g., Flash Attention 84.5 vs 81.6). Margins are small elsewhere, e.g., Radix Sort 67.7 vs 67.4.
    • Cost: about 1,600-6,200 LLM calls and 70-630M input tokens per run, roughly 0.4-1.5x ScientistOne and two to three orders of magnitude more than AIRA. AIM loses Data Select IFEval to AdaEvolve (61.8 vs 82.7) and ICP to DeepScientist (53.5 vs 55.7).

    Notable quotes

    The Auditor checks whether the implementation follows the intended idea, satisfies the task requirements, and obtains its score without exploiting the verifier.
    Thus, subsequent search decisions are grounded in the mechanism actually evaluated rather than the initially misaligned one.
    This indicates that language models are generally more reliable at performing relative, ordinal comparisons of research ideas than they are at predicting absolute, uncalibrated performance scores from raw text.
    Overall, our approach tends to require more executions to reach its best score.

    Limitations

    • The statistical evidence is thin: 3 runs per cell, standard errors only, and no significance tests. Many system-optimization margins are inside one SE (e.g., Radix Sort 69.5 +/- 2.3 vs 68.7 +/- 1.6), and every ablation and surrogate study uses only Flash Attention.
    • The Solution Auditor is an unvalidated LLM judge: no precision or recall against human audits is reported. Its flags also filter the final reported scores, and the drop in idea mismatches after rewriting is measured by the same auditor.
    • The setup is tied to one stack: a Gemini-3.1-Pro-Preview backbone, ScientistOne's Ideator and Gemini Deep Solver, and a research brief generated with Claude Code. Cost is heavy (hundreds of millions of input tokens per long-horizon run, with no dollar figures). The theory assumes faithful realization and exchangeable competitive directions, assumptions the authors themselves call idealized.

    Open questions

    • How accurate is the LLM Solution Auditor at catching reward hacking and task mismatch, and how often does it falsely reject legitimate fast solutions?
    • Could a system estimate a task's effective semantic breadth (K/G) online and use it to shift budget between idea-level exploration and code-level refinement, as the authors propose?
    • Does the advantage hold under matched token budgets, and does it transfer to research tasks without an execution verifier (e.g., literature or finance research judged by an LLM)?
