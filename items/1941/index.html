    Mid-Harness: Scaling Actions Between Model and Harness for Terminal Agents

    ← Go backGroundability, Not Scale Alone: When Weak Reviewers Can…NextEverMine: Dissecting the Self-Evolution of Research… →
    📰 Latest · 2026-10-02
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-02

    Source: huggingface-daily-papers · 2026-09-30
    Link: https://arxiv.org/abs/2609.39982

    A drop-in model-call wrapper that samples N candidate shell actions per step and lets a verifier pick one before execution lifts a 9B terminal agent from 50.0% to 57.1% Pass@1 (68.0% with a GPT-5.6 Sol verifier) without touching the generator or the harness. Stacked on Best-of-3 trajectories it reaches 66.3%, beating Best-of-7 at lower token cost. For anyone building coding agents, it puts per-action verification on the table as a separate test-time compute knob, distinct from scaling whole trajectories.

    Executive summary

    Mid-Harness puts a sampling-plus-verification layer inside the agent's model-call wrapper. At each step it draws N candidate actions from the same history, a verifier (listwise, pointwise, or pairwise) picks one, and only that action goes to the unchanged harness for execution. With a TMAX-9B generator on TerminalBench-Lite (98 tasks, 3 runs each), sampling more candidates helps little when verification is weak. Pairwise self-verification is the best zero-shot mechanism (54.76% Pass@1 vs 50.00% base), and LoRA-distilling GPT-5.6 Sol's pairwise judgments into the verifier raises this to 57.14%. Composed with trajectory-level scaling, it beats spending the same budget on more trajectories alone, and the gains carry over to 4B-550B models, Terminal-Bench 2.1, SWE-bench Verified Mini, FeatureBench-Mini, and the Terminus-2 harness.

    Problem: one bad command poisons the rest of the trajectory

    A terminal agent commits to a long sequence of stochastically sampled actions, and each executed command changes the environment that later decisions depend on. A wrong package install or a bad code edit can derail a run even when the same model could have produced a better command. The paper asks when test-time compute spent before an action executes (at the model-harness boundary) improves trajectory success, and what makes that compute effective. Without gold per-action labels, candidate quality is measured indirectly through end-to-end task success.

    • 'Action reliability' means consistently generating actions that support task completion; it is evaluated through trajectory-level success.
    • This complements trajectory-level scaling (Best-of-T, Sequential Refine), which needs fresh environment runs. Mid-Harness needs only one environment instance.
    • Two requirements are studied jointly: does the generator propose useful alternatives (coverage), and can verification find them before execution?

    Method: the 'mid-harness' layer is a wrapper around model.generate

    The harness loop stays the same (generate, parse, execute, update messages). Only the model-call wrapper changes: generate(messages) becomes 'sample N candidates with the same messages, then return verify(llm, messages, candidates)'. The verifier sees the task, the observed history and terminal state, and the candidate actions, but not the generator's <think> reasoning. It always returns one of the proposed candidates. The other candidates are discarded, and the next step samples a fresh set from the updated history. No model weights or serving architecture change.

    • Listwise: one call sees all N candidates and returns a letter. Cheapest, but the verifier has to separate every candidate in a single response.
    • Pointwise: N independent 0-10 scores, then argmax (like a process reward model). Parallel, but actions with different purposes end up on a single absolute scale.
    • Pairwise (default): the verifier compares two candidates and returns a rationale, two 1-10 scores, and an A/B/TIE preference. Results are aggregated with margin-weighted win rates (weight = max(|sA-sB|/9, 0.1)).
    • At N=8 the pairwise mechanism runs a ring followed by a 4-pivot tournament (22-25 comparisons instead of 28 for all pairs). At N=4 it runs all 6 pairs. Candidates that fail to parse are dropped and identical tool calls are deduplicated.
    • Decision-only variant: the verifier emits a single A/B token, and candidates are scored by the mean of the softmaxed A/B log-probs.

    Setup: models, harness, benchmarks, distillation

    The main generator is TMAX-9B (Qwen3.5-9B trained with RL on synthetic terminal tasks), run in the Vanillux2 harness. Scale experiments use TMAX-4B and TMAX-27B. The generator samples at temperature 0.8 with up to 64 steps, a 65,536-token context, and a 16,384-token output limit per step. The verifier is the same model with thinking off and temperature 0 (61,440-token context, 2,048-token output). The frontier reference verifier is GPT-5.6 Sol, used listwise because of cost. The distilled verifier is a LoRA adapter (rank 64, alpha 128, lr 1e-4, 2 epochs, 4x H200) trained on 117,631 GPT-5.6 Sol pairwise responses (rationale, scores, preference) collected from 732 TMAX-9B trajectories over 244 hard TMAX-15k tasks, with A/B balancing. The adapter is active only for verifier calls.

    • Benchmarks: TerminalBench-Lite (98 of 100 tasks), Terminal-Bench 2.1 (all 89), SWE-bench Verified Mini (50), FeatureBench-Mini (23 CPU-only tasks).
    • Metrics: 3 runs per task. Pass@1 is the mean exact success across runs; Pass@3 counts a task solved if any run succeeds.
    • Trajectory baselines: Best-of-T with a probabilistic pivot tournament (TMAX as trajectory verifier) and Sequential Refine (SR) with R rounds, where each round runs fresh from a summary of the previous run.
    • Cost proxies: parallelized output tokens (POT) for latency, total verifier output tokens, and reference-priced dollars at OpenRouter Qwen3.5-9B rates ($0.08/$0.13 per M input/output tokens).

    Results: verification quality, not candidate width, is the bottleneck

    A frontier verifier shows that the 9B generator's own samples contain much better actions than it executes by default: 64.63% Pass@1 at N=4 and 68.03% at N=8, against 50.00% for the base agent. Self-verification recovers only part of this gap. Under zero-shot listwise verification, going from N=4 to N=8 moves Pass@1 only from 49.32% to 51.02%. A 'first-runnable' control with no verifier scores 49.66%. Pairwise verification is the best zero-shot mechanism, and distillation narrows the gap further. Pairwise verification is costly: at N=8 it adds about 26.6k POT versus at most 1.3k for listwise or pointwise, and 125.7k total verifier output tokens per run versus 0.6k (listwise) and 7.0k (pointwise). Decision-only verification cuts reference-priced cost by 20.9-24.1% on 9B while slightly raising Pass@1, but it lowers Pass@1 at 4B and 27B.

    • Distillation offline (21 held-out tasks): score MAE drops from 2.59 to 1.05, pairwise agreement with the teacher rises from 59.01% to 74.58%, and top-candidate agreement rises from 38.52% to 57.79%.
    • Clear verifier failures judged by GPT-5.6 Terra fall from 3,328 to 1,810. 67.4% of the remaining distilled failures are 'candidate semantics' or 'execution feasibility' errors, i.e. misjudging what a command will actually do in this environment.
    • Agreement with the teacher is highest early in the trajectory (68.13% at turns 1-4) and lower later (54.07% at turns 17-32).
    • Spending more verifier compute does not reliably help. Five responses per pair drops Pass@1 from 57.14% to 53.40% at 4.99x the verifier output. Enabling thinking gives 54.76% to 56.12% at 4.86x. Rubric scaling gives 54.76% to 55.10% at 2.26x.

    Composition with trajectory scaling and transfer

    Mid-Harness is complementary to scaling whole trajectories. With TMAX-9B, Best-of-3 trajectories reaches 55.10%. Generating those 3 runs with zero-shot or distilled Mid-Harness raises this to 61.22% or 66.33%, with the same number of environment executions. Distilled Mid-Harness alone (57.14%) matches Best-of-5 at about one-third of its reference-priced cost. Mid-Harness + SR (60.20%) and Mid-Harness + Best-of-3 (66.33%) both beat Best-of-7 (59.18%) at lower estimated cost, while SR alone plateaus around 55-56%. Gains hold across model scales (4B, 27B), another harness (Terminus-2 with Qwen3.5-9B and Nemotron3.5 Lightning), and harder benchmarks.

    • Across all seven transfer settings, zero-shot Mid-Harness improves Pass@3 and matches or improves Pass@1.
    • In bootstrap 95% CIs over 98 paired tasks, only distilled 9B (+7.14 pp, [+1.36, +12.93]) and distilled 27B (+5.10 pp, [+0.34, +9.86]) exclude zero. The other four comparisons have positive point estimates but CIs that include zero.
    • On Hard-difficulty tasks, distilled Mid-Harness gains 2.3 / 6.9 / 10.3 pp at 4B / 9B / 27B. On software-engineering tasks the gains are 2.6 / 5.1 / 20.5 pp. Scientific-computing Pass@1 falls 10.0 pp at 27B.

    Key findings

    • Coverage is there; verification is the bottleneck. A GPT-5.6 Sol verifier choosing among TMAX-9B's own 8 samples raises Pass@1 from 50.00% to 68.03%, while zero-shot listwise self-verification moves only from 49.32% (N=4) to 51.02% (N=8).
    • Pairwise comparison is the best zero-shot mechanism (54.76% Pass@1 / 71.43% Pass@3 at N=8). LoRA-distilling 117k GPT-5.6 Sol pairwise judgments into the 9B verifier raises this to 57.14% / 75.51% without changing the generator.
    • Combining scaling axes is more cost-efficient. Distilled Mid-Harness + Best-of-3 reaches 66.33% Pass@1 (vs 55.10% for Best-of-3 alone, +11.23 pp with the same 3 environment runs), and Mid-Harness + one SR round reaches 60.20%; both beat Best-of-7 (59.18%) at lower reference-priced cost.
    • Pairwise verification is expensive: about 125.7k total verifier output tokens per run at N=8 versus 0.6k for listwise. Decision-only one-token verifiers cut end-to-end cost by 20.9-24.1% at 9B with slightly higher Pass@1, but lose 1.4-3.4 pp Pass@1 at 4B and 27B.
    • The gains transfer to Terminal-Bench 2.1 (TMAX-9B 21.72% to 27.34%; Nemotron3 Ultra 550B 50.94% to 56.18%), SWE-bench Verified Mini (46.67% to 48.67%), and FeatureBench-Mini (TMAX-27B 17.39% to 23.19%), and to the Terminus-2 harness.
    • 67.4% of the remaining distilled-verifier failures are about command semantics or execution feasibility, i.e. predicting what a command will do in the current environment. Agreement with the teacher falls from 68.13% at turns 1-4 to 54.07% at turns 17-32.

    Notable quotes

    Together, these results identify verifying what an action will do in the current environment without executing it as a central challenge in converting candidate diversity into successful trajectories.
    This contrast suggests that the weaker zero-shot verifier struggles to distinguish useful actions when comparing the full candidate set at once, so additional candidates alone offer little benefit.
    Thus, combining action and trajectory scaling can achieve higher success at lower estimated token cost than increasing trajectory count alone.
    Action verification should complement these safeguards, not replace them.

    Limitations

    • There are no gold per-action labels, so verification correctness and candidate coverage are inferred only from end-to-end success. Comparing verifiers requires new online environment runs, not re-scoring a fixed trajectory set.
    • Statistical power is limited: 3 runs per task on 98 tasks. Only 2 of 6 Pass@1 improvements over the base agent (distilled 9B and 27B) have bootstrap 95% CIs that exclude zero, and some domains regress (scientific computing -10.0 pp at 27B).
    • Distillation leaves a large gap to frontier verification (57.14% vs 68.03%). Sampling and verifying at every step is costly, and the paper does not compare action scaling against simply giving one candidate more reasoning budget at equal cost. All dollar costs are reference-priced proxies for locally served models.

    Open questions

    • Can adaptive verification (varying N and comparison effort per step, e.g. only at high-uncertainty or late-trajectory steps) keep the gains at a fraction of the pairwise cost?
    • Would a world model that predicts command effects, or RL-trained verifiers co-adapted with the generator (as in V1), close the semantics/feasibility gap that supervised distillation leaves?
    • How does per-action verification compare with spending the same compute on longer generator reasoning or on a larger generator, and do the two compose?
