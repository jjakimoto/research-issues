    When Sub-Agents Work in Parallel: The Promises and Pitfalls of Dynamic Concurrency in Long-Horizon Coding Tasks

    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-08

    Source: arxiv · 2026-10-07
    Link: https://arxiv.org/abs/2610.10263

    Across 2,124 paired runs of Codex, Claude Code and Kimi Code, letting the main agent spawn concurrent sub-agents on its own helped only on the longest tasks (Claude Code +14.3 pts task pass on LoopsBench) and hurt on bounded SWE-bench fixes (Claude Code -24 pts). It cost 1.41-3.31x the tokens and was slower in 14 of 15 agent-benchmark cells. If you orchestrate sub-agents, enable fan-out selectively: give each agent an isolated workspace, set joins that fit the time budget, and keep the main agent monitoring, because the top failures were fan-out using up the budget, sub-agents killed before the join, and overwritten shared files.

    Executive summary

    This is the first controlled study of native dynamic concurrency, where the main agent decides at run time whether, when and how to spawn sub-agents. It covers Codex (multi_agent v2, GPT-5.4), Claude Code (Dynamic Workflow, Claude Opus 5) and Kimi Code (AgentSwarm, Kimi K3), each run with concurrency on and off on 354 tasks from five benchmarks: 2,124 executions, 11.2B tokens, $20,780.02. Concurrency does not reliably raise success: task-resolution effects range from -11.9 to +2.3 percentage points, and token use rises 1.41-3.31x. Gains cluster on the longest-horizon tasks, and bounded SWE-bench Verified tasks see no gain or a loss. Manual annotation of all 1,062 concurrent trajectories produced a taxonomy of 4 categories, 13 subcategories and 28 failure patterns. Shared-state/merge conflicts are the largest category, and concurrency pays off through complementary work, alternative attempts with selection, and independent validation.

    Problem: static workflows vs. dynamic concurrency

    Earlier multi-agent coding systems (ChatDev, MetaGPT, CodeR, TRAE, OpenHands) fix the sub-agents' roles, number, communication and sync points in advance. Frontier agents now let the main agent build an execution plan mid-run, spawn sub-agents on demand, then reconcile shared files and verify the integrated artifact. Existing evaluations target bounded tasks like SWE-bench (patches of a few dozen lines), while dynamic concurrency is aimed at long-horizon work that produces tens of thousands of lines.

    • Claude Code: the main agent writes a workflow script with parallel stages, explicit dependencies and joins (activated via 'ultracode').
    • Kimi Code: launches a batch of sub-agents from a shared template, waits for the whole batch, and returns one ordered report.
    • Codex: direct and nested delegation; the main agent keeps working and exchanges messages with sub-agents.
    • Motivating seqtk example (Kimi, ProgramBench): 22 subcommands go to 20 sub-agents at minute 17.5 of a 40-minute run. The main agent assumes a 2-hour sub-agent timeout, never reaches integration, 18 sub-agents are aborted at the deadline, and the program passes 92 of 440 tests.

    Study design

    Each agent runs with its native scaffold, native model and highest reasoning effort, in a concurrent mode (default native settings) and a sequential mode that guarantees no sub-agents are created. Backbone model, prompt, environment and time budget are held fixed. Tasks were drawn by stratified random sampling within each benchmark's own easy/medium/hard tiers: 25% of each long-horizon benchmark and 20% of SWE-bench Verified.

    • Long-horizon: RepoZero (Py2JS 100 tasks, C2Rust 50), NL2Repo (26), ProgramBench (50), LoopsBench (28). Short-horizon comparison: SWE-bench Verified (100).
    • 354 tasks (104 easy / 161 medium / 89 hard) x 3 agents x 2 modes = 2,124 cells.
    • Reference/gold change sizes span 0.8-54.4K lines across difficulty groups. LoopsBench is the largest, and a single full LoopsBench run would cost $11,354.
    • Sequential-mode switches: Codex disables multi_agent and multi_agent_v2. Claude Code disables the Workflow, Task and Agent tools. Kimi Code sets swarm_mode=false.
    • Failure analysis: all 1,062 concurrent trajectories were reviewed against the paired sequential run. A codebook came from a 50-trajectory pilot, each case was double-annotated (Cohen's kappa = 0.77), and a senior author adjudicated.

    Effectiveness, cost and wall-clock (RQ1)

    Gains are uneven. On LoopsBench, concurrency raises task pass for Codex (21.4 to 25.0) and Claude Code (7.1 to 21.4), and test pass improves for all three agents (up to +6.0 pts). On SWE-bench Verified, Codex is unchanged at 71.0, while Claude Code (83.0 to 59.0) and Kimi Code (77.0 to 59.0) drop. Pooled exact McNemar tests with Holm correction find the overall declines for Claude Code (p=5.08e-7) and Kimi Code (p=0.0132) significant, and Codex's gain (p=0.229) not significant. Averaged over agents, the concurrent-minus-sequential test-pass gap grows with implementation size: -8.29 (RepoZero), -0.04 (NL2Repo), +1.24 (ProgramBench), +4.31 (LoopsBench).

    • Token use is 1.41-3.31x sequential, and shell calls often rise several-fold (Claude Code on LoopsBench: 791.6 vs 107.4).
    • Codex needs 24.12M tokens per solved task with concurrency vs 7.69M sequentially.
    • Mean runtime rises in 14 of 15 agent-benchmark cells. Claude Code on SWE-bench Verified takes 27.8 vs 17.5 min while solving fewer tasks.
    • Of 366 tasks solved in both modes, concurrency was faster on 102 (27.9%) and at least 20% faster on 46 (12.6%).
    • Concurrency still yields unique solves: Claude Code solves 4 LoopsBench tasks only with concurrency (0 only sequentially). On SWE-bench Verified, Codex uniquely solves 9 tasks in each mode.

    How agents delegate over time (RQ2)

    Harder tasks draw more delegation. Pooled mean sub-agents created: 6.69 (easy), 7.53 (medium), 15.84 (hard). Mean peak concurrent sub-agents: 3.66, 4.61, 6.70. The agents differ sharply in style: Codex keeps small groups and part of the implementation itself, Claude Code creates successive workflow waves, and Kimi Code launches big batches.

    • Hard LoopsBench: Claude Code creates 133.69 sub-agents per task (peak 25.46). Kimi Code creates 67.00 (peak 37.46). Codex's mean peaks range from 1.21 to 3.00 across task groups.
    • LoopsBench is 14.6% of hard tasks but 62.9% of all sub-agents created on hard tasks.
    • Median first sub-agent start: 4.0% of the trace (Codex), 22.1% (Claude Code), 26.0% (Kimi Code).
    • Median overlap fraction (at least 2 sub-agents active): 23.9% Codex, 52.7% Claude Code, 15.6% Kimi Code. In 24.3% of Codex executions, sub-agents are created but never overlap.
    • Median last sub-agent endpoint: 83.3% of the trace (Codex), 100.0% (Claude Code, with late review stages), 93.6% (Kimi Code, waiting on the batch).

    Taxonomy of concurrency failures (RQ3)

    650 of the 1,062 concurrent trajectories show at least one concurrency failure, with 804 pattern instances in total. Shared State and Merge problems (267, 33.2%) behave like data races. They are followed by Execution Governance (233, 29.0%), Task Orchestration (229, 28.5%) and Global Context Management (75, 9.3%).

    • Most frequent patterns: Fan-out Budget Exhaustion 154 (19.2%), Early Sub-Agent Termination 128 (15.9%), Deliverable Overwrite 120 (14.9%), Artifact Leakage 54 (6.7%), Same-File Collision 42 (5.2%), No Failure Takeover 42 (5.2%), Serial Investigation 40 (5.0%).
    • Load Imbalance is 39.8% of Claude Code's failure instances. Concurrent Writes are 62.9% of Codex's.
    • Pseudo-concurrency: in tailspin (Kimi), 17 sub-agents investigate but none implements, and the run passes 0 of 785 tests.
    • No active monitoring: in hopscotch-map (Claude Code), the artifact already passed all 39 tests, but a 10-minute blocking wait on a sub-agent ran out the deadline before a final response.
    • Overloaded handoff: an 80K-character brief aggregating up to 60 findings per probe made the receiving sub-agent redo investigation. Unchanged retry: a stalled sub-agent was relaunched 4 times with the same brief.
    • Environment contamination: two sub-agents delete and recreate the same /tmp fixture, and one sub-agent replaces the shared system Git executable.

    When concurrency helps, and implications (RQ4 + discussion)

    In 131 paired trajectories where concurrency won, the gain always came from the main agent actually using the parallel work. The paper's practitioner advice is to enable concurrency selectively rather than by default: mainly for hard, long-horizon tasks that decompose into independent parts, support parallel attempts, or benefit from independent validation, and to weigh that against token and time budgets.

    • Complementary work: in justext (Kimi), 8 sub-agents handle delivery files while the main agent writes the core algorithm. Wall time drops from 734.116 to 467.997 s, with both modes passing all tests.
    • Alternative attempts: in Halite (Codex), the main agent merges a sub-agent's map behavior with its own protocol handling and passes 292/391 tests, vs 0/391 sequentially. In unidecode, it picks the 1.4.0 tables over 1.3.8.
    • Independent validation: in a LoopsBench security lab (Codex), a crypto sub-agent finds the P-256 curve-order requirement for ECDSA nonce reuse, and the concurrent run passes all checks where sequential fails.
    • Research agenda: decomposition, ownership and load balancing; runtime monitoring and takeover of stalled sub-agents; carrying interface contracts and progress across contexts; isolation, synchronization and conflict detection for shared files and environments.

    Key findings

    • Concurrency changes end-to-end task resolution by between -11.9 and +2.3 percentage points per agent, while mean token use rises to 1.41-3.31x sequential.
    • Claude Code's task pass falls 24.0 pts on SWE-bench Verified (83.0 to 59.0) but rises 14.3 pts on LoopsBench (7.1 to 21.4). The pooled declines for Claude Code (p=5.08e-7) and Kimi Code (p=0.0132) are significant, and Codex's small gain (p=0.229) is not.
    • The concurrency advantage in test pass grows with implementation size: -8.29 (RepoZero), -0.04 (NL2Repo), +1.24 (ProgramBench), +4.31 (LoopsBench), averaged across agents.
    • Parallelism rarely saves time: runtime rises in 14 of 15 agent-benchmark cells. Of 366 tasks solved in both modes, only 102 (27.9%) finish faster with concurrency and 46 (12.6%) at least 20% faster.
    • Codex spends 24.12M tokens per solved task with concurrency vs 7.69M sequentially.
    • 650 of 1,062 concurrent trajectories contain concurrency failures (804 instances). Shared state/merge (33.2%) is the largest category, and the top patterns are Fan-out Budget Exhaustion (19.2%), Early Sub-Agent Termination (15.9%) and Deliverable Overwrite (14.9%).

    Notable quotes

    Even Codex, the agent showing a small overall gain in resolved tasks, consumes 24.12 million recorded tokens per solved task under concurrency, compared with 7.69 million under sequential execution.
    Of the 366 cases solved in both modes, concurrent execution finishes faster in 102 cases (27.9%).
    Thus, the parallelism introduced by dynamic concurrency does not automatically translate into lower end-to-end latency.
    Our findings provide practical guidance for practitioners on when to use dynamic concurrency: it should be enabled selectively rather than by default.

    Limitations

    • Each task/agent/mode cell was run once, since long-horizon runs are expensive. The authors argue run-to-run randomness is unlikely to change the trends, citing agreement with the original LoopsBench results, but per-benchmark differences of a few tasks (e.g., Codex RepoZero 40.0 vs 40.7%) are within noise.
    • Results are scoped to three agent-model pairs selected in July 2026 (GPT-5.4, Claude Opus 5, Kimi K3) with native default concurrency settings, five benchmarks and fixed time budgets. Batch waits and long workflows are penalized by short deadlines (e.g., the 40-minute seqtk run), so different budgets could shift the balance.
    • ProgramBench has 0% task pass for every agent in both modes, so that benchmark only offers partial-progress (test pass) signal. The failure taxonomy relies on manual annotation (kappa = 0.77).

    Open questions

    • Can the main agent learn a selective-concurrency policy that predicts from task structure and remaining budget when fan-out will pay off, avoiding Fan-out Budget Exhaustion and Early Sub-Agent Termination?
    • How much of the 33.2% shared-state/merge failure share would disappear with enforced per-sub-agent workspace isolation (e.g., worktrees) and explicit interface contracts?
    • Would budget-aware joins and active main-agent monitoring (taking over stalled work, finalizing completed artifacts) recover the runtime and token overhead seen in 14 of 15 settings?
