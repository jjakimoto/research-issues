FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution

📰 Latest · 2026-08-24 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-24

Source: huggingface-daily-papers · 2026-08-17
Link: https://arxiv.org/abs/2608.16157

FreeToken shows the bottleneck for running frontier open-weight MoE models locally is not GPU capacity but how the serving stack orchestrates PCIe, host DRAM and CPU cores: by splitting each decode step's expert cache misses between PCIe cache-fill and in-place CPU execution using a closed-form ratio q* = m*B_P/B_H derived from two measured bandwidths, it gets 1.3-2.3x the decode throughput of llama.cpp/Ollama/KTransformers on the same hardware and weights - a 35B MoE at 39.3 tok/s on an 8 GB RTX 4060 laptop, 284B DeepSeek-V4-Flash interactive on a 32 GB RTX 5090, and 753B GLM-5.2 at 14.9 tok/s on one RTX PRO 6000, with routed computation kept exact.

Executive summary

FreeToken is an edge-native MoE serving system that treats a personal machine (GPU + CPU + host DRAM + PCIe) as one elastic inference platform instead of a small GPU with an offload bolted on. Its core mechanism is bandwidth-adaptive execution: at each decode step the unique missing experts m are split into a cache-fill set F of size q* (transferred over PCIe, executed on GPU, left resident) and a CPU-execution set C (run in place from the host-resident pool), with q* = m*B_P/B_H derived from the measured PCIe expert-transfer bandwidth B_P and the measured host-side expert-kernel bandwidth B_H. Around that sit full-layer double-buffered prefill, semantic anchors for recurrent-state reuse across agent context edits, a global LRU expert cache shared by all MoE layers, and an elastic KV/expert VRAM split rebuildable at runtime. On six machines, three models (Qwen3.6-35B-A3B, DeepSeek-V4-Flash 284B-A13B, GLM-5.2 753B-A40B) and four real agentic workloads it beats llama.cpp, Ollama, KTransformers and MoE-Infinity by 1.3-2.3x on decode while keeping the routed computation numerically exact.

The problem: prefill goes dense, decode goes miss-bound, and edge hardware is never dedicated

The paper frames edge MoE serving as three coupled failures of existing engines. Prefill destroys MoE sparsity because thousands of tokens per layer activate nearly the whole expert set, so a prefill pass streams almost the entire pool across PCIe; an FP4 DeepSeek-V4-Flash deployment moves roughly 140 GB of expert weights, adding about 2 s on an RTX 5090 (PCIe 5.0 x16, ~60 GB/s), ~5 s on 4090/3090-class desktops (PCIe 4.0 x16, ~25 GB/s), and 10 s or more on the x8 links common in laptops. Decode is the opposite regime: only a sparse subset is routed per token, but static placement (llama.cpp assigns MoE tensors at load; KTransformers pins a hot subset and runs the rest on CPU) captures only a fraction of routed traffic, and a CPU-only path is capped by ~50 GB/s dual-channel DDR4 or 80-90 GB/s DDR5 against the 1-1.8 TB/s an RTX 4090/5090 draws from on-package memory. Third, none of it is dedicated - the desktop compositor, browsers and games take VRAM mid-session, and KV demand grows across agent turns while the expert working set stays roughly fixed.

  • Agentic re-prefill: hybrid-attention/recurrent models (gated DeltaNet in Qwen3.6-35B-A3B, Kimi Delta Attention in Kimi-K3) compress the prefix into one state, so a context edit after a checkpoint invalidates it and forces re-prefill of thousands of tokens - and an RTX 5090 delivers roughly a fifth of an H100's and a tenth of a B200's dense BF16 throughput.
  • The right miss split is hardware-specific: transfer-only leaves residual host bandwidth and cores idle, CPU-only leaves the PCIe link idle and forfeits future cache hits; an RTX 4060 laptop on LPDDR5 and an RTX 5090 desktop on DDR5 sit at opposite ends of the balance, and the optimum cannot be read off spec sheets.
  • Startup cost recurs on edge machines: reading the ~140 GB FP4 DeepSeek-V4-Flash pool from a 7 GB/s NVMe takes about 20 s before any warmup.

Design: two-level expert hierarchy, pipelined prefill, semantic anchors

The CPU-resident expert pool holds the complete routed-expert weights and is the source of truth; non-expert weights stay GPU-resident. Remaining VRAM becomes a single elastic expert cache shared by all MoE layers, each slot holding every tensor needed to evaluate one layer-expert pair, so residency, lookup and execution operate on logical (layer, expert) identifiers. Because the host pool is authoritative, GPU memory affects only performance, never correctness. Prefill does not fetch on demand: two full-layer buffers are drawn from the same global slot pool, the GPU computes layer l from one while a dedicated transfer stream loads all of layer l+1 into the other - loading the full layer lets transfer begin before that layer's routing is known. Sharing the decode cache's slot pool means no separate prefill cache and no phase handoff. If the pool cannot spare two full layers, FreeToken falls back to on-demand prefill loading rather than oversubscribing VRAM.

  • Semantic anchors: recurrent-state checkpoints are placed at special-token boundaries (thinking segments, tool calls, tool outputs, conversation turns) because that is exactly where harnesses edit - OpenClaw strips thinking blocks from every assistant turn but the latest, OpenCode replaces tool outputs beyond a recent window with a placeholder, SWE-agent elides all but the last few observations.
  • Full-attention KV uses a radix prefix tree (as in SGLang); a new request restores from the deepest checkpoint whose position survives the edit, so only the genuinely new suffix is re-prefilled. Checkpoint slots use LRU eviction independent of the KV pool.
  • Elastic memory: at any scheduler safe point the KV/expert split can be rebuilt for a revised VRAM budget without restarting the engine or reloading the host expert pool.
  • Fast bootstrap: weights are read from disk directly into their final host bank layout and pinned only afterward; there is no warmup phase - the first request runs cold through the ordinary decode path.

The q* policy: turning bandwidth balance into a scheduling decision

At each MoE layer during decode, routing and cache lookup run on the GPU; resident experts H execute on GPU directly. The m unique misses M are split into a cache-fill set F (size q, transferred into slots, executed on GPU, left resident for reuse) and a CPU-execution set C (executed in place from the host pool, residency unchanged). Since expert DMA and CPU expert kernels read the same host-memory subsystem, a saturated PCIe link leaves residual host bandwidth B_R = B_H - B_P; balancing T_fill = q*S/B_P against T_cpu = (m-q)*S/(B_H - B_P), where S is the byte size of one complete expert, gives q* ~ m*B_P/B_H. The exposed layer latency is the slower of the two concurrent branches, which is exactly what the equation balances. The formulation self-degenerates: as B_H approaches B_P, q* approaches m and the system becomes pure on-demand cache fill with no separate policy. At least one fill is always retained so the cache keeps warming even when the CPU handles most misses. Residency is a shared global LRU that follows router choices step by step rather than a workload-agnostic load-time placement.

  • B_P and B_H are empirically profiled on the target hardware at deployment, measured on the deployed tensor shapes rather than taken from spec sheets.
  • CPU and GPU partial sums are merged, preserving the exact MoE output without algorithmic approximation - unlike HOBBIT (reduced-precision replicas) or SiDA/SMoE (substituting or skipping low-scoring experts).
  • Execution order: launch the CPU branch first, then the GPU miss path (cache update, batch copy of F, grouped evaluation of G = H union F), with CPU workers processing C concurrently.

Implementation: all routing-dependent control inside a captured CUDA Graph

A host-controlled cache would reintroduce a device synchronization at every MoE layer, so FreeToken keeps all routing-dependent control on the GPU, expressed as data (fixed-shape work buffers and device-resident valid counts) inside a statically captured graph. One kernel per MoE layer deduplicates routed experts, classifies them against the residency table, derives the bandwidth-based fetch count q, selects eviction victims, and rewrites logical expert IDs into physical slot IDs or a special CPU-assignment flag. A single-pass kernel identifies the K least-recently-used candidate slots at once. The CPU branch is captured into the same graph: for each supported decode batch size, stable pinned I/O buffers and persistent task descriptors are prepared, and the D2H copies, a host-function submit node, the concurrent GPU path, a sync node and the H2D result copy are captured together, so replay re-executes the whole heterogeneous step with no per-token Python scheduling.

  • CPU workers are a persistent C++ pool pinned to physical cores, using architecture-specific SIMD with in-kernel dequantization to stay bandwidth-bound, returning gate-weighted per-token partial outputs.
  • Model checkpoints are normalized into expert banks keyed on a flattened layer-expert identifier; the FreeToken Weight (FTW) format pre-merges weights into that runtime layout so launch skips tensor discovery and repacking.
  • The paper notes existing hybrid engines cannot do this: KTransformers-style host-side heuristics carry scheduling cost and per-layer synchronization that cannot be captured into a CUDA Graph, and llama.cpp cannot maintain graph execution in hybrid mode.

Evaluation: six machines, three models, four real agentic workloads

Baselines are llama.cpp, Ollama, KTransformers and MoE-Infinity, with bit-exactly aligned weight formats (Qwen3.6-35B-A3B in BF16 everywhere; DeepSeek-V4-Flash's native MXFP4 expert blocks consumed bit-exactly; the 8 GB laptop uses the official NVFP4 Qwen3.6 release; GLM-5.2 is a 433 GB NVFP4 checkpoint). Workloads: W1 AIME math reasoning (single-turn, decode-dominated); W2 a SWE-bench issue through the OpenCode harness with real tool execution over three scripted turns; W3 the same issue driven by Claude Code through each engine's Anthropic-compatible endpoint, spawning concurrently-requesting subagents and growing sessions to 56-65k tokens; W4 thirteen fixed turns of an email/calendar agent through OpenClaw with a ~24.5k-token system-context floor (its 120 s idle watchdog disabled so slow engines stay measurable). The 3090/4090/5090 boxes are rented dual-socket servers capped at 6 CPU threads and NUMA-pinned to emulate edge hosts. Metrics are per-request mean decode tok/s and per-request mean TTFT.

  • Decode: 77-83 tok/s on Qwen3.6 and 22-25 tok/s on DSV4-Flash, i.e. 1.8-2.3x and 1.5-1.9x the strongest baseline in each workload; FreeToken stays within 12% of its single-turn W1 rate across the three agent workloads while KTransformers on DSV4-Flash has already lost 31% of its W1 rate by W2.
  • TTFT: lowest mean in five of six multi-turn cells. Tails separate the engines far more: FreeToken's worst turn stays below 44 s in every cell, while llama.cpp hits 232 s, Ollama 179 s and KTransformers 946 s - past OpenClaw's 120 s idle watchdog and near Claude Code's ~10-minute default timeout.
  • Prefill: with double buffering, each 8,192-token chunk completes in 1.19-1.22 s, the time to stream the 64.4 GB expert pool once at 52.7 GB/s, and throughput climbs to 6.7k tok/s at 16k tokens.
  • Cross-hardware: 1.3x on RTX 3090 and 4090, 1.9x on the 5090 server, 2.1x on the 5090 desktop, 1.8x on the RTX 4060 laptop, where NVFP4 sustains 39.3 tok/s on an 8 GB PCIe x8 machine - 92% of the RTX 4090 rate. Moving the same 5090 silicon from the many-channel server to a dual-channel consumer desktop costs FreeToken 4% of decode rate while llama.cpp keeps only 80%.
  • Frontier tier: GLM-5.2 on one RTX PRO 6000 at 14.9 tok/s vs llama.cpp's 7.3 (2.0x) with bit-identical expert weights and comparable mean TTFT (7.5 vs 7.8 s). KTransformers has no servable path - its GLM-5.2 methods need 753 GB-1.5 TB of host-resident experts against 512 GiB available.

Why it matters

The paper's positioning is that the accessibility gap for open weights is a software problem, not a hardware one: over a hundred million consumer machines already have discrete GPUs, and MoE sparsity already makes the computation feasible - DeepSeek-V4-Flash activates 6 of 256 routed experts in each of its 43 layers, so only 13B of 284B parameters participate per token, which fits an RTX 5090's 32 GB at deployed precision. What does not fit is the full expert pool. Prior offloading work (EdgeMoE, Mixtral-offloading, MoE-Infinity, ProMoE, ExpertFlow, FineMoE) competes on predicting misses but serves every miss as a PCIe transfer, so decode stays link-bound no matter how good prediction gets while host compute idles; prior hybrid CPU-GPU work (Fiddler, KTransformers, HybriMoE, SMoE) fixes or heuristically recomputes the division and is evaluated on single-shot short-prompt inference with no cross-request prefix reuse.

  • Supports more than 20 MoE models; the practical headline is 35B on a laptop, 284B on a gaming desktop, 753B on one workstation GPU.
  • The 39.3 tok/s laptop figure is explicitly compared against the 33 tok/s median decode speed of Codex in production traces.
  • Code at github.com/FlashML-org/FreeToken, releases at flashml.ai.

Key findings

  • The closed-form q* = m*B_P/B_H split of decode misses between PCIe cache-fill and in-place CPU execution, kept device-resident inside a captured CUDA Graph, yields 77-83 tok/s on Qwen3.6-35B-A3B (1.8-2.3x the best baseline) and 22-25 tok/s on 284B DeepSeek-V4-Flash (1.5-1.9x) on a single RTX 5090, with the MoE output exact (no approximation, no router modification).
  • A global LRU expert cache shared across all MoE layers cuts decode-time miss rate to 16% (Qwen3.6, cache = 37% of the pool) and 39% (DSV4-Flash, cache = 11%), versus 41%/59% for KTransformers' prefill-updated placement and 62%/89% for llama.cpp's static split on identical replayed routing traces.
  • Full-layer double-buffered prefill makes prefill purely transfer-bound: each 8,192-token chunk takes 1.19-1.22 s (exactly the time to move the 64.4 GB pool once at 52.7 GB/s) and throughput reaches 6.7k tok/s at 16k tokens; removing the second buffer costs 19% at 4k, 25% at 8k and 26% at 16k tokens.
  • Agentic robustness is the differentiator: FreeToken's decode rate stays within 12% of its single-turn W1 value across three agent workloads, while KTransformers on DSV4-Flash loses 31% of its W1 rate by the three-turn OpenCode workload, and MoE-Infinity can only serve W1 at all (8.8 tok/s).
  • Tail TTFT is treated as an availability boundary: FreeToken's worst turn stays under 44 s in every cell while every baseline crosses 150 s somewhere (llama.cpp 232 s, Ollama 179 s, KTransformers 946 s), past OpenClaw's 120 s idle watchdog.
  • Capability, not just speed: 39.3 tok/s for a 35B NVFP4 MoE on an 8 GB RTX 4060 laptop over PCIe x8 (92% of the RTX 4090 rate, above the 33 tok/s median Codex decode speed), a 284B model interactive on a 32 GB gaming desktop, and 753B GLM-5.2 at 14.9 tok/s on one RTX PRO 6000 where KTransformers has no servable path at all.

Notable quotes

Disabling the second buffer serializes transfer against computation and costs 19% of throughput at 4k tokens, 25% at 8k, and 26% at 16k, the penalty growing with prompt length as the share of hidden computation rises.
As a result, victim discovery always costs exactly one pass, regardless of the realized miss count.
Loading reads expert weights from disk directly into their final host layout and pins the memory only afterward; pinning empty buffers first would fault in and zero gigabytes of pages merely to overwrite them.
MoE-Infinity serves only W1 (8.8 tok/s): its per-expert prefill staging cap aborts the longer-prompt workloads, and its bundled server retains no KV cache across requests.

Limitations

  • The policy depends on two bandwidths (B_P, B_H) empirically profiled on the target machine at deployment, and on the fast path being establishable at all: when the complete expert pool cannot be pinned or DMA-registered (a restriction on some operating systems and driver configurations) FreeToken falls back to a pure-CPU MoE backend where every routed expert executes on the CPU. Pipelined prefill likewise degrades to on-demand loading whenever the slot pool cannot spare two full layers.
  • The workload assumption is small decode batches / interactive single-user agent serving - expert execution is memory-bound in that regime, which is what makes CPU co-execution pay off; the paper reports no batch-size sweep or multi-tenant/high-concurrency results, and by its own account cross-engine wall-clock totals are not compared because agent trajectories diverge.
  • Three of the six systems (3090, 4090, 5090) are rented dual-socket servers artificially capped at 6 CPU threads and NUMA-pinned to emulate an edge host, so most measurements are on emulated rather than native edge hosts; the semantic-anchor mechanism also assumes harnesses edit context only at special-token block boundaries, which a harness that truncates at arbitrary positions would break. No peak-memory measurements are reported.

Open questions

  • How does the q* split behave under concurrent multi-request or larger-batch decode, where expert execution stops being purely memory-bound and CPU cores are also contended by other applications - and how does the elastic KV/expert rebuild interact with a VRAM budget that shrinks mid-generation because a game or browser claimed gigabytes?
  • Since q* is derived from statically profiled B_P and B_H, can the ratio be re-estimated online as real contention changes the effective bandwidths, rather than measured once at deployment?
  • The semantic-anchor state cache is evaluated indirectly through end-to-end TTFT; how much of the TTFT win comes from anchors versus pipelined loading, and how robust is anchoring to harnesses whose context edits do not align with special-token block boundaries?
