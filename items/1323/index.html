HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

📰 Latest · 2026-09-05 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-05

Source: arxiv · 2026-09-01
Link: https://arxiv.org/abs/2609.01437

A ByteDance Seed-led benchmark makes the agent harness itself the unit of evaluation: six frontier models must grow a runnable execution system from a deliberately crippled seed, then iterate on it from downstream feedback. Model-built harnesses already beat the human reference on ML experimentation and match it on writing, but trail badly on search (52.4 vs 92.2 BrowseComp) and code — and self-evolution gains largely evaporate on held-out tasks.

Executive summary

HarnessDev evaluates whether an LLM can build the software that runs it, not whether it can answer a task. A creator LLM starts from a weak-but-runnable seed harness (no agent loop, no tools policy, no context management, no state, no recovery, no verifier — it scores 0.0 on every benchmark unmodified) and must implement six control modules; the finished harness is then FROZEN and run by a separate executor LLM on 2,207 hidden downstream instances across code, data analysis, writing and research. Under Self-Eval the best creator (Opus 4.8) averages 67.8 against an 86.2 human-engineered reference: it exceeds the reference on MLE-bench (32.9 vs 24.0) and matches it on EQ-Bench3 (84.6 vs 83.7), but is far behind on BrowseComp (52.4 vs 92.2) and still behind on code (69.3 vs 80.0 SWE-Pro, 64.8 vs 88.8 Terminal-Bench). In the Evolution stage all five self-runtime lineages improve on the visible feedback set (up to +13.9 points) but held-out gains collapse to +1.43 to +4.44 (mean +3.11), and under a fixed Gemini executor three of four lineages regress (GPT-5.5 by -10.32).

What counts as a "harness" here (all six layers, as code)

The harness is not a prompt template or a tool list — it is the entire model-external execution substrate, delivered as a Python package the creator must write. Appendix C fixes the contract as six functional modules with concrete signatures. Roles are separated: a creator LLM L_C works inside a development environment D to produce harness H; H is then frozen and an executor LLM L_E runs it on the downstream task, with an evaluator J scoring the output. Tokens the creator spent building the harness are excluded from reported cost; only executor tokens count.

  • execution.py — run(task) -> Result; step(state, observation) -> Action (the control loop)
  • tools.py — register(toolspec); call(name, **params) -> Observation (tool policy)
  • context.py — build(task, history, state) -> Prompt; compress(messages) -> Messages
  • state.py — save(checkpoint); load(id); resume() -> State (persistent state / memory)
  • lifecycle.py — beforeAction / afterAction / onFailure -> Recovery / onTimeout -> Graceful
  • evaluation.py — evaluate(result, criteria) -> Score; recordTrajectory(step)
  • The seed supplies only a stable CLI, an LLM gateway with no policy, passive primitives (paths, files, search, process, artifact io) and the audit envelope (result.json, trajectory.jsonl, response.md, logs)

How the benchmark and its tasks were constructed and validated

Creation gives every creator the same weak seed plus a task-family specification, tool/permission constraints, a short design tutorial, and only one to three development cases; the creator never sees the human implementation or the hidden evaluation set. Downstream coverage is five existing public benchmarks re-used as hidden evaluation sets, totalling 2,207 unique instances. Validity rests on structural guarantees rather than trust: the score path is isolated from the harness (SWE-Pro credit comes only from the real repository diff, Terminal-Bench credit only from final environment state, so a harness cannot earn points by self-reporting success), and every run retains its trajectory, results and metric artifacts alongside the frozen source for post-hoc audit. The authors audited every reported run and report a null result — no harness scored through a prohibited route. Each creator-benchmark pair is built and evaluated three independent times and reported as avg@3.

  • Code: SWE-bench Pro public split, 731 tasks; Terminal-Bench 2.1, 89 tasks
  • Data analysis: MLE-bench, 75 tasks, medal score; Writing: EQ-Bench3, 46 tasks; Research: BrowseComp, 1,266 tasks
  • Two evaluation views: Self-Eval (L_E = L_C, the deployment regime) and Unified-Eval (every harness run by a fixed Gemini 3.1 Pro)
  • Explicitly banned: hard-coded instance solutions, patches derived from task IDs or filename allowlists, reading hidden tests/answers/scorer internals, bypassing the provider-neutral runtime interface
  • Human references are verified public leaderboard results, NOT paired controls under one executor — a limitation the authors flag repeatedly

Creation results: the gap is domain-shaped, not uniform

The unmodified seed scores 0.0 on all five benchmarks, so every point is attributable to creator-written execution logic. Under Self-Eval, Opus 4.8 leads with a 67.8 average against the 86.2 human-reference average. The ordering of the gap is the useful signal: search/research is worst, code is next, short-form writing is already at parity, and ML experimentation is ahead of the chosen reference. Notably, 77.8% of failed Data tasks were attributed to harness defects rather than executor incapability.

  • Search/research is the largest gap: best creator BrowseComp 52.6 (GPT-5.5) / 52.4 (Opus) vs 92.2 reference
  • Code still trails: Opus 69.3 SWE-Pro vs 80.0; Gemini 68.8 Terminal-Bench vs 88.8
  • Writing at parity: Opus 84.6 EQ-Bench3 vs 83.7 reference
  • ML experimentation ahead: Opus 32.9 and Gemini 32.4 MLE-bench medal rate vs 24.0 reference
  • Wide spread across creators: 67.8 (Opus) down to 22.8 (Seed 2.0 Pro) on the same seed and specification

Cost and executor portability: harnesses co-adapt to the model that wrote them

Execution cost varies enormously and is uncorrelated with quality — MLE-bench token use spans roughly nineteen-fold, and GPT-5.5 reaches a 19.1 medal rate on 29.3M tokens while DeepSeek V4 reaches 19.6 on 208.4M. The authors deliberately refuse to collapse this into a single cost-adjusted score. Portability is per-harness: swapping the executor to Gemini improves several Qwen and DeepSeek harnesses but wrecks Opus's, because Opus's harnesses encode assumptions about their original runtime. One Opus Code harness hard-codes a 120-step limit around its original executor and nearly collapses under Gemini.

  • Opus SWE-Pro falls 69.3 -> 33.0 and Writing 84.6 -> 74.2 when the executor changes to Gemini
  • In the Opus Search harness the duplicate-query rate rises from 10.1% to 88.2% under a different executor
  • Qwen gains +17.6 points on BrowseComp and +12.9 on MLE-bench under Gemini
  • Fixing the executor substantially reorders the leaderboard, so Self-Eval measures harness design, executor capability AND their compatibility
  • Per-task compute for MLE-bench: one A800-SXM4-80GB GPU, 14 vCPUs, 227 GiB RAM, 36,000 s wall clock and a 500-step cap

Evolution: iterating on your own harness helps a little, unreliably

Evolution starts each creator from its own frozen RQ1 code harness H_0 and gives it downstream execution feedback from a fixed 100-task SWE-Pro set plus all 89 Terminal-Bench tasks, with a budget of ten post-H_0 full-evaluation pairs. After all trajectories end, every official version is additionally scored on a disjoint 630-instance SWE-Pro held-out split the creator never sees. Nine lineages produced 73 official versions and 64 adjacent switches. Every self-runtime lineage improved on the visible feedback set, but the held-out delta is roughly a quarter to a third the size, and under a fixed executor most lineages regress.

  • All five self-runtime declared versions beat H_0 on held-out tasks, by +1.43 to +4.44 points, mean +3.11
  • Under the fixed Gemini runtime only Opus improves (+2.70); Qwen -1.11, DeepSeek -2.38, GPT-5.5 -10.32
  • Feedback gains overstate progress: Qwen +13.9 and DeepSeek +13.4 on the feedback pair translate to only +1.43 and +3.17 held-out
  • Of 64 official switches, 8 regress on both benchmarks, 16 on one, 3 trade off, 7 change nothing, 27 sit inside the repeated-run noise band, only 2 show clear positive evidence, and 1 contains no executable code change at all
  • Re-running the SAME commit varies by about +/-4.75 pair-score points
  • Feedback score and held-out score move in the same direction on only 34 of 64 switches (53.1%), and only 2 of 9 declared final versions are held-out optimal
  • Median declared version changes 8 files, +476/-38 lines; across 64 switches 58 touch execution/control flow, 37 tools, 17 lifecycle recovery, 16 context, only 4 state, and none add a standalone verifier

Implementation forensics: what the generated harnesses actually get wrong

The most actionable part for harness builders is the audit of frozen artifacts against their recorded execution traces. State and memory are the systematic blind spot; a large fraction of generated machinery is never executed; and the creators are far better at writing code than at diagnosing why their harness failed. Edit volume is a non-signal — the 18 Code artifacts add 17,111 net lines in total, yet Gemini adds the fewest (1,006) and gets the best Terminal-Bench score (68.8).

  • All 18 Code harnesses implement an explicit execution loop; tools complete in 13/18, lifecycle control 13/18, verification 15/18
  • State/memory is the clearest gap: 11/18 define a State class, but only ONE exposes a state-saving interface and only ONE implements periodic checkpointing — and zero checkpoint events fire across 26,679 recorded trajectories
  • Dead code is rampant: of 108 Code component instances, 18 are never observed (all state/memory); 124 of 587 Writing features are confirmed dead; of 169 new functions added during Evolution, 31 are reachable only through dead code and 25 have no caller
  • Validation is mostly syntactic: 441 of 2,325 executed Data tasks produce degenerate submissions that no harness detects
  • Writing self-tests is not the skill that matters: self-test count correlates with downstream score at only Spearman 0.13-0.26 (n.s.), while revision calls reach 0.57 (p <= .0005)
  • Diagnosis is the weakest loop step: the dedicated trajectory interface was called only twice across all lineages, and explicit case inspection covered just 0.5%-40.2% of the 189 feedback tasks
  • The best counter-example: Opus noticed 99 of 100 runs reported success while only 48 actually passed, traced it to premature completion, and added a completion gate

Key findings

  • Model-built harnesses beat the human-engineered reference on ML experimentation (Opus 32.9 / Gemini 32.4 MLE-bench medal vs 24.0) and match it on short-form writing (84.6 vs 83.7), but the search/research gap is enormous (52.4-52.6 BrowseComp vs 92.2) and code still trails (69.3 vs 80.0 SWE-Pro; 68.8 vs 88.8 Terminal-Bench). Best overall creator average 67.8 vs 86.2.
  • Harnesses co-adapt to the model that wrote them: Opus's SWE-Pro score falls 69.3 -> 33.0 and its Search harness's duplicate-query rate rises from 10.1% to 88.2% when the executor is swapped to Gemini, while Qwen gains +17.6 on BrowseComp under the same swap.
  • Cost is decoupled from quality — MLE-bench execution tokens vary about nineteen-fold, with GPT-5.5 scoring 19.1 on 29.3M tokens against DeepSeek's 19.6 on 208.4M.
  • Evolution gains are real but small and fragile: all five self-runtime lineages improve held-out by +1.43 to +4.44 (mean +3.11), yet under a fixed Gemini executor three of four regress (GPT-5.5 by -10.32). Feedback-set gains of +13.9 shrink to +1.43 held-out.
  • Most apparent Evolution progress is noise: the same commit re-run varies by about +/-4.75 pair-score points, only 2 of 64 official switches show clear positive evidence beyond that band, feedback and held-out scores agree in direction only 53.1% of the time, and just 2 of 9 declared final versions are actually held-out optimal.
  • Persistent state is the structural blind spot: 11 of 18 code harnesses define a State class but only one saves state and only one checkpoints, and no checkpoint event fires in 26,679 recorded trajectories.
  • Code volume does not predict harness quality (Gemini adds the fewest lines at 1,006 and wins Terminal-Bench at 68.8), and self-test count barely correlates with score (Spearman 0.13-0.26, n.s.) while revision calls do (0.57, p <= .0005).

Notable quotes

Unmodified, it produces an empty or partial artifact and scores zero on every downstream benchmark.
No checkpoint event appears in 26,679 recorded task trajectories.
A runnable harness can therefore be used by another model, but capability transfers only when its prompts, tool protocol, budgets, and stopping rules remain compatible.
Visible feedback is therefore useful for local search but unreliable for final selection: repeatedly optimizing a noisy score can favor a lucky run and amplify overfitting.

Limitations

  • Human references are unpaired external leaderboard results, not controls run under a common executor, so the reported 'distance to human' mixes harness quality with the reference system's executor model; Unified-Eval cannot fully remove executor-model differences.
  • Evolution has only ONE trajectory per creator-runtime cell (nine lineages) and its post-freeze held-out evaluation covers SWE-Pro only, so the trajectories support no uncertainty estimates — with a +/-4.75-point noise band, most individual lineage conclusions are underpowered.
  • The development environment D is held fixed (Claude Code 2.1.177, or Codex 0.144.3 for GPT-5.5), and Evolution covers code harnesses only; whether an evolved harness can itself serve as the development environment for further evolution is left to future work.

Open questions

  • Why is the search/research gap so much larger than the code gap — is long-horizon information seeking a harness-design problem the creators cannot see from 1-3 development cases, or an executor-capability ceiling?
  • Given that feedback and held-out scores agree only 53.1% of the time, what selection signal SHOULD an autonomous self-improving agent use to decide which of its own harness versions to keep?
  • Can the state/memory layer be forced into existence — every creator declares it and none uses it — and would persistent state plus real checkpointing close any of the code or search gap?
