    Groundability, Not Scale Alone: When Weak Reviewers Can Audit Strong Coding Agents

    ← Go backFalse Frontiers: Diagnosing and Mitigating Co-Cheating in…NextMid-Harness: Scaling Actions Between Model and Harness for… →
    📰 Latest · 2026-10-02 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-02

    Source: arxiv · 2026-10-01
    Link: https://arxiv.org/abs/2610.01023

    When small, nominally weaker models review strong coding-agent patches, the evidence they get matters more than their size. Given decisive execution evidence, GPT-OSS-120B and GPT-4.1 judge all 122 held-out GPT-5.4 traces correctly. A deployable cascade (no-op gate, static errors caused by the patch, generated tests that must fail on base, an 8B residual reviewer) still over-rejects 66% of correct patches. Build mechanical checks, not bigger judges.

    Executive summary

    The paper asks when a nominally weaker reviewer model can reliably decide accept / reject / uncertain on a strong coding agent's patch. The main failure it targets is omission: a missing branch, implementation, or check. Using 411 real traces labeled by execution (three agents) plus 101 controlled cases, it shows that raw traces and structured-but-unchecked evidence raise defect catch and false rejection together. 'Groundable' evidence (an independent check that can settle the disputed requirement) breaks that trade-off: with official execution evidence as an upper bound, 5 of 6 reviewers improve both rates on held-out traces. A frozen cascade that can actually be deployed recovers only part of this: coverage 0.89/0.86, catch 0.76/0.80, but over-rejection 0.66/0.67 on held-out GPT-5.4 and Gemini traces.

    Problem: omissions hide in plausible patches

    Coding agents return patches with confident summaries, and the user must decide whether the task was actually done. In 154 real GPT-5.4 traces on SWE-bench Lite/Verified (10 Python repos), official hidden tests mark 101 patches as defective. Omissions are the largest bucket (76). The authors define groundability as whether an independent check (a sound static analysis or a runnable test) can answer the disputed question, exposing real defects without raising the same alarm on correct patches. 'Weak' means an earlier or smaller model tier than the audited GPT-5.4 agent. It is not a measured capability ordering or a cost claim.

    • Running example (django-11905): the guard `self.rhs not in (True, False)` looks correct, but since 1 == True in Python the integer 1 still passes, so the official fail-to-pass test still fails.
    • Reviewability (can the reviewer reach the right decision from this evidence?) is kept separate from correctness (does the patch pass the hidden official suite?).
    • Reviewer is held fixed while the evidence varies, the reverse of most weak-to-strong / sandwiching studies.

    Benchmark: 411 execution-labeled traces + 101 controlled cases

    Three audited agents run with a minimal JSON-tool harness (12 turns, 2048 max output tokens per turn): GPT-5.4 (primary), Gemini-2.5-Pro (cross-agent transfer) and Claude-Sonnet-5 (coverage set). Each trace is labeled by stripping test hunks the agent added and running the official fail-to-pass / pass-to-pass suites in the official SWE-bench containers. The label is accept, or reject with a bucket: real omission, regression, or no code change. Test IDs and labels never appear in deployable prompts, and automated leakage audits found zero failures. All design choices were made on a 32-trace Django design set. The remaining partitions were fixed and evaluated once.

    • GPT-5.4 core: 154 traces (53 accept / 76 omission / 9 regression / 16 no change). This includes the 32-trace design set; the other 122 are held out.
    • Gemini transfer: 59 traces (15 / 33 / 1 / 10) over 6 Python repos.
    • Accept/no-change sets: 78 GPT-5.4 traces on SWE-bench Multilingual (9 non-Python languages) and 120 Claude-Sonnet traces. All 61 submitted patches pass. Every rejection is an empty submission (137 total).
    • Controlled cases: 37 reference-patch controls, 34 single-piece ablations (9 import / 10 surface / 15 partial-logic) and a 30-case naturalistic pilot.

    Evidence formats, reviewers and metrics

    Each trace is shown in three ways: (1) agent artifacts (final summary, patch only, or full trace), i.e. testimony; (2) structured, non-grounded evidence: changed hunks, requirement coverage, heuristic audit signals and LLM-proposed 'what is missing' items, plus an empty-section control; (3) grounded evidence backed by a check the pipeline ran. The upper bound uses official execution results. The deployable version uses generated tests that pass a fail-on-base check. Grounded evidence is tested in two formats, with unchecked risk notes kept or removed. Six reviewers: Llama-3.1-8B, Qwen-2.5-Coder-32B, Qwen-2.5-72B, GPT-OSS-120B, Qwen3-235B, GPT-4.1. Each runs with temperature 0.8, a k=5 majority vote (ties = uncertain) and JSON output (decision, rationale, cited_evidence), with no tools.

    • Metrics: catch = rejected defects / all defects; over-rejection = rejected acceptable patches / all acceptable patches. Abstentions stay in both denominators. Also coverage (fraction decided) and selective risk (error rate among decisions).
    • An evidence change 'improves the trade-off' only if catch rises without higher over-rejection, or over-rejection falls without lower catch, since rejecting everything maximizes catch.
    • The reviewer prompt explicitly says official execution evidence is decisive and generic risk flags are not. The misreadings the paper reports happen despite this instruction.

    Results: raw and structured evidence fail, official checks break the trade-off

    Patch-only review looks precise only because it accepts almost everything. On the nine real design-set omissions, Llama-8B accepts 9/9 from the diff and GPT-4.1 catches 0.27. Full traces give no reviewer its best trade-off (Qwen-32B catches 0.17 of omissions). Naming a construction-known missing item lifts catch on 15 synthetic partial-logic omissions from 0.53 to 1.00 (GPT-4.1) and from 0.07 to 1.00 (Llama-8B). On real traces, though, structured evidence raises false rejections too: on the design set GPT-4.1 catches 0.91 of defects but rejects 0.86 of acceptable patches. With official execution evidence, in a format chosen on the design set and then frozen, 5 of 6 reviewers improve both catch and over-rejection on the 122 held-out traces. Qwen-2.5-72B is the exception.

    • Bigger is not better: under structured evidence Qwen3-235B has the lowest catch (0.28), below Llama-8B (0.70).
    • Gemini transfer (3 reviewers, frozen formats): all catch 44/44 defects. Llama-8B wrongly rejects 1 of 15 acceptable patches; GPT-OSS-120B and GPT-4.1 get all 59 right.
    • Accept/no-change sets: structured evidence yields only 12, 5 and 7 correct accepts of 61 (GPT-4.1 abstains on 40/61). Grounded evidence restores 49, 61 and 61. Patch-only Llama-8B accepts 64/137 empty submissions, while patch-only GPT-4.1 abstains on 126/137.
    • Of the three interventions tested (different reviewer, more votes, different evidence), only changing the evidence improves the aggregate result consistently. Votes help a little: the grounded three-reviewer mean goes 0.953 (K=1) to 0.978 (K=5) to 0.985 (K=9).

    The deployable cascade (frozen, run once)

    Official tests do not exist at deployment time, so Algorithm 1 tries cheap checks first and stops at the first decision. Stage 0 rejects empty patches. Stage 1 rejects on a sound static error, only if the patch caused it. Stage 2 has Gemini-2.5-Pro generate a test from the issue and patch (at most 3 repair attempts, repair feedback from the base side only). The test is kept only if it fails behaviorally on the unpatched repo; it then rejects if it fails on the patch and accepts if it passes. Stage 3 sends the remaining traces to Llama-3.1-8B with k=5 votes, and 'uncertain' becomes an abstention. On the 121 scored held-out GPT-5.4 traces (89 defects, 32 acceptable), Stages 0-2 decide 36 traces: 15 no-op rejects, 0 static rejects, 11 test-fail rejects, 10 test-pass accepts. The 8B reviewer handles the other 85: 63 reject, 9 accept, 13 abstain.

    • The attribution filter matters. Without it, static analysis wrongly rejects two correct dev-set patches, and an unrelated execution error makes the reviewer reject 4 of 5 correct patches.
    • Generated tests are asymmetric: a checked test that still fails on the patch has reject precision 0.82, but a passing test has accept precision only 0.30. One test covers much less behavior than an official suite.
    • 19 of the 21 held-out false rejections come from the residual reviewer stage.
    • Three hypotheses tested on the design set failed. Re-running 18 failed tests in faithful Docker environments recovered no decisions. Harness repair moved generated-test decisions only from 13 to 16/32. Patch-conditioned generation produced no test that passes on the agent patch but fails on the reference patch.

    Why it matters for agent builders

    The cascade's measured advantage is coverage, not accuracy. On traces both systems decide, it is not significantly more correct than structured review (p >= 0.12). It does beat patch-only review (paired permutation p from 0.0002 to 0.03), and lower-risk baselines abstain on 25%-66% of traces. The design guidance: spend budget on targeted checks, consume a patch-caused failure mechanically, send only unresolved cases to the reviewer with the patch, check results and needed context, and always allow 'uncertain'. Small models misread even decisive evidence. In audited over-rejections the rationale says execution failed while the cited line says it passed. So decisive grounded evidence should be applied by a mechanical gate, not re-read by an LLM.

    • Tool-using baseline (GPT-4.1 with read/search/exec tools, 12 turns, 1 sample, on subsets of 40 held-out and 20 Gemini traces): coverage 0.55/0.45, risk among decided traces 0.36/0.11 vs 0.46/0.33 for the cascade on the same subsets. It used 58-84x the prompt tokens (about 84k-91k per trace) but issued only 0.90 tool commands per trace.
    • Qwen-2.5-72B dissection: over-rejection replicates (41/53 under the clean format) and survives prompt calibration (40/53). Of 198 audited over-rejections, 173 contradict their own citation, so reviewers should be screened for evidence-to-decision calibration before deployment.

    Key findings

    • Patch-only review misses omissions: on 9 real design-set omissions Llama-8B accepts 9/9 and GPT-4.1 catches 0.27, with over-rejection near 0.
    • Structured but unchecked evidence raises catch and false alarms together: GPT-4.1 catches 0.91 of design-set defects but rejects 0.86 of acceptable patches.
    • With official execution evidence (upper bound), 5 of 6 reviewers improve both rates on 122 held-out traces. GPT-OSS-120B and GPT-4.1 reach catch 1.00 / over-rejection 0.00, and Llama-8B reaches 0.98 / 0.00. Qwen-2.5-72B's over-rejection does not improve (0.44 to 0.47).
    • Scale is not monotonic: under structured evidence Qwen3-235B catches 0.28 vs Llama-8B's 0.70. Only the evidence intervention improves results consistently, not more votes or a different reviewer.
    • The deployable cascade reaches coverage 0.89/0.86, risk 0.33/0.26, catch 0.76/0.80 and over-rejection 0.66/0.67 (held-out GPT-5.4 / Gemini). 19 of the 21 held-out false rejections come from the residual 8B reviewer.
    • Generated tests that pass the fail-on-base filter are asymmetric evidence: reject precision 0.82 when they still fail on the patch, accept precision only 0.30 when they pass.

    Notable quotes

    Patch-only review misses omissions because it only shows what changed.
    Without a checkable signal for each case, catch and false alarms rise together.
    A patch-caused failure can therefore support rejection, but one passing test cannot establish correctness.
    Practical systems should prioritize reliable checks and safer handling of unresolved cases over larger reviewers alone.

    Limitations

    • Real-defect results cover only Python (GPT-5.4 and Gemini sets on SWE-bench). The multilingual and Claude sets contain no defects and measure only acceptance and no-change handling. The 32-trace design set is all Django.
    • The strongest result uses official execution evidence, which is not available at deployment. The deployable cascade still has risk 0.33/0.26 and over-rejection 0.66/0.67, so the authors call it a stress test, not a reliable deployed reviewer.
    • Call counts exclude test generation, the test sets lack a full-set generated-test-only baseline, and the tool-using reviewer baseline is limited (1 sample, about 0.9 tool commands per trace). The paper therefore makes no total-cost or general agentic-review claim.

    Open questions

    • How can generated tests be made decisive in the accept direction? A single passing test has accept precision of only 0.30, and both under- and over-specified probes occur.
    • Can the residual stage, which causes most false rejections, be calibrated, for example by screening reviewers for evidence-to-decision consistency or by abstaining more, without giving up the cascade's coverage advantage?
    • Do the groundability findings hold for non-Python defects, adversarial (not benign) omissions, and stronger tool-using reviewers that actually run checks?
