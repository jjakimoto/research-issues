SWE-Gate: Passing Functional Tests Is Not Enough for Software Engineering Agents

📰 Latest · 2026-09-12 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-12

Source: arxiv · 2026-09-03
Link: https://arxiv.org/abs/2609.04167

SWE-Gate shows SWE-bench-style functional tests miss a third of the ways agent patches actually fail: across four LLM backends, 221 of 644 functionally passing repairs violate executable review-derived acceptance constraints, so leaderboard pass rates systematically overstate real-world patch acceptability.

Executive summary

SWE-Gate is a repository-level benchmark that evaluates coding agents on two separable, independently executable dimensions: functional correctness and compliance with review-derived acceptance constraints (gates) mined from real pull-request review comments. Each of its 303 instances (75 open-source Python repos, six domains) ships an issue description, a mutant patch, separate functional and constraint tests, plus a non-compliant patch (passes functional, fails constraint) and a gold patch (passes both), proving the two dimensions are separable and jointly satisfiable. Evaluating GPT-5.5, GPT-5.4-mini, DeepSeek-V4-Flash and GPT-4o-mini under a common Mini-SWE-Agent scaffold, 644 patches pass functional tests but only 423 pass both - a 34.3% hidden failure rate. Giving the agent the natural-language constraint raises constraint compliance by 10.2-25.6 points but slightly lowers functional success.

The gap the benchmark targets

Existing repository-level benchmarks use a single criterion: does the patch pass the PR's functional tests. In practice maintainers reject functionally correct patches during review for reasons like breaking backward compatibility, altering exception semantics, or ignoring repository conventions. The authors call these review-derived acceptance constraints, or gates, and argue they are objectively testable and separable from the functional requirement.

  • Motivating case: a Pydantic PR adding conditional serialization of extra fields, where the reviewer rejected a new core-schema representation as breaking and asked for a parameter instead
  • A functional test can check the serialization behavior while a separate compatibility test checks the public schema is unchanged
  • Prior constraint-aware repo-level work (SWE-Shield) relies on LLM-based verification; SWE-Gate uses deterministic executable oracles

Instance schema and the validation matrix

Each instance contains seven artifacts: issue description, mutant patch, functional test, constraint description, constraint test, non-compliant patch, and gold patch. Validity is defined by an execution matrix over the original repo, the mutant, the non-compliant repair and the gold repair.

  • The non-compliant patch proves the constraint is not a restatement of the functional requirement
  • The gold patch proves the constraint is satisfiable simultaneously with the functional fix
  • Agent-generated edits to benchmark test files are discarded before execution to prevent evaluation leakage

Constraint-first construction pipeline

Rather than reusing the source issue-PR pair, SWE-Gate extracts a constraint seed from real review discussions in mature seed repositories and transfers it into a compatible instance repository, following SWE-Mirror's cross-repository transfer paradigm. A first-stage LLM decomposes review comments into atomic suggestions and rule-based filters drop workflow, docs-only, test-only, formatting, naming and vague requests; a second stage keeps only candidates with a linked issue, supporting diff, an added (not restated) requirement, and independently validatable behavior.

  • Synthesis is a progressive two-phase generate-execute-refine loop: first mutant plus functional test, then constraint test, non-compliant patch and gold patch
  • Quality assurance is three-layer: structural checks, Docker validation of the full matrix, LLM semantic review against a human-derived failure-pattern taxonomy, then final manual inspection
  • Rejection patterns include constraints restating the issue, constraints prescribing a specific API, constraint tests enforcing unstated behavior, and descriptions leaking hidden evaluation artifacts
  • Authors explicitly say the transfer mitigates but does not eliminate training-data contamination

Metrics and results

Three metrics: FSR (functional successes over all instances), CFR (joint successes over functional successes), and JSR (joint successes over all instances, the headline metric). A patch passing functional but failing constraint validation is a hidden failure. Under the intended Constraint-Provided setting, functional and joint rates diverge sharply for every model.

  • GPT-5.5: FSR 74.9%, CFR 70.5%, JSR 52.8%
  • GPT-4o-mini bottoms out at FSR 9.2% and JSR 4.3%, showing the benchmark is hard for weaker models
  • Aggregate hidden failure rate is 34.3%, ranging 29.5% (GPT-5.5) to 53.6% (GPT-4o-mini)

Constraint guidance ablation and category analysis

The no-constraint condition withholds the natural-language constraint but keeps the same hidden tests. Supplying the constraint raises CFR and JSR for all four models while functional success stays flat or drops, which the authors read as a complexity trade-off rather than a causal claim (one generation per model-instance). Per-category results use a multi-label taxonomy, so rows overlap and cannot be summed.

  • Joint successes across all models rise from 360 to 423 when the constraint is supplied
  • CFR gains: +15.9 (GPT-5.5), +13.5 (GPT-5.4-mini), +10.2 (DeepSeek-V4-Flash), +25.6 (GPT-4o-mini) points
  • FSR falls 3.3-9.9 points for three models and 0.7 for GPT-5.5
  • Hardest constraint categories for the stronger models: Scope Generalization and Lifecycle Cleanup/Resource
  • Easiest: Missing-vs-Empty/Sentinel Distinction (74.2-81.6%) and Ordering/Argument Preservation (75.0-79.6%)

Key findings

  • Across four LLM backends, 644 patches pass the functional tests but only 423 pass both suites: 221 hidden failures, 34.3% of all functional successes.
  • Even GPT-5.5 converts only 227 functional successes into 160 joint successes (CFR 70.5%, JSR 52.8%), so 29.5% of its working patches would be rejected on review grounds.
  • Supplying the natural-language constraint raises CFR by 10.2 to 25.6 percentage points and lifts total joint successes from 360 to 423, but lowers FSR for every model (-0.7 to -9.9 points).
  • The benchmark is 303 instances over 75 Python repositories; dominant constraint categories are Error Semantics (152 instances, 50.2%) and Schema/Metadata/Typing (143, 47.2%).
  • Constraint difficulty is uneven: Scope Generalization and Lifecycle Cleanup/Resource are hardest for the stronger models, while Sentinel Distinction (74.2-81.6%) and Ordering/Argument Preservation (75.0-79.6%) are comparatively easy.
  • GPT-4o-mini functionally resolves only 9.2% of instances and has a 53.6% hidden failure rate, confirming the tasks are not trivially solvable.

Notable quotes

The corresponding CFR is 70.5%, meaning that 29.5% of its functionally successful repairs violate the accompanying constraint.

One possible explanation is that satisfying an additional requirement increases the complexity of the repair and may steer an agent away from a simpler functionally adequate patch.
These constraints demand coverage beyond the immediate failure or preservation across a resource lifecycle, making them difficult to satisfy with a narrowly localized patch.

Limitations

  • Python-only, 303 instances, and constraints must be expressible as executable tests - review requirements that resist mechanical oracles are excluded by construction.
  • Instances are LLM-synthesized via cross-repository transfer rather than taken directly from the original issue-PR pairs; the authors concede this mitigates but does not eliminate training-data contamination.
  • One generation per model-instance and overlapping multi-label categories (some with only 19-30 instances) make the ablation and per-category comparisons descriptive rather than causal.

Open questions

  • How can review requirements that cannot be expressed as executable tests (readability, maintainability, design taste) be evaluated reliably?
  • Does the functional-vs-constraint trade-off persist under stronger scaffolds, more interaction steps, or multi-sample generation?
  • Would fine-tuning agents on constraint-annotated repair tasks close the 34.3% hidden failure gap, and does it generalize beyond Python?
