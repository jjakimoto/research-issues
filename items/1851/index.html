    Compact Documentation for Coding Agents: A Benchmark, an Optimizer, and Why It Does Not Transfer

    ← Go backFinancial Language Models as Applied Artificial Intelligence…NextYour Transformer Can Hold Two Thoughts at Once: Evidence of… →
    📰 Latest · 2026-09-28 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-28

    Source: arxiv · 2026-09-25
    Link: https://arxiv.org/abs/2609.31587

    The authors built a roundtrip benchmark and a prompt optimizer that produce file descriptions accurate enough to rebuild the code. Those descriptions lift issue resolution from 0.08 to 0.71 when the agent cannot see the source. Once the source is in context they help nothing and sometimes hurt, and a positive control confirms the evaluation could have seen a real gain. So if you build coding agents, per-file summaries sitting next to readable code are likely wasted tokens, and documentation earns its place only when the code does not fit in the context window.

    Executive summary

    The paper introduces a roundtrip benchmark: describe a source file, regenerate it from the description alone, and score the result with the file's original tests. The benchmark shows that completeness, not length, drives how well a description rebuilds its file. Using the benchmark as the objective, an optimization loop finds a description-writing prompt that reaches full fidelity and also works on held-out files. The motivating hypothesis was that better documentation helps agents fix real issues. That held only when the source file was withheld. With the source present, across two model families, ten repositories, and a validated positive control, neither compact descriptions nor retrieved context beat giving the agent the issue alone.

    When documentation helps at all

    Controlled experiments with a weak agent (Flash-lite) show that a description helps only when it carries intent or a contract the code does not expose. A description that restates readable code adds nothing.

    • On three hand-built codebases, the contract appears only in the description. Adding the description takes the agent from 0/3 to 3/3 on each.
    • When the description only restates visible code, including a real 423-line file, the agent succeeds with or without it.
    • Uplift tracks completeness exactly: descriptions carrying 1, 3 or 5 of 5 facts give 1, 3 and 5 correct.
    • Length is second-order: a complete 38-word description and a complete 664-word one both score 5/5.

    The roundtrip benchmark

    There are 11 fixtures from SWE-bench Verified, picked by a scripted filter: the gold patch touches exactly one non-test file and the test patch names the oracle tests. That filter admits 429 of 2294 instances, which are then narrowed to sympy. The pipeline runs describe (tests hidden), then regenerate (a separate model sees only the description, an empty scaffold and a contract file of public symbols), then evaluate (the original tests).

    • Both stages run on gemini-3.5-flash at temperature 0, with 3 runs per fixture.
    • Mean fidelity is 0.32 +/- 0.35. One fixture scores 1.00, four score 0.00, so the benchmark is far from saturated.
    • Density (description tokens divided by code tokens) correlates with fidelity at Pearson 0.88. All zero-fidelity fixtures have density below 0.45.

    Optimizing the description writer

    The describe prompt is treated as a harness. gemini-2.5-pro proposes rewrites, and the objective is J = mean fidelity - 0.1 * (mean words / 300). The loop trains on 3 fixtures and tests on 2 held-out fixtures.

    • Fidelity first rises to 1.0 on training, then description length falls while fidelity stays at 1.0.
    • Held-out fidelity rises from 0.5 to 1.0 using fewer words than the baseline; three independent runs all reach full training fidelity.
    • Without ever seeing the hand-built failure analysis, the discovered prompt asks for exactly its fixes: exact imports, constants with literal values, and exact signatures, defaults, exceptions and return paths.
    • OpenWiki's agent-oriented documentation rebuilds code worse on 3 of 3 fixtures.

    Transfer: source withheld vs. source present

    Descriptions are generated from the pre-fix file, so the fix cannot leak into them. With the file withheld, optimized descriptions work as a substitute for the code. With the file present, the normal agent setting, the benefit disappears.

    • Source withheld: mean test-pass fraction is 0.08 with the issue alone, 0.21 with the baseline description and 0.71 with the optimized one.
    • Django with Gemini 3.1 Pro: issue alone 9/15, compact 8/15, full description 4/15.
    • Positive control, SWE-ContextBench django: retrieved context resolves 15/29 versus 14/29 for issue alone.
    • Full SCB Lite with Gemini 3.8 Flash: issue alone 33/58, context 30/58, compact 29/58 (McNemar p=0.22 and p=0.25).

    Editing without loading the file, and the boundary

    In a targeted-symbol protocol, the agent names the symbols it needs and receives only their source. The description did not help (17 vs 14 of 33 runs, mean pass fraction 0.94 in both) and cost more tokens than it saved. The authors conclude that this kind of documentation is a compression format for code that does not fit in context, and is redundant inside the window.

    • A full description of a file the agent can already read nudges it to rewrite rather than patch (a distractor effect).
    • Description length does not predict the penalty; the authors attribute it to redundant content.

    Key findings

    • With the source withheld, optimized descriptions raise the mean test-pass fraction on issue resolution from 0.08 (issue only) to 0.71, against 0.21 for baseline descriptions.
    • With the source present, on full SWE-ContextBench Lite (58 paired tasks), issue alone resolves 33, retrieved context 30 and the compact description 29 (McNemar p=0.22 and p=0.25).
    • Longer documentation does worse: with Gemini 3.1 Pro on django Kind-B, issue alone resolves 9/15, compact 8/15 and the full optimized description 4/15.
    • The positive control shows the setup can detect a gain: retrieved context resolves 15 vs 14 of 29 django tasks.
    • Roundtrip fidelity tracks description density (Pearson 0.88 across 11 fixtures).
    • Completeness, not length, decides success: descriptions with 1, 3 or 5 of 5 facts yield exactly 1, 3 and 5 correct.

    Notable quotes

    The description’s only reliable effect is that its presence in the prompt occasionally pushes the agent to rewrite a file it would otherwise have edited minimally, breaking tasks the issue alone resolves.
    A tool that documents what the code does cannot supply a contract the code does not exhibit, which is exactly the information an agent needs here.
    Editing steered by a description pays exactly when the code is much larger than its description, which is rare for a single file and is the normal situation at repository scale.
    The optimizer had no access to our hand analysis of failure modes, so the agreement between the failures we catalogued and the fixes it discovered is independent evidence that the improvements are genuine.

    Limitations

    • The roundtrip benchmark is small (11 sympy fixtures plus 3 hand-built codebases) in a single language and project family; the optimizer is a proof of concept with 3 training and 2 held-out fixtures.
    • The largest source-present run uses one economical model and one summary length (about 80 words); stronger-model replications cover only django subsets, and attrition is not perfectly random.
    • The benchmark needs a capable regenerator: two open-weight models scored zero on every fixture because they hallucinated imports. Contamination controls reduce but cannot rule out memorization.

    Open questions

    • Does the source-withheld benefit carry over to repository scale, where whole codebases do not fit in context?
    • Would documentation aimed at the specific issue, or carrying only contracts and intent the code does not show, beat the issue alone even when the source is present?
    • Can agent harnesses avoid the rewrite-instead-of-patch distractor effect that redundant full descriptions cause?
