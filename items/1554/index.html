    Memory–Skill Isomorphism: One Skill Carrier, Two Native Uses

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-16

    Source: arxiv · 2026-09-15
    Link: https://arxiv.org/abs/2609.16669

    A deployed single-system audit argues agents do not need a separate memory subsystem: distilled memory can be an ordinary Agent Skill sharing the same progressive-disclosure read path as capability skills, while writes must stay forked (append-only history vs. rewrite-and-revalidate current state) — and the audit shows only 1 of 4 write entry points is actually governed.

    Executive summary

    Kang Ruiyuan (X32 Studio) claims a definitional isomorphism between memory and skill carriers: five memory read requirements map bijectively onto the native Agent Skills affordances (resident description L0, on-demand body L1, references L2), so the memory component is implemented literally as a Skill directory rather than a parallel memory service. Reads are shared; writes are not — historical evidence is appended while current indexes and procedures are rewritten and revalidated. The evaluation is a single-deployment audit with small, mostly underpowered batches: a selected-task availability signal, two null carrier comparisons against BM25, a first-turn context accounting favoring the resident index, and a write-governance audit finding 4 physical write entries with 1/4 ledger coverage. A preregistered description-only ablation found the body was never opened at all (0/16 opens), yielding a provisional 'Z-mixed' verdict.

    The isomorphism is a bijection on reads only

    A Skill exposes three disclosure levels: the resident description (L0), the body opened on demand (L1), and references read or searched on demand (L2). Both distilled memory and capability tiers use identical read operations. The paper is explicit that the isomorphism is finite and definitional and asserts nothing about shared write semantics, content, provenance, or lifecycle.

    • Memory Skill: description = hot cues/index; SKILL.md body = colder index + curation policy; reference/*.md = detailed cold memories with grep-style lookup
    • The deployment's controlled-write gate caps each resident description at 1,024 characters, forcing the hot index to be compressed and rewritten rather than accumulated
    • The cap belongs to the governed deployment, not to the Agent Skills specification
    • Raw outcomes and provenance stay outside the stack in an unmounted, append-only archive

    Why the write layer must fork

    Sharing discovery does not imply one update function. History must preserve provenance so it is appended; current procedures must track best-known state so they are replaced and revalidated. Design Rule 1 states two distilled tiers may share one disclosure stack when both re-enter decisions through a trigger–body shape, and each tier declares write invariants the fork preserves.

    • Falsifiability: a single append-only log with validated current-state projections is an instance of the framework, not a counterexample
    • No cross-implementation impossibility is claimed; the fork is a deployment-level requirement
    • The engineering claim becomes 'one auditable contract', not 'one update function'

    RQ1 — availability on a selected task (exploratory)

    On a selected delegation task, failure means omitting an explicit provider/model binding or the post-dispatch runner confirmation. Form A (rule in L0 plus full lesson in L2) gave 0/8 failures, Form B (narrative in L0, lesson only in L2) gave 1/8, against a same-day, non-concurrent historical floor arm of 6/6 failures. Fisher exact p = 0.00033 and 0.00466, unadjusted for multiplicity.

    • A vs B: -12.5 pp, p = 1.0 — no detected difference in writing form
    • Explicitly labeled a post-selection existence signal, not a confirmatory rate
    • The batch cannot separate cue-only from full-body effects

    RQ2 — resident Skill index vs BM25 retrieval

    A deployed 6-skill resident arm was compared with a 0-skill arm using unconditional top-k sparse BM25 injection every turn, on five tasks with paired seeds. Lesson application was 8/10 in both arms (Fisher p = 1.0; McNemar p = 1.0, 0 discordant). First-turn added tokens against a 1,462-token no-knowledge baseline were 1,313 for the resident index versus 1,365 / 3,980 / 4,949 for BM25 at increasing k.

    • Provider-reported batch cost: $0.09619 resident vs $0.12521 retrieved
    • Session prompt totals 1,218,713 vs 1,436,897 tokens
    • Knowledge-component characters differ hugely (268,576 vs 916,903), yet behavior does not
    • The arms differ by more than delivery — six real skills mounted vs zero
    • A voided second batch gave mean first-turn +1,522.8 resident vs +11,999.2 BM25, so the ratio is corpus-dependent

    RQ3 — migration, maintenance, and write governance

    The carrier migrates as plain files: 21 files / 177,321 bytes copied, 0 code lines changed, 0 service restarts. Behavior after migration was 0/8 vs 0/8, a double floor that cannot establish preservation. The content store grew +64% with 0/11 content changes touching harness code, while the machinery itself changed 15 times. The write-surface audit enumerates four physical entries — apply_change, facts_append, lesson_append, and bare write/edit — of which only apply_change records an expectation in the settlement ledger.

    • Ledger coverage 1/4; a bare file edit bypasses both the carrier gate and the ledger
    • Two payload snapshots disagree (177,321 vs 185,582 bytes), so no byte-identical claim is made
    • The 15-edit count traces to deployment history at commit 57ecad8dd3

    E1 — preregistered description-only ablation

    E1 compared a description-only arm against a full-resident arm (n = 8/arm, paired seeds) with the L0 text byte-identical and the L1 body the only permitted difference. Fail rates were 0/8 vs 1/8: -12.5 pp, Fisher p = 1.0, McNemar p = 1.0. Delivery was logged prospectively for the first time and recorded 0/16 body or reference opens before action, emptying the delivery stratum in both arms. Under the frozen zone table the verdict is Z-mixed (provisional).

    • Binding held in 100% of both arms; runner confirmation 100% vs 87.5%
    • Preregistration froze 2026-09-12T14:54:00Z with a three-item amendment
    • Sensitivity: dropping two read-visibility-flagged units gives 0/6 vs 1/8, verdict unchanged
    • Retained cascade dissociations refute a trigger–body causal reading

    Key findings

    • Write governance is the most complete identification in the paper: 4 physical write entries exist, but only 1/4 (apply_change) reaches the settlement ledger — a bare file edit bypasses both the 1,024-character description gate and the ledger.
    • First-turn knowledge cost: 1,313 added tokens for the resident Skill index vs 1,365 / 3,980 / 4,949 for BM25 at increasing k, against a 1,462-token no-knowledge baseline.
    • Behaviorally the carriers are indistinguishable: 8/10 lesson application in both arms (Fisher p = 1.0, McNemar p = 1.0, 0 discordant pairs); batch cost $0.09619 resident vs $0.12521 retrieved.
    • Availability, not carrier form, moved outcomes on the selected task: 0/8 and 1/8 failures with the lesson vs a 6/6 non-concurrent historical floor (p = 0.00033 and 0.00466, unadjusted, post-selection).
    • E1 recorded 0/16 body or reference opens before action, with fail rates 0/8 (description-only) vs 1/8 (full resident); verdict Z-mixed (provisional).
    • Portability is file-level: 21 files / 177,321 bytes copied, 0 code lines and 0 restarts, +64% content growth with 0/11 content changes touching harness code — but the machinery itself changed 15 times.

    Notable quotes

    Knowledge that never re-enters the decision context cannot change an action.
    The memory component is not a service beside the Skill system.
    Sharing a read carrier does not imply one write operation.
    The arms differ by more than delivery: the resident arm mounts six real skills while the retrieval arm mounts zero, so the comparison is a deployed system against a retrieval arm.

    Limitations

    • Single deployment, tiny samples (n = 6–10 per arm); the RQ1 task was selected on prior floor evidence and the floor arm was historical and non-concurrent.
    • Body delivery was uninstrumented in RQ1–RQ2, so a null cannot separate routing failure from a weak lesson; the only prospective instrument read zero opens.
    • The carrier comparison is against unconditional sparse BM25 only, and migration behavior is a 0/8 vs 0/8 double floor.

    Open questions

    • Does the shared carrier compound across repeated reflection cycles? The loop is implemented but compounding gain is unmeasured.
    • Can the three unledgered write entries be brought under one settlement contract without collapsing the append-vs-rewrite fork?
    • Where does the crossover lie against dense or conditional retrieval?
