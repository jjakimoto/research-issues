    VibeMemBench: Evaluating Memory Systems for Coding Agents on Real Repository Coding Tasks

    ← Go backAutoGym: Blueprint-First Generation of Verifiable Agent GymsNextSWE-Proof: Can Language Models Resolve Real-World Issues… →
    📰 Latest · 2026-09-22
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-22

    Source: arxiv · 2026-09-20
    Link: https://arxiv.org/abs/2609.23570

    The first benchmark that isolates a memory-on/memory-off toggle on executable repository coding tasks finds that repository history genuinely contains useful experience (frozen verified records lift Resolved by 1.1-4.5 points and cut agent steps on all five solvers), yet four production memory systems fail to beat the matched memory-off baseline in 11 of 12 pairings. The dominant failure is record FORM — raw transcript volume — not retrieval coverage.

    Executive summary

    VibeMemBench turns memory evaluation into a matched paired comparison on real repository coding tasks: 111 targets from 90 SWE-rebench V2 repositories, 3,634 prior trajectories from the same repos, executable tests as the outcome, and only the declared memory condition varying between runs. A four-stage construction pipeline retains a target only if some injected history experience verifiably raises its executable outcome under a reference solver. Transferring that frozen verified experience to five held-out solvers gives +1.1 to +4.5 points Resolved on four of five and fewer agent steps on all five. But when Mem0, SimpleMem, MemoryOS and A-MEM must construct and retrieve from the same history, 11 of 12 pairings land at or below the memory-off baseline; 69.3% of losses are form degradation.

    Task construction and the 111 targets

    Targets are built from SWE-rebench V2 via four filtering stages: patch validation, oracle-assisted offline patch-pattern screening (only earlier instances from the SAME repository), history execution plus target-aware experience distillation, and retention by verified uplift. Each distilled experience records a bug class, root cause, fix pattern and reusable lesson, and never sees the target gold patch, test patch or test outcome.

    • 111 targets across 90 repositories, 3,634 completed history trajectories, nine languages concentrated on Python
    • Not a bug-repair slice: bug fixes are under a third of primary task types
    • Retention rule: keep a target only if the memory-off reference resolved share < 1 AND the best candidate combination has positive uplift
    • Reference setting: deepseek-v4-flash + MiniSWEAgent, four seeds per condition
    • The reference uplift is reported as a selection audit, separate from transfer results

    The matched intervention protocol

    For a fixed agent configuration and a paired evaluation set of targets x seeds, the benchmark compares memory-off against memory-on. Only the declared persistence and retrieval mechanism may change.

    • Layer 1 (transfer): the frozen verified experience is injected directly into five held-out solvers - deepseek-v4-pro, glm-5, glm-5.2, kimi-k2.7-code, qwen3.8-max - four seeds each
    • Layer 2 (retrieval): Mem0, SimpleMem, MemoryOS and A-MEM ingest the full eligible prior history, then a declared target query selects ONE top-ranked experience
    • Retrieval happens BEFORE the target trajectory, so this is offline top-1 memory, not online closed-loop memory
    • Memory systems use deepseek-v4-flash for record extraction and Qwen3-Embedding-4B for embeddings
    • An irrelevant-memory control injects one fixed distractor passage with no software content

    Metrics

    The primary metric is Resolved, the share of target-seed runs whose declared test predicate passes; the paired effect is the memory-on minus memory-off difference. The uncertainty unit is the target.

    • Resolved over 444 target-seed runs per condition
    • 95% percentile bootstrap CI on the paired difference, 10,000 resamples at target level with seeds kept intact
    • Input and output tokens are solver-side only - memory-side token consumption is never recorded
    • Wall-clock time and API price are excluded because they vary with provider and pricing policy

    Results: availability versus use

    Direct injection helps modestly but consistently in direction; retrieval by existing memory systems nearly uniformly does not. All five transfer bootstrap intervals cross zero. The irrelevant-memory control sits 0.7 to 3.4 points BELOW memory-off.

    • Injection lowers agent steps for all five solvers and input tokens for four of five
    • kimi-k2.7-code gains most (+4.5) from a 69.8% baseline while deepseek-v4-pro gains nothing from 67.1%
    • Retrieval: 11 of 12 pairings at or below memory-off; no system interval lies above zero; the glm-5/Mem0 interval lies entirely below it
    • The one exception, MemoryOS on glm-5 (+2.0), still trails the frozen verified experience
    • A Mem0 retrieval-budget dose curve stays below memory-off at every budget from one to five records

    Why it breaks: headroom and record form

    Two mechanisms explain the gap. First, solver headroom: across 1,332 retrieval pairings the net effect is a loss of 127 resolved seeds, and in 42.0% of pairings a 4/4 memory-off ceiling leaves an injected record able only to lose seeds. Second, record form: a 231-pairing diagnostic cohort attributes 69.3% of failures to form degradation.

    • Of 444 target-system pairs reaching both deepseek-v4-pro and kimi-k2.7-code, 118 move both solvers and 64 move them in OPPOSITE directions; in 61 of those the lower-baseline solver gains
    • Opposite-sign share rises with the memory-off gap: 0.0% at 0 seeds, 52.3% at 1, 75.0% at 2, 85.7% at 3+
    • A headroom-only rule predicts sign on 56.5% of 641 sign-changing pairings versus 52.4% for a content-only rule
    • Transcript systems (MemoryOS, A-MEM) produce every case of instruction pollution and shell noise; atomic systems account for all overgeneralization and schema omission
    • Injected records average 65 lines against a four-field frozen record
    • Counterfactual bound: substituting the frozen verified experience recovers 196 seeds over the 160 form-degradation pairings
    • When a solver fails without memory and the record carries a directory or identifier anchor, injection raises Resolved on 55.2% of such pairings with no observed loss

    Key findings

    • Direct injection of a verified prior experience raises Resolved on four of five held-out solvers by 1.1 to 4.5 percentage points and lowers agent steps on all five; all five bootstrap CIs cross zero.
    • Eleven of twelve solver-system retrieval pairings fall at or below the matched memory-off baseline; the only gain is MemoryOS on glm-5 at +2.0 points, and the glm-5/Mem0 CI [-10.59, -0.45] lies entirely below zero.
    • The irrelevant-memory distractor control sits 0.7 to 3.4 points below memory-off on all three solvers that run it, ruling out generic added-context effects.
    • Failure attribution over 231 failing pairings: form degradation 69.3%, coverage miss 16.0%, use failure 13.4%, ranking miss only 1.3%.
    • A strip ablation recovers 0.60 seeds/pairing when flagged instruction-pollution lines are removed versus 0.48 when equally many random unflagged lines are removed, locating the harm in transcript volume.
    • Headroom dominates: across 1,332 retrieval pairings the net effect is -127 resolved seeds, 42.0% of pairings sit at a 4/4 memory-off ceiling, and of 64 opposite-sign solver pairs, 61 have the weaker-baseline solver gaining.

    Notable quotes

    The irrelevant-memory control stays 0.7 to 3.4 points below the memory-off baseline on each of the three solvers that run it, so injected text alone reproduces none of the gains.
    Eleven of the twelve solver and system pairings stay at or below the matched memory-off baseline, no system interval lies above zero, and the glm-5 and Mem0 interval lies entirely below it.
    Because random deletion recovers comparably, the harm operates through transcript volume rather than instruction semantics, and the lexical pollution flag marks a bulky record rather than a failure mechanism.
    Injection should be gated on expected solver headroom rather than applied uniformly.

    Limitations

    • Selection bias by design: all 111 targets have positive reference uplift, so the benchmark measures the downstream value of known transferable experience rather than how often a deployed agent finds such a pair.
    • Statistical power: with 111 targets all five transfer bootstrap intervals cross zero; retrieval is offline top-1, not online closed-loop memory.
    • Scope: the solver pool omits proprietary frontier models, memory-side token consumption is never recorded, and the language mix concentrates on Python.

    Open questions

    • Would a memory system that compresses a retrieved trajectory down to the span stating the fix close the availability-to-use gap?
    • How should a harness estimate solver headroom at runtime in order to gate injection?
    • What extraction schema retains not just a fix field but the constraints anchoring a fix to the target?
