    Agent Skill Evolution: How Revisions Affect Coding Agents

    📰 Latest · 2026-10-06 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-06

    Source: arxiv · 2026-10-04
    Link: https://arxiv.org/abs/2610.04832

    The first large study of how SKILL.md revisions change agent behaviour. Adding a concrete rule that names a command or path the Skill did not mention before raises single-answer compliance by +0.41 and the rate at which sandbox agents take the required action by +0.23, with no detectable extra tokens per agent episode. Two caveats: on-demand Skill loading keeps only about half that gain, and about 1 in 5 rule-model pairs adds tokens with no measurable benefit.

    Executive summary

    The authors rebuilt git histories for 3,159 SKILL.md files in 856 repositories (taken from the SkillMD-138K snapshot) and compared each Skill's first and last versions (2,608 pairs). They first describe how Skills co-evolve with harness files like CLAUDE.md and AGENTS.md. They then turn added or deleted 'directives' (imperative lines that name a backticked command, path or identifier) into 396 probes and an 80-task executable sandbox. These are run under three conditions: no body (name and description only), the old body, and the new body. They test 16 open-weight models, 5 closed models (Claude Sonnet 3.5/3.7/4.5, Haiku 4.5, GPT-5.5) and 4 mini-SWE-agent agents. An added rule reliably raises compliance and agent actions, and the gain comes mostly from tokens new to the Skill. Deleting a rule lowers compliance about three quarters as much as adding one raises it. A revision costs input tokens in single answers but nothing detectable per agent episode, while carrying a Skill body at all adds 37-57% tokens per episode. This is an arXiv preprint (v1, cs.SE) with no peer-review venue stated.

    Problem and framing

    Skills are revised like code, but earlier evaluations compare a Skill against having no Skill, at a single version. This paper measures what one revision does to an agent. A revision is the cumulative change from the first to the last observed version of a Skill, a median of two revision commits apart. A 'rule change' is a revision that adds or deletes a mechanically checkable directive naming a command, path or identifier. The estimand is the new-minus-old difference on the same probe and model. Confidence intervals come from a repository-clustered bootstrap (4,000 resamples) with Holm correction.

    • RQ1: how do Skills co-evolve with harness configuration (CLAUDE.md, AGENTS.md, .claude/, Copilot instructions, MCP config, plugin manifests)?
    • RQ2: effect on effectiveness at three levels. L1 is string-checked directive compliance in one answer, L2 is whether an executing agent takes the required action, and L3 is final artifact correctness (automated check plus blind human judges).
    • RQ3: effect on cost. The marginal cost of a revision is new minus old. The carrying cost of a Skill body is old minus none (name and description only).
    • Models ran without thinking modes. Qwen 3/3.5 thinking was disabled and GPT-5.5 reasoning effort was set to none. Single-step prompts were capped at 8,192 tokens of usable input.

    Dataset and RQ1: Skills change with their harness

    The authors sampled 1,500 repositories from SkillMD-138K (7,959 SKILL.md files) and followed each file with git log --follow. 40% had at least two versions. Consecutive versions are a median of under three days apart. 60% of revised Skills end longer, but median net growth is only +18 words. Commits that revise a Skill change harness files more often than size-matched commits in the same repository.

    • 55.0% of the 2,608 revisions add or delete a MUST/NEVER constraint, a conditional rule or a numbered step. 19% change only examples or code, and 14% change only prose.
    • Executable surface grows from a small base: +0.44 repository paths, +0.25 shell commands and +101 words per Skill. Density per 1,000 words shows no detectable change.
    • Matched on repository and files changed, 23.0% of Skill-revision commits touch harness config versus 18.5% of other commits (+4.5 points). The excess comes from CLAUDE.md (+2.1), AGENTS.md (+2.0), other agents' config such as Cursor and Codex (+1.9), and Claude Code agent and command definitions (+1.4 each). Settings, hooks and MCP config do not change more often.
    • Skill-creation commits change harness config in 36.7% of cases versus 21.8% matched (+14.8 points).
    • 37.6% of revision commits carry an AI-agent or bot signature, versus 40.5% of other commits. Only 0.4% of commit subjects name a model version.

    Method: probes, conditions, models, sandbox

    Directives are extracted by regex, at most three per Skill. Qwen 3.5-27B writes a realistic user request that needs the directive without mentioning it, plus the strings a compliant answer must or must not contain. A response complies if its code spans contain every required string. The grader's precision is 0.97-0.98 and its recall is 0.73-0.82 against two blind annotators. Re-weighted human labels give a larger gain (about +0.52) than the string check (+0.41). The sandbox benchmark has 80 tasks from 57 repositories and runs the unmodified mini-SWE-agent scaffold (twelve steps, no network).

    • Probe sets: 396 added-directive probes (main set N=300, run on all 16 open models), 245 deleted-directive probes, and 1,349 dilution probes built around an unchanged directive.
    • Open models (3.8B-32B): Qwen 2.5/3/3.5, Phi 3/3.5/4-mini, Mistral 7B v0.2/v0.3, Llama 3/3.1-8B, OLMo 2/3-7B, Gemma 2-9B. They are arranged in generation ladders so that comparing generations never mixes vendors.
    • Sandbox agents: Qwen 3.5-9B, Qwen 3.5-27B, Devstral-Small-2507 and Claude Sonnet 4.5, all under mini-SWE-agent. Neither Claude Code nor the Codex CLI was tested.
    • Controls: old version plus only the rule line, new version minus the rule line, old version plus unrelated text of equal length, old version plus one sentence that names the token without stating a rule, and requests that do not need the rule.
    • On-demand loading: only the name and description go in the prompt, and the body sits at its path in the checkout. The sandbox shows only the first and last 2,000 characters of any command output.

    Results: single answers and agents

    All 21 models follow an added rule more often. Across the 16 open models the gain is +0.41. On the 147-probe subset, the five closed models gain +0.42 to +0.45. In the sandbox every agent takes the required action more often (+0.23 on average). The gain is concentrated in tokens the old Skill never mentioned, and it shrinks in long contexts and under on-demand loading.

    • A new token lifts compliance by +0.51 to +0.66 from an old-version baseline of 0.05. A token already in the old Skill starts at 0.61 and gains only +0.08.
    • Stating the rule adds +0.15 beyond a sentence that only names the token. Unrelated text of the same length has no detectable effect. Revisions that change only prose or examples move compliance with existing rules by just +0.017.
    • A new rule leaks a little into requests that do not need it: the token is used +0.02 to +0.06 more often there, versus +0.38 to +0.45 where it is needed.
    • The benefit falls with Skill occupancy, from 0.424 when the Skill takes a small share of the context window to 0.270 when it fills three quarters of it. Inside realistic agent contexts, about 3/5 of the short-answer gain survives at about 15k tokens and about 2/5 at about 40k.
    • Older and newer model generations gain similarly. No difference is significant after Holm correction, and the data-derived bound is 0.077 (0.062 along the Sonnet ladder).
    • Agents that read the rule do not always act on it. Once the rule was displayed, Sonnet 4.5 acted in 88% of episodes and Qwen 3.5-27B in 61%. The gap appears with the body preloaded too (81% vs 62%).
    • Stale references are not the explanation. On the 62 tasks where everything the old Skill names still exists, the action gain is +0.22, versus +0.23 on all 80 tasks.

    Cost and guidance for Skill maintainers

    In a single answer, a revision adds 18-19% input tokens and slightly shortens the output, because a model told which command to run hedges less. Total tokens per request rise 17% on open models and 24-27% on the four Claude models. Local latency drops 1.6-7.2% because decoding dominates. In agent episodes, a revision changes tokens by -2.3% to +3.0% (every 95% CI spans 0, and an increase above about +12% is excluded) because agents take fewer steps. Carrying the Skill body at all costs +37% to +57% per episode (50% on average).

    • Overhead candidates: in 20% of rule-model pairs the prompt grows with no detected compliance change. Of the 55 rules that most models classify as overhead, 27 are already followed without the rule and 28 are ignored whether present or not. The authors say the first group needs controlled removal tests and the second needs rewriting.
    • A revision that changes a rule or procedure adds a median of +248 tokens. A prose-only revision adds +6.
    • Only about 25% of later in-scope commits actually need an added rule (95% CI 14-40%). That implies roughly +0.10 single-answer compliance (0.25 x 0.41) and +0.06 agent action (0.25 x 0.23) per in-scope request, while every request pays for the added tokens.
    • The authors' three practices: add a rule when it gives the agent information the Skill lacks; before deleting a rule, confirm the agent should stop following it; size a Skill for the smallest model that will read it.

    Key findings

    • 55% of the 2,608 Skill revisions change a rule or procedure. Skill-revision commits touch harness config more often than size-matched commits (23.0% vs 18.5%), mostly CLAUDE.md (+2.1 points) and AGENTS.md (+2.0 points).
    • An added rule raises single-answer compliance on all 21 models: +0.41 on average across 16 open models and +0.42 to +0.45 for the five closed models (Claude Sonnet 3.5/3.7/4.5, Haiku 4.5, GPT-5.5). Almost all of the gain comes from tokens new to the Skill (+0.51 to +0.66), versus +0.08 when the old Skill already named the token.
    • In the mini-SWE-agent sandbox the required-action rate rises +0.23 on average (Devstral +0.36, Sonnet 4.5 +0.19). Blind-judged final correctness rises +0.10 pooled over the three judged agents. Sonnet 4.5's +0.06 is not significant.
    • Under on-demand loading (only name and description in the prompt) the four agents keep about 51% of the action gain and the three open models about 38%. Sonnet 4.5 keeps its full +0.19.
    • Deleting a rule lowers compliance with it by 0.27-0.33 on each of eight models, about three quarters of what adding one gives. Deleting a replaced rule costs -0.58, while deleting a duplicate costs only -0.12.
    • A revision adds 18-19% input tokens per single answer but no detectable tokens per agent episode (-2.3% to +3.0%). Carrying a Skill body adds 37-57% per episode. 20% of rule-model pairs add tokens with no detected compliance gain.

    Notable quotes

    Adding only the rule line to the old Skill gives about two thirds of the full effect.
    Before deleting a rule, check that the agent should no longer follow it, since deletions are followed too.
    With the body in the prompt the two act on the rule in 81% and 62% of episodes, so the gap is not specific to on-demand loading.
    Settings, hooks and MCP configuration change about as often as in other commits, and plugin manifests no more often.

    Limitations

    • Only concrete, string-checkable rules are covered. The literal filter keeps 17% of candidate directives and under-represents prohibitions, conditional rules and permission guardrails. The string check also credits mere token exposure, and the automated final check agrees with humans only moderately (kappa 0.50-0.55).
    • The setup is narrow: small open models (3.8B-32B), closed models from just two vendors, no reasoning or thinking modes, and a single research scaffold (mini-SWE-agent with 2,000-character output truncation) rather than Claude Code or Codex. The Sonnet 4.5 correctness estimate is underpowered (72 pairs, power about 0.5).
    • This is a non-peer-reviewed arXiv preprint. The main corpus has no repository above 375 stars (a separate high-star set has 146 repositories above 1,000 stars), and probes were generated by Qwen 3.5-27B, which gives Qwen models a slight advantage (+0.04).

    Open questions

    • Do the gains, and the about-half retention under on-demand loading, hold in production harnesses like Claude Code and the Codex CLI, which display whole files, and with reasoning models?
    • What is the net effect of a revision on natural task streams, given that only about 25% of later in-scope commits need the added rule while every request pays for its tokens?
    • Could a pre-merge check that runs a revision's probes reliably flag rules that add tokens without any gain, and can behaviour-based graders evaluate prohibitions and permission guardrails?
