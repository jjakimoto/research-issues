TRUSS: Towards Task-Reliable and User-Safe Automated Agent Skill Generation

📰 Latest · 2026-08-19
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-19

Source: arXiv (cs.AI, cross-listed cs.SE) · 2026-08-19
Link: https://arxiv.org/abs/2608.17588

Direct LLM judgment catches only 19.05% of malicious agent-skill artifacts; adding structured static inspection plus brokered sandboxed execution takes detection to 100% on their benchmark and lifts generated-skill task effectiveness from 17.11% to 52.94%. The interesting part for anyone auto-generating Claude-style Skills is that the dangerous behavior is a chain of individually plausible steps, invisible to artifact inspection.

Executive summary

TRUSS is an evidence-guided framework for generating agent Skills — reusable natural-language procedures bundled with executable resources — that treats the generated artifact as untrusted until both statically inspected and observed executing. Candidates are checked against source and domain evidence and screened for nine safety properties; survivors are loaded by a shadow agent inside a Controllable Execution Environment where every requested action passes a policy broker and is logged with provenance. Failures trace back to the responsible Skill content to drive refinement. Across three benchmarks it reports perfect detection of injected artifacts, roughly halved attack success with zero attack regression, and simultaneous large gains in task effectiveness and security — contradicting a simple safety-versus-capability trade-off in this setting.

Why artifact inspection is not enough

Skills typically execute with full local user privileges, and the paper's motivating example is an install fragment that is downloaded in one step and executed several steps later. Each step is individually plausible; only the chain is dangerous. That is the argument for runtime evidence over static review.

  • Two interacting goals: Functional Effectiveness (verified gain over the base agent, evaluated pairwise so previously-passing tasks are not broken) and Safety Reliability (no security-relevant behavior beyond authorized scope).
  • Effectiveness is defined as the expected utility of the trajectory with the Skill minus the empty-Skill trajectory.
  • The objective maximizes effectiveness minus a lambda-weighted mean of per-property violation risks.

Generator / Checker / Refiner loop

The generator emits a full package (instruction doc plus referenced executable resources), records regime and provenance, freezes the candidate, and assigns a content digest — so every revision is a distinct auditable object that must re-enter static checking from scratch.

  • Static inspection maps each claimed effect to a usage condition and a procedural span backed by source or open-world evidence; unresolved items convert into executable runtime obligations rather than being waved through.
  • Nine safety properties are scoped by reconciling declared behavior against implemented capabilities, with findings bound to exact artifact locations.
  • A Static Gate admits a digest only when static criteria are discharged and runtime obligations are well-specified.
  • The Refiner uses the Function and Safety Record as a revision specification, with satisfied entries acting as preservation constraints so utility and safety are traded off in a single edit.

The Controllable Execution Environment

Runtime checking happens in a disposable workspace with synthetic data, the Skill mounted read-only, host resources excluded, and per-scenario budgets. An Intermediate Breaker vets each action, and — importantly — blocked actions still appear in the trace and count as violations, so the environment measures intent rather than just outcome.

  • Networking is disabled; HTTP terminates at brokered mock services.
  • Events bind request to observation via call identity plus broker decision and causal parent, preserving provenance.
  • Synthetic canaries track protected data, and lifecycle observation extends through cleanup.
  • Nine properties spread across phases: Control Integrity, Access Boundary, Execution Integrity (static); Evidence Integrity, Authority Integrity (runtime); Lifecycle Isolation, Resource Boundedness, Composition Integrity, Transaction Safety (both).

Benchmarks and models

Three research questions map to three benchmarks: detection, repair under executable attacks, and end-to-end generation.

  • SkillInject: 84 injection templates yielding 84 matched pairs, 168 blinded artifacts.
  • SkillSafetyBench: 155 cases with official attack and task verifiers.
  • SkillGenBench: 187 tasks across three source types.
  • GPT 5.5 for generation and semantic inspection; GPT 5.4 mini for brokered execution when split. Harbor Codex agent for SkillSafetyBench; a Claude Code harness (via an Anthropic Messages to OpenAI Responses adapter) for SkillGenBench.

What the repair numbers actually say

Repair roughly halves attack success rate without ever creating a new attack, but the residual is substantial and the retained utility is strongly model-dependent — a 29-point gap in safe task completion between two executors of the same framework.

  • GPT 5.5: ASR 38.71% to 19.35%, 30 attacks eliminated, 0.00% attack regression, safe task completion 52.90%.
  • GPT 5.4: ASR 46.45% to 29.68%, 26 attacks eliminated, 0.00% attack regression, safe task completion 23.87%.
  • Raw task completion hides unsafe successes: 16 unsafe completions under GPT 5.5 and 25 under GPT 5.4, which is why safe task completion is the honest joint metric.

Key findings

  • Asking an LLM directly whether a Skill is dangerous is close to useless as a screen: 19.05% recall, 44.64% precision.
  • Structured static inspection recovers most of the gap (F1 87.36%), and brokered runtime execution closes the remainder — +18.45 pp precision and +5.95 pp recall on top of static.
  • Repair halved attack success with zero attack regression in both configurations, but 19–30% of attacks still succeed after repair.
  • Safety and effectiveness rose together in the generation setting (17.11% to 52.94% effectiveness, 50.80% to 100% security), contradicting a simple safety-capability trade-off here.
  • Executor model choice matters as much as the framework: a 29.03 pp gap in safe task completion between GPT 5.5 and GPT 5.4 under identical machinery.

Limitations

  • The 100% precision/recall and 100% Security figures are saturated results on matched-pair and probe-based benchmarks the authors constructed — that pattern usually signals a benchmark ceiling rather than a solved problem.
  • Runtime certification is explicitly sensitive to scenario coverage and executor behavior, so missing observer coverage leaves obligations unresolved rather than proven safe.
  • Component contributions are not separated: the LLM-generator versus TRUSS comparison bundles inspection, execution evidence, and refinement, and the ablation is deferred. The abstract also reports 38.71% where the introduction says 38.70%.

Open questions

  • How much of the perfect detection score survives against attacks not drawn from the authors' own 84 injection templates?
  • Which of the three components — static inspection, brokered execution, or refinement — actually carries the +22.99 pp effectiveness gain over a plain LLM generator?
  • Can the CEE's brokered-mock approach scale to Skills whose value depends on real network and filesystem effects, where synthetic scenarios cannot stand in?
