    Program Synthesis with Large Language Models

    ← Go backAutonomous synthesis of metastable materialsNextMeasuring Coding Challenge Competence With APPS →
    📚 Foundations · 2026-10-08 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-08

    Theme: Executable foundations for coding-agent evaluation
    APPS and MBPP helped establish execution against tests as the primary object of code-generation evaluation. Together they also expose why a pass rate is not a complete reliability measure: results depend on sampling budget, prompt choice, test completeness, human feedback, and whether the model understands execution rather than merely producing one lucky program.
    Source: arxiv
    Link: https://arxiv.org/abs/2108.07732

    Introduces MBPP and separates test-passing synthesis, interactive repair, and execution-level semantic grounding.

    Executive summary

    This paper introduces MBPP, a 974-task benchmark of short Python programs, and evaluates decoder-only Transformers ranging from 244M to 137B parameters by executing generated code against tests. The 137B model solved 59.6% of MBPP test problems with at least one of 80 few-shot samples, while fine-tuning on only 374 examples improved performance by roughly 10 percentage points across most model sizes. Human feedback raised the solve rate from 30% to over 65% after four interventions, but separate execution experiments never exceeded 29% accuracy, exposing a gap between producing test-passing code and tracking program semantics.

    Benchmark and evaluation contract

    MBPP contains 974 crowd-sourced tasks, each pairing a natural-language specification with a self-contained Python function and three correctness tests. The evaluation executes generated programs rather than relying on lexical similarity.

    • The main split reserves 10 problems for few-shot prompting, 500 for testing, and 374 for fine-tuning.
    • The authors also manually edited and verified a 426-problem subset to improve specification clarity and test accuracy.
    • For each MBPP test task, the synthesis evaluation draws 80 samples at temperature 0.5 and checks them for semantic correctness.

    Scaling, sampling, and test-based success

    Synthesis performance rises approximately linearly with the logarithm of model size, and fine-tuning supplies a roughly constant improvement in the fraction of tasks solved. Results also show that pass-at-many-samples can conceal low per-sample reliability and substantial prompt sensitivity.

    • The largest 137B model solved 59.6% of MBPP problems using few-shot prompting and 80 samples.
    • Ensembling prompt-example seeds increased the problems solved from 59.6% to 66.4%.
    • Among 50 tasks given adversarial challenge tests, 33 had solutions passing the normal tests but only 29 passed both sets.
    • Beam search performed poorly, while higher-temperature sampling became more effective as the sample budget increased.

    Interactive repair with human feedback

    The paper studies 50 edited MBPP problems in a dialog setting where participants provide up to four one-sentence natural-language hints. People often repair underspecified requirements, missing imports, identifier errors, and small logical mistakes, although the model increasingly loses track of earlier context over longer dialogs.

    • The solve rate rose from 30% initially to 55% after one intervention and to over 65% after four interventions.
    • Human feedback enabled solutions to 10 problems that the model could not solve without assistance.
    • One human correction was more effective than the reported five-sample, no-feedback baseline.

    Execution and semantic grounding

    To distinguish code generation from code understanding, the authors ask the 137B model to predict outputs of ground-truth MBPP programs under seven combinations of source code, natural-language descriptions, and examples. Example-rich prompts often outperform prompts containing unambiguous source code, indicating weak execution-level grounding.

    • Few-shot execution accuracy never exceeded 29% on a single held-out test case.
    • The strongest single-output few-shot conditions were code plus examples at 28.8% and natural language plus examples at 28.6%; code alone reached 16.4%.
    • Execution fine-tuning used 5,236 training instances and 1,260 validation instances.
    • Fine-tuning improved execution mainly when source code was present without test examples.

    Significance for coding-agent evaluation

    MBPP established an executable benchmark for natural-language-to-code systems while demonstrating why a single aggregate pass rate is insufficient. Coding-agent evaluation should report sample budgets and per-sample reliability, test beyond visible examples, assess interactive correction, and separately measure execution or state-tracking ability.

    • Functional tests are more meaningful than BLEU because semantically equivalent programs may have little token overlap.
    • Passing visible tests does not guarantee generalization, and rare outputs directly hard-code asserted cases.
    • Generation success with many attempts can coexist with poor ability to predict what a program actually does.

    Key findings

    • Executable functional tests reveal synthesis ability more faithfully than token-level similarity metrics.
    • Few-shot MBPP performance scales approximately log-linearly from 244M to 137B parameters.
    • Prompt selection, sampling strategy, specification clarity, and test completeness materially affect reported success.
    • Short natural-language feedback can more than double the cumulative solve rate, from 30% to over 65%.
    • Strong test-passing synthesis does not imply execution understanding: all evaluated execution conditions remained below 29% accuracy.

    Notable quotes

    For each problem in the test dataset, we use temperature sampling (with temperature 0.5) to generate 80 samples of code and then execute the code contained in the samples against tests for semantic correctness.
    Counting all four dialog turns, the fraction of problems solved is increased from 30% to over 65%, and counting only one, from 30% to 55%.
    Overall execution performance is relatively poor, with accuracy never exceeding 29% for any prompt type.
    This suggests that models are in some sense not really “reading” the source code and using it to execute.

    Limitations

    • MBPP programs are short and simple, and the models disproportionately solve the shortest and simplest tasks.
    • Many nominally solved tasks have only one or two successful outputs among 80 samples, making results dependent on large sampling budgets.
    • Visible tests can be incomplete or exploited, while the models remain poor at predicting program outputs and can lose dialog context.

    Open questions

    • Can training on larger and more detailed execution traces produce transferable semantic understanding?
    • How should coding-agent benchmarks control for sample budget, prompt selection, weak tests, and hard-coded test-case overfitting?
    • What interaction mechanisms can preserve context and make human corrections reliable over longer coding dialogs?
