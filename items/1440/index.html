Large Language Models as Tool Makers

📚 Foundations · 2026-09-11 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-11

Theme: Agents That Create Reusable Tools
These papers treat executable tools as procedural memory: an LLM abstracts a task family into code, separates tool construction from application, executes the artifact, and reuses it on later instances. Their gains establish the value of transferable executable abstractions, but their small validation sets and narrow benchmarks leave lifecycle reliability largely unresolved.
Source: arxiv
Link: https://arxiv.org/abs/2305.17126

Introduces a create-verify-wrap-cache-use pipeline in which expensive tool synthesis is amortized across repeated calls by cheaper agents.

Executive summary

LATM is a closed-loop framework in which a capable LLM creates reusable Python tools and a potentially cheaper LLM invokes them on subsequent instances. Its one-time tool-making cost can be amortized across many requests, forming a functional cache keyed by task capability rather than textual similarity. Across six reasoning tasks, GPT-3.5 Turbo using GPT-4-generated tools substantially outperformed GPT-3.5 chain-of-thought prompting, while a lightweight dispatcher identified cached tools or unseen tasks with roughly 95–96% accuracy.

Problem and objective

Tool-augmented LLM methods depend on suitable tools already existing, while repeatedly asking a powerful model to solve every instance is expensive. LATM tests whether an LLM can instead create a generic executable tool once and delegate its repeated use to a cheaper model.

  • The target is recurring task families rather than a separate program synthesized for every instance.
  • Tools are Python utility functions intended to capture reusable algorithmic functionality.
  • The paper frames reusable tools as a functional cache that generalizes beyond caches of natural-language responses.

Tool-making and tool-using method

A tool maker proposes, verifies, and wraps a Python function; a tool user then converts new natural-language inputs into function calls. The experiments use three task demonstrations, three validation samples, and at most three retries in both proposing and verification.

  • Tool proposing follows programming by example and feeds execution errors back into the model after failed attempts.
  • Tool verification generates and executes unit tests; failures lead the model to repair function calls in the tests, not the proposed function itself.
  • Tool wrapping packages the function with examples of converting questions into calls, enabling in-context use by the cheaper model.
  • The principal configuration uses GPT-4 as tool maker and GPT-3.5 Turbo as tool user.

Functional cache and dispatcher

For a stream of heterogeneous requests, a lightweight dispatcher compares each request with cached function APIs. It routes cache hits to the tool user and treats misses as novel tasks whose examples can be accumulated until a new tool is created.

  • Cached entries represent functionality rather than textually similar answers.
  • A cache miss may initially be solved by a powerful model or human labeler.
  • GPT-3.5 Turbo served as the dispatcher in the reported experiments.

Evaluation and results

The evaluation covers Logical Deduction, Tracking Shuffled Objects, Dyck Language, Word Sorting, Chinese Remainder Theorem, and a generated Scheduling Meeting task. Each dataset contains 3 training, 3 validation, and 240 test instances.

  • GPT-3.5 Turbo with LATM improved over its chain-of-thought baseline on all six tasks, with gains ranging from 13.3 to 100.0 percentage points.
  • The dispatcher selected the appropriate existing tool with 95% ± 2% accuracy and decided whether tool-making was required with 96% ± 3% accuracy.
  • GPT-4 produced verification-passing tools more reliably than GPT-3.5 Turbo on difficult tasks, although even GPT-4 succeeded in only 3/5 Logical Deduction and Scheduling Meeting trials.
  • Only 2 of 60 trials showed the tool maker correcting its mistakes using error messages.

Significance and boundaries

LATM demonstrates a division of labor in which expensive reasoning produces durable executable artifacts and cheaper models perform repeated invocation. The paper also makes clear that reliable autonomous tool creation, validation, safety, and adaptation remain open problems.

  • At the study's prices, one GPT-4 call cost more than 15 times one GPT-3.5 Turbo call, motivating amortization of the tool-making cost.
  • Reusing GPT-4-generated chain-of-thought traces did not reproduce the benefit of reusable executable tools.
  • The authors identify incremental refinement and upgrading of existing tools as a future direction.

Key findings

  • GPT-3.5 Turbo with LATM beat GPT-3.5 Turbo with chain-of-thought on every evaluated task, gaining 13.3–100.0 percentage points.
  • Tool creation required model capacity: GPT-3.5 Turbo failed all five trials on Logical Deduction, Tracking Shuffled Objects, and Scheduling Meeting, while GPT-4 succeeded in 3/5, 4/5, and 3/5 trials respectively.
  • The lightweight dispatcher achieved 95% ± 2% accuracy selecting cached tools and 96% ± 3% accuracy recognizing when new tool-making was needed.
  • LATM changes repeated serving cost from using the expensive model for every instance, O(nC), to a one-time expensive tool-making cost plus cheap invocations, O(C + nc).
  • Transferring GPT-4-generated chain-of-thought traces was far weaker than transferring executable tools: LATM scored 79.7 versus 36.8 on Logical Deduction and 99.6 versus 63.2 on Tracking Shuffled Objects.

Notable quotes

The tool-making stage, including tool proposing, verification, and wrapping, only needs to be performed once for each type of task.
Over five random constructions of the test set, the accuracy in correctly determining the suitable tool is 95% ± 2%.
We observe that using CoT from a large model has a similar or even worse performance than human-written CoT, which is much worse than LATM.

Limitations

  • The evaluation uses only six narrowly structured reasoning tasks, five from Big-Bench and one synthetically generated; the authors note a lack of high-quality datasets representing authentic recurring human-computer interactions.
  • Tool reliability and generalization remain weak: verification uses only three validation examples, does not repair the function itself, and tool generation frequently fails on harder tasks.
  • The study does not address control and safety issues in depth, and accumulated tool-making history can encounter context-length constraints.

Open questions

  • How can a tool maker incrementally refine or upgrade an existing tool when new problem instances expose missing behavior?
  • What validation, sandboxing, and governance mechanisms can ensure that autonomously generated tools are correct and safe in real-world deployments?
  • How well does the functional-cache architecture perform over long-running streams with distribution shifts, overlapping task families, and evolving tool repositories?
