    CodePlan: Repository-level Coding using LLMs and Planning

    ← Go backMASAI: Modular Architecture for Software-engineering AI…NextDeep Reinforcement Learning in Quantitative Algorithmic… →
    📚 Foundations · 2026-09-28 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-28

    Theme: Planning and modularity for repository-scale coding
    Repository-level coding requires more than generating an isolated patch. CodePlan uses dependency-aware planning to propagate edits through a codebase, while MASAI separates testing, reproduction, localization, repair, and ranking into specialized modules; both make context selection and executable feedback first-class architectural components.
    Source: arxiv
    Link: https://arxiv.org/abs/2309.12499

    A foundational hybrid architecture that combines LLM-generated local edits with incremental dependency analysis and adaptive planning to propagate changes across an entire repository.

    Executive summary

    CodePlan formulates repository-level editing as an online planning problem: an LLM edits bounded code fragments, while incremental static analysis discovers dependent blocks that may also require changes. It maintains both a repository dependency graph and an evolving plan graph, supplying each edit with spatial context from related code and temporal context from causally preceding edits. Across six C# migration and Python temporal-edit tasks, the authors report that CodePlan reached a valid repository state on five tasks, while oracle-guided repair baselines reached none, although the small and partly proprietary evaluation limits generalization.

    Problem and formulation

    Repository-wide migrations and related edits cannot be treated as independent local generations because one seed edit can create transitive obligations across files. CodePlan takes a repository, seed edit specifications, a correctness oracle, and an LLM, then seeks a chain of derived edit specifications that leaves the repository valid under that oracle.

    • Seed specifications may be natural-language instructions or initial code edits.
    • Derived specifications identify dependent code blocks whose consistency may be affected.
    • The oracle can be a build, static checker, type system, test suite, or verification tool.

    Incremental analysis and adaptive planning

    A dependency graph records syntactic and semantic relations such as containment, imports, inheritance, overrides, calls, object construction, and field use. After every LLM edit, CodePlan classifies atomic modifications, additions, and deletions; incrementally updates the graph; applies change-may-impact rules; and extends a directed acyclic plan graph with newly affected blocks.

    • Plan nodes contain a code block, an edit instruction, and pending/completed status.
    • Cause-labelled plan edges preserve why one edit obligation followed another.
    • Incremental updates preserve relationships that a fresh static snapshot might lose after names, signatures, or imports change.

    Contextualized execution loop

    For each pending obligation, CodePlan extracts the target block plus a sketch of its enclosing class, gathers spatial context from the dependency graph, and gathers temporal context by linearizing causal paths through prior edits. The LLM returns a localized replacement, which is merged into the repository before analysis and planning repeat; once the plan is exhausted, oracle diagnostics become seed specifications for another iteration.

    • Spatial context exposes related declarations and call or class relationships.
    • Temporal context includes before/after fragments and the dependency relation that caused the current obligation.
    • The implementation uses tree-sitter-based custom analysis for C# and Jedi for Python, with GPT-4-32k as the principal edit model.

    Evaluation design

    The study evaluates three C# migration repositories and three Python temporal-edit repositories, spanning 4–168 files and 1,874–20,413 lines of code; the target commits changed 2–97 files. Build-Repair and Pyright-Repair use the same spatial and temporal contextualization as CodePlan but obtain edit locations reactively from compiler or checker diagnostics, isolating adaptive planning as the principal difference.

    • Block metrics count matched, missed, and spurious edited blocks.
    • Edit quality is measured with file-level Levenshtein distance and Diff BLEU over changed hunks.
    • The C# oracle is a successful build; the Python oracle is Pyright plus correctness against the target edit.

    Results and significance

    CodePlan passed all three migration tasks and two of three temporal-edit tasks, whereas the oracle-guided baselines passed none. It handled changes that did not trigger build or type errors—such as a new optional argument or a newly required dictionary key—because may-impact analysis still exposed callers to the LLM. The context ablation on Int-1 degraded from a perfect repository match to 30 missed and 54 spurious blocks after three iterations, showing that planning alone is insufficient without causal and structural context.

    • On Int-1 and Int-2, a second oracle-driven iteration repaired erroneous LLM edits without changing CodePlan's already-perfect block localization.
    • On Ext-1, CodePlan matched all 58 required blocks and achieved Diff BLEU 1.00; Build-Repair missed six blocks.
    • Replacing GPT-4-32k with Coeditor retained the planning architecture but missed one location on each of T-2 and T-3, indicating that local edit-model capability still matters.

    Key findings

    • Repository-scale coding can be decomposed into bounded LLM edits while static analysis carries responsibility for discovering and propagating cross-file obligations.
    • Reactive compiler or type-checker repair misses behaviorally necessary edits that do not violate an oracle; dependency-guided may-impact analysis exposes those locations proactively.
    • CodePlan produced valid outcomes on five of six evaluated repositories, compared with zero for the oracle-guided baselines using the same contextualization machinery.
    • Spatial and temporal context were essential: removing both on Int-1 changed a perfect result into 30 missed blocks, 54 spurious blocks, Diff BLEU 0.51, and 69 oracle errors after three iterations.
    • The planning framework can use another local edit model, but Coeditor's weaker context interpretation reduced edit-site coverage and edit similarity on two temporal-edit tasks.

    Notable quotes

    The existing techniques assume that the next edit location is provided by the developer and do not account for the effect of an edit on the dependent code.
    An LLM can be provided a code fragment and an instruction to edit it in a prompt.
    As code generated by the LLM is merged, the dependency relations associated with the code at the change site are re-analyzed.
    Once all the nodes in the plan graph are marked as completed and no new nodes are added, an iteration of repository-level code edits is completed.

    Limitations

    • The approach depends on accurate static dependency analysis; dynamically typed code and dynamic dispatch, data-flow, algorithmic, concurrency, and distributed-execution dependencies remain difficult or unsupported.
    • The evaluation covers only six repositories, two languages, and two task classes, includes two unavailable proprietary repositories, and manually preprocesses source and target repositories for stylistic uniformity.
    • CodePlan trusts individual LLM edits, updates one block at a time, and may not recover from incorrect or spurious generations even with repeated oracle-guided iterations; configuration, metadata, project, and external-dependency artifacts are also outside its current graph.

    Open questions

    • How can repository planning combine static graphs with runtime, data-flow, algorithmic, and execution dependencies without making analysis prohibitively expensive?
    • Can multi-block or transactional edit scheduling improve correctness and efficiency while preserving causal provenance and safe rollback?
    • How well do the reported advantages hold across larger public benchmarks, additional languages and repository artifacts, stronger modern edit models, and fully automated evaluation without manual normalization?
