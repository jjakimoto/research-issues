RepoAtlas: Guiding Coding Agents via Evolving Multimodal Repository Views

📰 Latest · 2026-09-17 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-17

Source: arxiv · 2026-09-15
Link: https://arxiv.org/abs/2609.16936

A training-free 'select-project-refresh' loop turns a repository code graph into an evolving paired visual+textual view for coding agents, lifting SWE-bench Verified resolve rates by up to 3.0 points while cutting input tokens, model calls, and API cost. It shows repository graphs help agents more as dynamic multimodal context than as static linearized text dumps.

Executive summary

RepoAtlas is a training-free module that maintains an evolving, budgeted multimodal view of a repository code graph for LLM coding agents working on issue resolution. It selects a task-relevant connected subgraph (15 nodes / 20 edges) using lexical, semantic, and trajectory evidence fused by node-wise max plus personalized PageRank propagation, projects it into aligned visual topology and a source-grounded textual index, and refreshes it only when the agent's exploration state (Localize / Edit / Test) makes the view stale. On all 500 SWE-bench Verified instances across three models it beats mini-SWE-agent, LocAgent, and SeeRepo on resolve rate while using the fewest input tokens and model calls.

Problem: repository context is either flat text or a stale picture

Repository-level issue resolution requires an agent to localize root causes across interdependent files from an issue report that rarely names them, in repos that exceed the context window. Code graphs expose non-local relations, but existing systems linearize them into text, leaving topology implicit. Rendering the whole graph fails too: VLMs become unreliable beyond a few dozen nodes, and a one-shot local view goes stale as exploration proceeds.

  • Three design questions: which graph region to expose, how to project it across modalities, and when to update it.
  • Prior work: text code-graph agents (CodexGraph, RepoGraph, LocAgent) have selection but no visuals; VisualCoder/DynamicGTR/GraphVista are visual but not repo-conditioned; SeeRepo lacks adaptive projection and auto refresh.
  • RepoAtlas is the only entry with all five properties, and is training-free — the base model is unchanged.

Method: select - project - refresh over an offline code graph

A directed typed graph is built once per repository snapshot (modules, classes, callables, variables; containment, inheritance, calls, imports, overrides, symbol use; tree-sitter / PyCG lineage). Each node stores qualified name, signature, and exact source location. Agent interaction is summarized as an exploration state of recently inspected files, relevant entities, the last view, and a phase in {Localize, Edit, Test}.

  • Selection: per-node direct relevance is the node-wise MAX of lexical, semantic, and trajectory evidence — a 'precision-preserving fusion' so several weak signals cannot outvote one strong exact match.
  • Propagation: personalized PageRank over an edge-type-weighted transition matrix, with final relevance the max of direct and propagated scores.
  • Structure: an argmax over connected candidate regions under budget, using supernodes; each supernode does 'representative exposure' of its highest-scoring member with an exact source location.
  • Projection: picks view form, layout, label granularity, and modality allocation; stable reference keys tie visual elements to textual records, and projection never changes what was selected.
  • Refresh: reuse the last view if it still covers phase-relevant evidence. Only the current image is retained. On first substantive edit the system enters Edit and drops the visual channel.

Results: higher resolve, fewer tokens, fewer calls, lower cost

Evaluated on all 500 SWE-bench Verified instances (three runs per configuration) with Qwen3.6-35B-A3B, MiMo-V2.5, and Kimi-K2.5, plus 560 LocBench instances for selection quality. Budgets fixed at 15 nodes / 20 edges.

  • Top resolve rate and lowest input tokens and model calls on all three models: 63.1% / 68.0% / 72.4%.
  • Margins over the strongest baseline: +1.6 pts / -7.9% tokens / -8.2% calls (Qwen3.6); +1.1 / -4.9% / -2.3% (MiMo); +3.0 / -4.5% / -7.8% (Kimi). Per-instance API cost falls 6.9%, 2.9%, 2.4%.
  • Output tokens are the one metric where it does not uniformly lead.
  • It presents 2.43 views per instance on average. SeeRepo, being request-only, obtained at least one view in just 40.5% of instances in the authors' reproduction.
  • LocBench selection at matched budget beats fixed k-hop on FA@3 (0.336 vs 0.256), FA@5 (0.392 vs 0.320), and AC (0.494 vs 0.412).

Ablations and case studies

Six stage-wise ablations on SWE-bench Verified plus a selection study on LocBench, followed by one success and one failure case from sympy.

  • Refresh policy matters most: no refresh -4.7 pts; per-call refresh collapses resolve to 51.0% (-12.1 pts) with the highest token and call counts.
  • Modalities are complementary: removing the textual channel costs 3.9 pts; removing the visual channel costs 1.9 pts and raises input tokens 9.8% and calls 8.1%.
  • Removing the node budget costs 3.3 pts with essentially unchanged tokens/calls — budgeting controls visual density, not interaction cost.
  • Removing representative exposure is the biggest selection hit: FR 0.252 -> 0.102, AC 0.494 -> 0.343.
  • Success case sympy-18698: RepoAtlas opens the gold file at median step 2 vs 7, 47.5 vs 66.3 model calls, and resolves 3/3 runs vs 0/3 for SeeRepo.

Significance

The paper reframes repository context construction as an evolving view-maintenance problem rather than a retrieval problem, and shows that a purely inference-time module can simultaneously improve correctness and reduce cost — unusual, since most context-enrichment methods buy accuracy with tokens.

  • Gains hold across three VLM families and scales.
  • The explicit phase model operationalizes the finding that visual context helps localization but distracts during editing.
  • A practical harness design rule: bound the view, keep only the current image, keep exact source locations in a persistent compact textual index.

Key findings

  • Best resolve rate on all three models — 63.1% / 68.0% / 72.4% — with the fewest input tokens and model calls in each panel; per-instance API cost drops 6.9% / 2.9% / 2.4%.
  • Refresh timing dominates: per-call refresh collapses resolve to 51.0% with the highest token (1073.2K) and call (59.1) counts, while never refreshing costs 4.7 pts.
  • Visual and textual channels are complementary — dropping the textual index costs 3.9 pts; dropping the visual channel costs 1.9 pts and raises input tokens 9.8%.
  • Representative exposure is the biggest selection lever: removing it drops function recall 0.252 -> 0.102 and actionable coverage 0.494 -> 0.343.
  • Efficiency comes from bounded context: only 2.43 views per instance, keeping just the current image, versus LocAgent's 1.6-1.9x input tokens.
  • On sympy-18698, RepoAtlas opened the gold file at median step 2 vs SeeRepo's 7 and resolved 3/3 runs vs 0/3.

Limitations

  • The code graph is static, so runtime-registered dependencies are invisible — in the sympy-17630 failure case RepoAtlas never reached the gold file across eight runs, while a text baseline solved it once.
  • Evaluation is confined to SWE-bench Verified and LocBench (Python) with three VLMs; generality to other languages and repository-level tasks is untested.
  • Output tokens are the one metric RepoAtlas does not uniformly improve.

Open questions

  • Can static repository graphs be augmented with dependencies inferred from execution traces?
  • Which projection strategies generalize to structurally diverse repositories?
  • Do the gains transfer to repository-level tasks other than issue resolution, and to smaller or non-vision models?
