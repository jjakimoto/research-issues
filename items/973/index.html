Natural-Language Workflows Are Not Software Yet: Artifact-Driven Compilation for Reliable Agent Execution

📰 Latest · 2026-08-24 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-24

Source: arxiv · 2026-08-21
Link: https://arxiv.org/abs/2608.21341

If you ship prose skill files or workflow prompts, this paper is the first to treat them as an unoptimized program: it measures the enforcement burden a prompt places on an agent (cyclomatic complexity, context pressure, live artifacts across a compaction point) and compiles the prose into a deterministic Python orchestrator plus per-step subagent modules with declared read/write artifacts. Averaged over three executor models, task resolve rate goes from 56% (raw text) to 84% (compiled) -- the +28 points in the abstract -- and the ablation shows almost all of it comes from burden-driven step decomposition, not from the LLM rewrite.

Executive summary

Artic (ARTIfact-driven workflow Compiler) argues natural-language workflows fail as software for two structural reasons: data dependencies are implicit (every step inherits all prior context, resembling a program in which intermediate results are stored as global variables), and instruction-following degrades with control-flow and context load. Artic compiles prose into a semi-structured artifact-driven language (agent / seq / if / while over an artifact store) where each step declares the artifacts it reads and writes and constraints gate produced artifacts, then runs constrained optimization guided by four program-analysis burden metrics, then validates the LLM translation with three passes (static join type-checking, induction over program structure, and coverage-guided dry-run simulation of source vs compiled workflow). On 488 instances from 11 domains (SOP-Bench + chi-Bench) the compiled workflow averages 85/82/85% resolve rate on GLM-4.7-Flash / GPT-OSS-120B / Qwen3-235B vs 62/46/60% for raw text. Compiled workflows are also 32 points more consistent across six executor models and 56 points more consistent under pass^10 repeats, and cut per-agent input tokens by 63%.

The failure model: a prose workflow is a program with only global variables

The unreliability is located in two places. First, implicit data flow: because a step does not declare its inputs, the executor must guess which of the accumulated intermediate results is the relevant evidence, and it guesses wrong when the context is noisy. Second, control-flow burden: an agent reads 'high risk OR recent acute utilization' as an AND. The paper explicitly rules out the naive fix a harness builder would reach for first -- splitting the prose into subagent calls with message passing -- because the overloaded step still combines referral information, utilization, medical records and complex route conditions. Decomposition only helps if it is targeted at the steps that are actually overloaded, which is what the burden metrics are for.

  • Failure mode 1: wrong evidence selection from a dense inherited context (implicit data dependency).
  • Failure mode 2: misread compound route conditions (or-vs-and) in a long instruction.
  • Failure mode 3: skipped steps, wrong transfers, and information lost during context compaction as branching and intermediate state grow.
  • Naive step-by-step subagent decomposition is explicitly shown insufficient -- the burden has to be measured, not just split.

The compiled artifact: what the compiler actually emits

The prototype core is 5.9K lines of Python and emits an executable workflow package with three parts. (1) Orchestrator -- a deterministic Python driver that invokes one step module at a time, checks the artifacts that step produced, and transfers control according to the returned route. (2) Step modules -- one per workflow statement, each implementing a shared two-function interface: exec_step transforms declared input artifacts into declared output artifacts and returns a next-step decision plus optional feedback, and check_artifact enforces the schema and quality gate before the orchestrator continues. (3) Runtime -- artifact I/O, path resolution, version metadata, and actor-call primitives for subagents, LLM checks and tools. A lowering validator checks the generated module against the interface and uses program analysis plus model-assisted prompt/entity analysis to catch undeclared reads -- for example a subagent prompt mentioning an input field absent from the step interface. Measured shape: on average 9.4 nodes, 11.9 edges, 9.2 artifacts per workflow.

  • Per-step generated interface: exec_step(declared inputs) -> (declared outputs, next-step route, optional feedback); check_artifact = schema + quality gate.
  • Artifact versioning is the main runtime contract: stable artifact name, versioned committed values; a retry or loop writes a new version rather than overwriting, so diagnostics point at the exact artifact that failed a gate and execution resumes from the latest valid artifacts.
  • Retry protocol: run step -> apply gate -> commit only on success; on failure the runtime records feedback and re-invokes the step with the previous artifact path plus the constraint feedback.
  • Runtime invariants enforced: artifacts versioned consistently, failed attempts never silently committed, retry feedback preserved, every selected route exists in the package.
  • The language stays semi-structured -- the local action inside a step is still a natural-language instruction; only data dependencies and control transfers are made explicit and inspectable.

The four burden metrics that drive the optimization loop

The trick for measuring a prompt is the finest-grained artifact-driven workflow fg(omega), where each agent step has one local goal and one focused artifact. Normalizing to fg() exposes the latent structure the prompt would otherwise ask a single agent to manage implicitly, and then ordinary static analysis applies. Four objectives: (1) control-flow complexity = cyclomatic complexity of the latent workflow; (2) context pressure, where a sequence ADDS (one agent carries both pieces of latent work), a branch takes the MAX (only one route runs), and a loop multiplies by the expected iteration count; (3) compaction pressure via standard live-variable analysis -- the total size of artifacts still live across the worst internal compaction point; (4) artifact cost, the summed size of materialized artifacts, which penalizes gratuitous materialization. The compiler searches for workflows that reduce the first three without inflating the fourth.

  • Compaction pressure is a live-variable analysis: the cost at a compaction point is the total size of artifacts still live across it.
  • Sequence composition adds context pressure while a branch takes the max -- this is what makes long linear prose steps score as expensive.
  • The optimizer is explicitly NOT a correctness check: the paper states the metrics do not check whether the compiler LLM correctly translated the source workflow.

Faithfulness validation: three passes over an LLM translation

Pass 1, static well-formedness: deterministic pre-LLM checks on surface syntax, that every artifact read is declared and available, and artifact-availability type-checking at control-flow joins. The central rule is path stability at joins -- the type of the artifacts a step reads must agree across all predecessor paths. The worked example is a workflow that retrieves a medical record only on the high-risk branch and then cross-checks utilization: the join check forces either retrieval on all paths or a rewrite of the later step's declared inputs. Pass 2, inductive validation: decompose the global faithfulness claim by program structure and check that each intermediate artifact is a legitimate conceptual boundary in the source before validating prefix and continuation. Pass 3, dry-run simulation: extract a logical formula from the validation target, use predicate coverage to enumerate concrete scenarios including cases where changing one predicate changes the expected artifact or route, then have LLM validators independently simulate source and compiled workflows on each scenario and compare trajectories.

  • Case study: the compiled workflow's first decision node checked only whether a referral message existed, not whether the referral came from a qualifying source. Predicate-coverage enumeration produced the exposing case; the two independent dry runs disagreed, localizing the fault to the referral-source predicate -- no oracle label needed.
  • Failure diagnostics feed back into the constrained-optimization stage rather than being surfaced to the user.

Results and exactly where the +28 points come from

Benchmark: 488 instances across 11 domains from SOP-Bench and chi-Bench, capped at 50 instances per domain for budget. Source workflows average 10,427 characters (max 31,431). Three compiler models (GPT-5.4, Sonnet-4.6, GLM-5) and six executor models from 3B active to 744B total, all through the same Codex-based agent harness reaching environments via MCP tools. Baselines: Text (prose straight to the executor), SkillCreator (LLM rewrites it into a clearer skill document -- still text), Code (a coding agent writes Python with LLM calls, same harness and executor), plus MASFactory and Chat2Workflow. The +28-point headline is the mean over the three executor columns: Artic 85/82/85 averages to 84%, Text 62/46/60 averages to 56%. Note the shape of the win: Code is a strong baseline on simple rule-like domains (100% on patient intake) because its implementations often use stable heuristics such as keyword matching, but collapses on Medical (12/12/8%); Artic wins by not collapsing anywhere.

  • Per-agent context pressure: compiled workflows cut average per-agent input tokens by 63% and output tokens by 50% versus one agent on the text workflow.
  • Compilation is a one-time offline cost: median first-package compilation under 5 minutes and average cost under $3 with GLM-5.
  • Compiler-model cost spread is large for near-identical quality: GLM-5 $2.02 / 80.0%, Sonnet-4.6 $13.27 / 84.0%, GPT-5.4 $38.19 / 76.0%.
  • SkillCreator -- pure text rewriting, the closest analogue to hand-tuning a skill file -- buys only 62->66 on GLM-4.7-Flash and nothing at all on GPT-OSS-120B (46->46).

How consistency and variance were actually measured

Three distinct reliability measurements, all on the Medical domain. (a) Cross-model spread: the text workflow ranges from 28% on its worst executor to 60% on its best -- twice the spread of the compiled workflow, which ranges from 72% to 88%. (b) Per-instance consistency: an instance counts as consistent when all six executor models either pass it or fail it under the same representation -- compiled 80% vs text 48%, the abstract's 32 points. (c) Repeated-execution consistency: pass^k following Tau-Bench, the probability that all k repeated runs are correct; each instance is run ten times and the unbiased per-instance estimator is C(x,k)/C(10,k). At k=10 the compiled workflow holds about 72% vs 16% for text, and from k=1 to k=10 it degrades 16 points vs 35. (d) Perturbation robustness: restricted to instances both representations originally solved, then injecting transient model request failure and forced context compaction at 10K and 20K tokens -- compiled preserves 100%, text drops to 80%.

  • pass^k estimator is combinatorial and unbiased (C(x,k)/C(10,k) from 10 repeats), not just 'ran it k times and all passed'.
  • The perturbation study is conditioned on cases both representations already solved, which isolates fragility from capability.
  • All reliability numbers are single-domain (Medical), so they are the paper's most suggestive but least broadly sampled claims.

Key findings

  • The +28-point headline is the gap between the mean of the three executor-column averages: Artic 85/82/85 (mean 84%) vs Text 62/46/60 (mean 56%), over 488 instances in 11 domains.
  • Ablation attributes almost all of the gain to the burden-driven optimization stage, not to the validator: with validation kept but optimization removed, Medical drops from 88% to 48% (-40 points), whereas removing dry-run feedback costs 8 points and removing validation as well costs another 8. Removing all three yields 0%.
  • Text-space rewriting is nearly worthless as a reliability fix: SkillCreator moves GLM-4.7-Flash from 62 to 66 and GPT-OSS-120B from 46 to 46, and actually hurts on several domains (video annotation 72->34, referral abuse v2 50->36).
  • Direct code generation is bimodal: 100% on patient intake and referral abuse v1 (keyword-matching heuristics that happen to fit simple rules) but 12/12/8% on Medical -- the compiled semi-structured form avoids both failure modes.
  • Compiled workflows are 32 points more consistent across six executor models (80% vs 48% of instances where all six agree) and 56 points more consistent under pass^10 (~72% vs 16%), with a cross-model spread half as wide (72-88% vs 28-60%).
  • Decomposition roughly halves per-agent context: 63% fewer average input tokens and 50% fewer output tokens per agent turn versus a single agent running the text workflow.
  • Compilation is cheap and offline -- median under 5 minutes and under $3 per workflow with GLM-5 -- and quality is stable across compiler models (80.0 / 76.0 / 84.0%) even though cost varies 19x.

Notable quotes

Overall, our compiled workflows achieve the best average task resolve rate for every executor model: 85% on GLM-4.7-Flash, 82% on GPT-OSS-120B, and 85% on Qwen3-235B.
The compiled workflow is consistent on 80% of instances, compared with 48% for the text baseline.
In the implementation, artifact data may be backed by a typed JSON object, a document, or a file, while constraints record the semantic properties that later checks and control transfers may inspect.
In our ablation study, a compiler variant without this correctness validation performs 16 percentage points worse than the full system.

Limitations

  • Compilation only fixes enforcement, not judgment: on 'Know your business' and warehouse inspection every representation stays low (Artic 64% and 50%) because the SOP itself asks the executor to decide whether mismatched business details are genuine typos or fabrications -- the paper calls this orthogonal to workflow enforcement.
  • Every reliability result (cross-model spread, per-instance consistency, pass^k, perturbation robustness) comes from a single domain (Medical, and only chi-Bench's care-management intake stage), and domains over 50 instances were subsampled to 50 for budget.
  • Faithfulness is only ever established by LLM dry runs and LLM-discharged local obligations -- there is no formal source semantics to verify against, so a systematic misreading shared by compiler and validator is invisible; the Artic value for referral abuse v2 is even inconsistent between two tables (100 vs 96).

Open questions

  • Do the burden metrics transfer back to plain prose authoring -- can a harness builder score an existing skill/prompt file with cyclomatic complexity, context pressure and live-artifact-at-compaction and get useful guidance without emitting a Python package at all?
  • Compiled packages hard-code an orchestrator and per-step interfaces; what is the maintenance story when the source SOP changes, and can the compiler do incremental recompilation instead of paying the full validation loop again?
  • Does the 28-point gap shrink toward zero as frontier executor models get better at long-context instruction following, or does the consistency advantage persist even when average resolve rates converge?
