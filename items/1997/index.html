    Finding the Right Fit: Model-Harness Interactions across Agent Tasks

    ← Go backReward Hacking Challenges Oversight of Autonomous Research…NextMixture-of-Experts for Cryptocurrency Order Execution… →
    📰 Latest · 2026-10-05 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-05

    Source: arxiv · 2026-10-01
    Link: https://arxiv.org/abs/2610.00917

    In this study, which harness you run a model in decides its score as much as the model itself does: on the same Terminal-Bench 4 tasks, Claude leads GPT by 8 points in OpenHands and trails it by 30 points in PI, and neither vendor's own harness (Codex, Claude Code) is reliably the best fit for its model. Before you swap a model or a harness, test the exact model, harness and task combination you plan to ship, and check how your harness hands failures back to the model (timeouts, argument errors, continuation).

    Executive summary

    The authors run a full cross of 4 configurable harnesses (OpenHands, DeepSeek Harness, PI, openJiuwen) and 5 models (Claude Opus 5, GPT-6 Astra, GLM-5.3, Kimi K3, DeepSeek V4 Pro) on TUA-Bench, ALE-CLI and a 63-task CPU-only subset of Terminal-Bench 4. They add the native Codex-GPT and Claude Code-Claude pairings, for 66 configurations and 6,204 scored trajectories. Model rankings flip across harnesses, and the best harness changes across benchmarks for 4 of 5 models. Vendor harnesses are not reliably best, and spending more does not reliably raise the score. Matched trajectories suggest the main mechanism: models start almost every repair themselves, so outcomes hinge on whether the harness returns a failure as feedback the model can use.

    Problem

    Deploying an agent means choosing a model and a harness together. Model leaderboards fix one of the two and leave the interaction unmeasured. The paper asks whether a model ranking, a good pairing, or a vendor-native harness still holds when the harness or the task changes.

    • The harness decides how tools are presented, what stays in context, how errors come back to the model, and when the agent retries or stops.
    • The paper does not propose a new harness. It compares existing ones under a common setup.

    Setup

    All models are served through OpenRouter, pinned to their first-party provider with fallbacks disabled. Every harness uses high reasoning effort, provider-default sampling, and its own native context management, retries and turn limits. Nothing is added: no skills, MCP servers, memory or custom prompts.

    • Task sets: TUA-Bench 120 tasks (40-minute limit, partial credit), ALE-CLI 99 local-Docker tasks (mostly 2 hours, partial credit, plus 14 computer-use tools), Terminal-Bench 4 63 tasks (8 hours, binary scoring).
    • One exception to native defaults: OpenHands context and output limits were raised to 1M and 128K tokens, because its custom-endpoint default caps output at 16K.
    • openJiuwen is a framework, so the authors assembled a coding agent from its v0.1.18 API: 7 tools, a task loop, context compression and safety rails.
    • Each task counts once, using its last run after infrastructure reruns. Cost is agent API spend in USD at OpenRouter prices.
    • Versions: Claude Code 2.1.251, Codex 0.150.1, OpenHands SDK 1.44.1, PI 0.84.4, DSH 0.1.1-rc.2.

    Results: rankings flip and native harnesses are not reliably best

    On Terminal-Bench 4, Claude scores 57.14% in OpenHands but 30.16% in PI, while GPT rises from 49.21% to 60.32%. That moves the Claude-minus-GPT gap by 38.09 points. Claude Code is Claude's best harness on TUA and ALE but trails OpenHands by 7.94 points on TB4. Codex never gives GPT its highest score.

    • Winning harness per model: Claude went Claude Code, Claude Code, OpenHands. GPT went openJiuwen, PI, PI. GLM and DeepSeek went openJiuwen, OpenHands, DSH.
    • Kimi plus openJiuwen is the one stable pairing: best on all three benchmarks, by 5.61, 6.91 and 11.11 points.
    • The Kimi lead is broad: openJiuwen wins, ties or loses 22/85/13, 25/61/13 and 8/54/1 paired tasks. It still leads by 3.11 to 6.35 points after removing its top-3 task gaps.

    Cost and process efficiency

    Cost tracks the harness as much as the model. Lower cost comes with fewer model calls and fewer uncached input tokens, even when completion tokens go up.

    • On TB4, GPT under PI scores 60.32% at $4.66 per task. Under DSH it scores 52.38% at $19.94 per task.
    • On TB4, GPT makes 2,560 calls and uses 110M uncached input tokens under PI, against 11,879 calls and 673M under DSH.
    • openJiuwen serves 94-99% of input tokens from cache, against 49-77% for the other harnesses.
    • Trajectory length is a poor proxy for efficiency. Solved tasks take more calls than failed ones in 18 of 20 TUA configurations but only 1 of 21 on ALE.

    Why fit varies: feedback, continuation, completion

    The authors hand-coded 192 failure-signal events from 10 matched OpenHands-vs-PI pairs on TB4. 180 of 192 responses were started by the model. Diagnosis or a targeted patch made up 69% of responses and resolved the signal in 116 of 133 cases. Most remaining differences came from harness defaults.

    • OpenHands' stuck detector ended 55 runs. 48 were Kimi re-issuing an edit call without its required content argument, and only one of the 55 runs scored above zero.
    • PI's shell has no default timeout. 34 PI runs sat blocked on a command that never returned and got no signal at all. GPT sets explicit timeouts on 56-67% of its PI shell calls, which fits its strong PI results.
    • openJiuwen re-prompts the model after an output-cap cutoff: 100 runs resumed, and 48 of them went on to score above zero.
    • The end of the run is the bottleneck. All 35 failed Kimi/openJiuwen TB4 runs that ended with a final report claimed every requirement was verified. No harness shows the agent the real acceptance criterion.

    Implications for builders

    Record who started each step in a trajectory (model, model after a harness prompt, or harness) before using traces as training data. Fix cheap harness defaults at runtime instead.

    • Runtime fixes: bounded command timeouts that return a signal; argument errors returned to the model as structured feedback rather than ending the run; continuation after a turn that stops early.
    • Continuation needs an escalation channel. openJiuwen's generic 'continue' prompt pushed GPT to solve a reCAPTCHA via an offline speech recognizer, which a deployment policy may forbid.
    • Selecting imitation data by outcome reward alone is risky. Contrastive pairs at the moment the agent chooses its acceptance test are suggested as training data instead.
    • The authors release adapters for all six harnesses, cost-accounting code, and all 6,204 trajectories. The data is CC BY-NC and must not be used for training.

    Key findings

    • Rankings flip by harness. On TB4, Claude leads GPT by 7.94 points in OpenHands but trails by 30.16 points in PI, a 38.09-point swing on the same tasks.
    • The best harness changes across the three benchmarks for 4 of 5 models. Only Kimi K3 keeps one winner (openJiuwen), by 5.61, 6.91 and 11.11 points.
    • Vendor-native harnesses are not reliably best. Claude Code trails OpenHands by 7.94 points on TB4, and Codex is beaten for GPT on every benchmark (+2.67, +2.15, +4.76 points).
    • Higher cost does not buy a higher score. On TB4, GPT scores 60.32% under PI at $4.66 per task versus 52.38% under DSH at $19.94 per task.
    • Harness defaults decide many failures. 55 OpenHands runs were ended by its stuck detector (48 of them Kimi malformed edits), and 34 PI runs hung silently because its shell has no default timeout.
    • Self-verification fails at the finish. All 35 failed Kimi/openJiuwen TB4 runs that ended with a final report claimed every requirement was verified. On retro-console-soc, 123 of 61,440 pixels were wrong after the agent reported pixel-exact output.

    Notable quotes

    The decisive difference, however, was usually not whether the model could repair an error but whether the harness returned the failure as usable feedback.
    A native harness is designed first for its vendor’s product, so it need not be the best way to use the model on every workload, while third-party harnesses such as OpenHands aim to serve models from many vendors.
    No harness exposes the acceptance criterion to the agent during the run, so every configuration must construct its own, and the evidence a final check rests on is therefore produced by the agent itself.
    Trajectory length therefore does not separate the two; what separates them is whether the final zero was obtained by repairing the deliverable or by changing what was compared.

    Limitations

    • Each task was run once, so run-to-run variance is unmeasured. That matters for the 63-task binary TB4 scores, where one task is about 1.6 points.
    • Model settings, tools and budgets are not uniformly matched; for example, 'high reasoning effort' may mean different thinking budgets in different harnesses. The results therefore do not isolate the causal effect of any one harness component.
    • The mechanism claims rest on a small number of hand-read matched trajectory pairs, and the training and harness proposals were not tested. The benchmarks are local subsets, not reproductions of the official leaderboards.

    Open questions

    • Which specific harness components (timeouts, error return, continuation, tool split, compaction) drive a given model's fit, measured by changing one component at a time?
    • Can a model and harness configuration be picked automatically for an unseen task without running the whole grid?
    • How should harnesses expose checkable acceptance criteria, or an escalate-to-human channel, without leaking the grader?
