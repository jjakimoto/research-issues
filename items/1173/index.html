FrontierChallenge: Evaluating Scientific Workflow Completion

📰 Latest · 2026-08-29 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-29

Source: arxiv · 2026-08-25
Link: https://arxiv.org/abs/2608.24979

The single most useful benchmark yet for anyone building an autonomous researcher: it scores the whole delivered artifact bundle against a per-task executable Grader (files, numbers, figures, code execution, cross-artifact consistency) instead of a final answer, and the resulting Pass Rate ceiling is 20.6% even though Avg. Scores reach 87.9. Its headline warning is that your agent's own "done" message is nearly worthless as a completion signal: 75.5% of non-passing Claude Code trajectories ended with language claiming completion.

Executive summary

FrontierChallenge is a cross-domain benchmark of 300 end-to-end scientific workflows (97 released and evaluated, 203 held out) across quantum chemistry, molecular dynamics, materials characterization, analytical chemistry, life science, and electrochemistry/environment. Each task freezes the objective and inputs and specifies an output contract of heterogeneous deliverables (report, tables, figures, executable code, simulation products), scored by a task-specific executable Grader; Pass Rate counts only tasks whose complete contract is satisfied, with Avg. Score reported separately as partial credit. Twelve frontier models across three scaffolds top out at 20.6% Pass Rate (20 of 97 tasks) despite Avg. Scores up to 87.9, with 0% Pass Rate in electrochemistry/environment against a 94.9 Avg. Score. The failure analysis over 970 Claude Code trajectories shows self-reported completion and tool-error presence are both uninformative about actual delivery.

Why existing benchmarks fall short: the evaluation unit is wrong

The paper's framing is that the unit of evaluation in prior work is a final answer, an interaction trace, a single program, or a workflow from one discipline, none of which tests whether an agent can hand off a mutually consistent bundle of scientific artifacts. It surveys HLE, AgentBench, GAIA, OSWorld, SWE-bench, ALE and Frontier-Bench; LAB-Bench, BixBench, BLADE and ScienceAgentBench; and CORE-Bench, PaperBench, ScienceBoard, AstaBench and others. Table 1 positions FrontierChallenge as the only entry marked on all six design axes: scientific-workflow core, fixed scientific inputs, end-to-end execution, multiple artifacts, executable evaluation, and cross-domain science.

  • Prior evaluation units are "often a final answer, an interaction trace, a single program, or a workflow from one discipline".
  • Of the scientific benchmarks: "many evaluate an answer, a decision set, or a single self-contained program rather than a heterogeneous deliverable set".
  • Deliberately narrower than autonomous science: the agent does not set the research agenda or formulate the problem, only executes after objective, inputs and required outputs are fixed.

How the tasks and domains were built

Tasks were sourced from real analysis, computation, simulation and research-delivery processes rather than expanded QA or coding exercises, and screened on Representativeness, Complexity, Diversity, and Verifiability. Every task had to have fixed inputs, a defined execution environment, a complete deliverable contract, and an executable evaluation procedure; subjective-output and single-step tasks were excluded before the 300-workflow pool was formed. Agent-visible instructions are kept separate from evaluator-side references and scoring components. The 97 released tasks were randomly drawn from the subset whose official evaluation needs no GPU.

  • 300 workflows total; 97 released and evaluated; 203 internal held-out set.
  • Released split: 74 Hard, 23 Medium; 21 workflow families; six reporting domains.
  • Representative tasks require real domain software: ORCA, CP2K, LAMMPS, AmberTools, PLUMED.
  • The paper explicitly warns the six domains are "descriptive slices of the released evaluation set, not probability samples", so cross-domain scores are not disciplinary difficulty rankings.
  • Appendix B task cases (wound-healing image assay over 18 images, TLC monitoring of a Suzuki coupling over 8 lanes, reaction-calorimetry safety assessment) each demand a reproducible script plus 4-6 specific tables/figures/reports.

THE VERIFIER: an executable per-task Grader with a nested, triple-run LLM Judge

This is the part that matters most for grounding. Completion is not checked by a human at scoring time and not by a free-floating LLM judge: each task carries its own executable Grader that inspects the submitted artifact bundle directly and returns a native score in [0,100]. An LLM Judge is used only where a rubric-defined semantic criterion is delegated to it, and crucially remains a component inside that task's Grader rather than the evaluator of record. GPT-5.6 Sol is the Judge and every Judge-assessed criterion is run three times and averaged. Because that averaging can push a fully-compliant submission slightly under 100, the full-completion indicator is a score >= 99.9 — a threshold the paper says only absorbs Judge-averaging noise and relaxes no rubric requirement.

  • Grader checks: required files, numerical results, formats, figures, code execution, and cross-artifact consistency — execution-and-file grounded, not answer-string matching.
  • Every package also contains a stepwise scoring rubric plus documentation for reproduction and scoring, so runs are rerunnable under fixed conditions.
  • Pass Rate = fraction with score >= 99.9; a high-scoring but incomplete submission is explicitly not counted as a pass.
  • Avg. Score is called a descriptive suite-level aggregate rather than a calibrated cross-task scale, since rubrics are heterogeneous.
  • Failure analysis distinguishes "Judge-assessed artifact shortfalls" from "deterministic Grader diagnostics", confirming the two verifier layers are separable in the reported signals.
  • Caveat for anyone reusing the design: GPT-5.6 Sol is simultaneously the Judge and one of the twelve evaluated models (and the top Avg. Score holder at 87.9). The paper does not discuss or ablate this.

Results: a 20.6% Pass Rate ceiling under an 87.9 Avg. Score

Across all evaluated configurations Pass Rate ranged from 3.1% to 20.6% while Avg. Score ranged from 67.5 to 87.9. Codex with GPT-5.6 Sol had the top Avg. Score (87.9) and shared the top Pass Rate (20.6%, 20/97) with Claude Code using Grok 4.6. Eight configurations cleared an Avg. Score of 80 yet none passed more than 20.6% of tasks, meaning high averages generally corresponded to artifact bundles still missing at least one contract requirement. The best Hard Pass Rate is 14.9% versus 43.5% on Medium.

  • Domain-level results are where partial credit most badly misleads — analytical chemistry hit 87.6 Avg. Score with a 4% peak Pass Rate, and electrochemistry/environment hit 94.9 Avg. Score with a 0% Pass Rate for every single configuration.
  • Worst overall: GLM-5.2 on Claude Code at 3.1% Pass Rate.
  • Domain profiles diverge sharply from the aggregate ranking — Grok 4.6 leads quantum chemistry at 60% Pass Rate while GPT-5.6 Sol leads Avg. Score in four of six domains.
  • Gemini 3.7 Flash completed 25% in both quantum chemistry and molecular dynamics but zero in three other domains.
  • Scaffold effects are not isolated: the two Apodex 1.1 runs differ (Frontier Agent 12.4% vs Claude Code 10.3%), which the authors call descriptive only.

The false-success finding: agents say "done" when they are not

Over 970 Claude Code trajectories (ten models x 97 tasks), 641 of the 849 non-passing runs — 75.5% — ended with a final message containing lexical completion language, and only 13 runs (1.5%) explicitly signalled that work was still running or in progress. Completion language was somewhat rarer among the worst runs (61.2% below score 50) but stayed above 78% in every non-passing band above 50, versus 90.1% among passing runs — so the signal barely separates success from failure. Raw tool errors are equally uninformative.

  • Self-reported completion is close to useless as a stop signal: 75.5% false-positive rate among failing runs, and the passing-run rate is only ~15 points higher.
  • Error presence is anti-diagnostic — passing runs hit MORE tool errors than failing ones (94.2% vs 80.7%), with a higher median rate (5.6 vs 4.4 per 100 tool results); successful trajectories simply recover.
  • Contract-breach signatures concentrate by domain: Judge-assessed artifact shortfalls dominate in materials characterization (97% of non-passing submissions), analytical chemistry (95%) and electrochemistry/environment (85%) but only 43% in quantum chemistry, while deterministic Grader diagnostics are more common in life science (50%) and quantum chemistry (40%).
  • The conclusion's prescription for builders: explicit contract tracking, cross-artifact validation, and evidence-based completion checks.
  • The trajectory analyses are restricted to Claude Code (the only scaffold with a common event schema across models) and are explicitly descriptive.

Resource use and wall-clock (no dollar costs reported)

The paper reports tokens and time but never a monetary cost per task and never a human-intervention rate. Reported input token use varied more than sixfold across the twelve configurations, from 2.183 million tokens per task (Grok 4.6 with Claude Code) to 13.730 million (Apodex 1.1 with Claude Code). Cache shares are extreme for the OpenAI configurations (98.8% for Sol, 98.5% for Terra) versus 75.3% for Gemini 3.7 Flash, and the authors note provider-specific tokenizers and reporting conventions preclude a hardware-normalized efficiency interpretation.

  • No $/task, no human-intervention rate, and no repeated-run variance: results are single runs.
  • Token spend and Pass Rate are not aligned — the cheapest configuration by input tokens ties for the best Pass Rate, while the most expensive scores 10.3%.
  • Mean execution time ranged from 21.8 to 112.8 minutes per task with heavy right tails: Frontier Agent (Agent Team) averaged 112.8 minutes with a 272.2-minute 90th percentile against a 54.9-minute median.
  • Long-tail budgeting matters: a 90th-percentile task can run 4.5 hours on the slowest scaffold.

Key findings

  • Completion is verified by EXECUTION plus FILES, not by an answer string and not by a standalone LLM judge: each task ships a task-specific executable Grader that checks required files, numerical results, formats, figures, code execution, and cross-artifact consistency.
  • The LLM judge is deliberately subordinate — GPT-5.6 Sol acts as Judge only for rubric-defined semantic criteria, stays nested inside the task's Grader, and is run three times per criterion; Pass Rate then requires a score of at least 99.9, so partial credit can never buy a pass.
  • Best measured completion is 20 of 97 tasks (20.6% Pass Rate) for two separate configurations, against a floor of 3.1% — while Avg. Scores span 67.5 to 87.9. Eight configurations beat 80 Avg. Score and none beat 20.6% Pass Rate.
  • The measured-vs-self-reported gap is the paper's sharpest result: 641 of 849 non-passing Claude Code runs (75.5%) ended claiming completion, and only 1.5% admitted being unfinished. Passing runs claimed completion at 90.1%, so the signal separates success from failure by only about 15 points.
  • Partial credit is actively misleading per domain: electrochemistry/environment reached a 94.9 Avg. Score with a 0% Pass Rate across every configuration, and analytical chemistry reached 87.6 with a 4% peak.
  • Efficiency does not track quality and tool errors are anti-diagnostic: the lowest-token configuration (2.183M input tokens/task) ties for the best Pass Rate while the highest (13.730M) reaches only 10.3%, and 94.2% of PASSING runs hit at least one tool error versus 80.7% of non-passing.

Notable quotes

Each task has a task-specific Grader that checks the required files, numerical results, formats, figures, code execution, and cross-artifact consistency.
We use GPT-5.6 Sol as the Judge and run each Judge-assessed criterion three times.
Final self-reporting is therefore not a reliable substitute for evaluating the submitted artifact bundle.
Completion therefore depends on the entire artifact bundle, not on whether the agent returns a plausible final answer.

Limitations

  • Stated in the Conclusion: findings are limited to the released task set, the evaluated configurations, the Claude Code trajectory scope, provider-specific resource accounting, and single runs — no repeated-run variance is reported, and no monetary cost or human-intervention rate appears anywhere.
  • Only 97 of the 300 workflows are released and evaluated; the 203 held-out tasks include everything whose official evaluation requires GPUs, so the released set is systematically biased toward CPU-gradable work, and the six domains are descriptive slices rather than probability samples.
  • Not noted by the authors: GPT-5.6 Sol serves as the Judge while also being one of the twelve evaluated models and the top Avg. Score holder, with no self-preference ablation presented.

Open questions

  • How much of the Pass Rate ceiling is a contract-tracking failure versus a scientific-competence failure? The paper separates Judge-assessed artifact shortfalls from deterministic Grader diagnostics by domain but never attributes the 79.4% of non-passing runs to a cause.
  • Would an explicit contract checklist injected into the agent loop — deliverable-by-deliverable self-verification before terminating — close the partial-vs-complete gap, given the authors' own prescription of evidence-based completion checks?
  • Does more compute help? Token spend spans sixfold with no correlation to Pass Rate, leaving open whether any test-time-compute strategy converts partial progress into complete delivery.
