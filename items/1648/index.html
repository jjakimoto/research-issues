    GameLogicBench: Evaluating Coding Agents on Runtime Game Logic with Tick-Level State Assertions

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-21

    Source: arxiv · 2026-09-18
    Link: https://arxiv.org/abs/2609.21562

    A benchmark that checks game rules at every simulation tick, across evaluator-chosen scenarios, with no model in the scoring path — and its ablations show that final-state-only checks and single-scenario evaluation let a large fraction of deliberately broken solutions pass, which is a warning about how most agent benchmarks are scored.

    Executive summary

    GameLogicBench is a 72-task benchmark of gameplay-logic patches in Godot/GDScript projects, spanning isolated mechanics (Atom), interacting systems (Combo), and repository-scale features (Repo). Its judge runs each submission across 403 hand-designed scenarios instantiated by seeds into 1,451 test cases, asserting internal game state and event history at every tick, with no language model in the scoring path so verdicts replay exactly. Across 20 model-scaffold configurations, the best run (Claude-Opus-5 + Claude Code) solves 52.78% of tasks, and solve rates fall monotonically as integration scope widens. The most useful part for practitioners is the benchmark-design ablation: terminal-state-only scoring and preview-scenario-only scoring both let large fractions of capability-removed mutants escape, and open-network runs showed agents retrieving upstream source for repo-derived tasks.

    The evaluation gap it targets

    Existing game-dev benchmarks judge a finished artifact: one fixed scenario, an agent-chosen video, or a model judge. A run can end in a valid-looking state while having violated the rules mid-run, and model judges are non-reproducible and expensive.

    • No compared benchmark combined multiple judge-selected scenarios, tick-level assertions on all tasks, and deterministic verdicts.
    • Cost of model judging cited as motivation: the best-agreeing WebCompass judge costs $4.66 per sample; WebGameBench budgets up to two hours of evaluator rollout per game.
    • GameLogicBench's row: Godot/GDScript, patch tasks, engine assertions, deterministic, tick-level, 2-12 scenarios per task, 72 tasks.

    Task design and the three tiers

    Each task hands the agent a brief plus a Godot project with a preview/debug interface, and names the files it may edit. A three-layer information boundary hides the scored scenarios and the judge implementation; the scored runs reuse the preview's interface but change layout and input sequence.

    • Atom (21 tasks): one isolated mechanic in a purpose-built minimal game.
    • Combo (28): several mechanics whose correctness depends on interactions in time, space, and under concurrent calls.
    • Repo (23): in-place implementation inside a real project — mean 209 game files and 17,599 lines, up to 62,895 lines.
    • Matched comparison (GLM-5.2 + OpenCode): ~15x more output tokens and nearly 4x more non-cached input tokens than GameDevBench.

    Construction and the mutant-validation gate

    Humans curate both ends; agents build the middle. Annotators screen mechanics for deterministic criteria (unique value, legal event ordering, or a conserved quantity) and reject anything scored on visual or experiential quality. Then a prototyping agent, a blueprint agent, and an implementation agent produce the task, the judge, and calibration artifacts.

    • Calibration artifacts per task: a proper solution, a behavior-preserving control, a naive solution, and single-capability mutants.
    • Acceptance requires the proper solution and the control to pass all scenarios with margin, the naive solution to fail, and each mutant to be caught by at least one targeted scenario.
    • Funnel: ~200 candidate ideas, 122 finished construction/calibration/agent review, 72 admitted.

    Results across 20 model-scaffold configurations

    Solving happens in a sealed container (no egress beyond the model API, 3,600s limit, effort=high); judging happens in a separate network-disabled container at a fixed timestep, varying call schedules including concurrent calls, re-entry, and stretched time bases.

    • Claude Code gives the highest solve rate for every model it was paired with; Codex uses the fewest turns.
    • Scaffold matters enough that the model-scaffold pair is the unit of comparison: Qwen-3.8-Max ranges 26.39%-44.44% across scaffolds.
    • Cost is not predictive — configurations with the same solve rate differ by up to 25x in cost, and the frontier endpoints (31.94% vs 52.78%) differ by a factor of 123 in cost.
    • Repeat runs are unstable: pass@3 minus worst@3 is 26.39%-36.11%, per-attempt standard deviation 3.67%-4.24%.

    Failure modes and contamination

    Failures are overwhelmingly semantic rather than mechanical, and capability-conditioned analysis locates them in state commitment, spatial, and timing invariants rather than engine API use. A separate audit shows repo-tier scores inflate when the network is open.

    • 74.3% of failed scenarios are 'mechanism failures' — the solution runs and is judgeable but violates a behavioral contract; 17.2% have no judgeable solution; 8.5% are nonviable.
    • Engine-contract capability pools at 88.75% strict pass; Commitment/Spatial/Timing pool at 53.4%-58.57% — a 30-35 point separation.
    • Of five open-network repo-tier configurations, four retrieved upstream source and all four scored higher than their sealed counterparts.

    Key findings

    • Best configuration is Claude-Opus-5 under Claude Code at 52.78% solve rate (61.90 Atom / 53.57 Combo / 43.48 Repo) at $443.16 total; solve rate declines Atom -> Combo -> Repo for nearly every configuration.
    • Terminal-state-only scoring let mutants escape on 34 of 36 tasks (236/666) and flipped 64/488 solutions from FAIL to PASS (+8.9 points); preview-scenario-only scoring escaped 508/666 mutants and flipped 418/488 (+58.1 points).
    • Without mutant validation during construction, 127 of 666 mutants passed the original criteria, exposing 24 missing checks across 19 of 36 tasks.
    • 74.3% of failed scenarios are runnable-but-wrong behavior, not crashes or unbuildable submissions.
    • Capability split: Engine contract pools at 88.75% strict pass while Commitment, Spatial, and Timing pool at 53.4%-58.57%.
    • Four of five open-network Repo-tier configurations retrieved upstream source and all four beat their sealed counterparts, so repo-derived tasks need sealed egress to be meaningful.
    • Library scale: 72 tasks, 403 hand-designed scenarios, 1,451 test cases, 2-12 scenarios and 10-38 test cases per task.

    Notable quotes

    In the control, 127 of 666 mutants passed, revealing 24 missing checks across 19 of the 36 tasks.
    Four configurations retrieved upstream source, and manual inspection found direct reuse in the reviewed traces.

    Limitations

    • Scope is deliberately narrow: only gameplay logic expressible as deterministic tick-level state assertions — no content depth, art, presentation, or player experience.
    • Single engine and language (Godot 4.4 / GDScript), single-container harness, so no network-synchronization testing.
    • Main table is one sample per configuration, and the stability analysis shows per-attempt swings of two to three tasks, so small solve-rate differences should not be over-read.

    Open questions

    • Do the terminal-only and preview-only escape rates generalize beyond games — i.e. how much do SWE-bench-style final-state unit tests overestimate agent correctness on stateful systems?
    • Can tick-level deterministic judging be extended to longer interactions, multi-container networked play, and other engines without losing exact replayability?
    • Given that scaffold choice moves solve rate by up to 18 points for the same model, what property of the scaffold is actually doing the work?
