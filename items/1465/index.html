Authority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant Coding Agents

📰 Latest · 2026-09-12 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-12

Source: arxiv · 2026-09-08
Link: https://arxiv.org/abs/2609.08371

A harness-level capability system gives each sub-agent its own frozen, typed permission store, cutting successful indirect prompt injections from 33-47/75 runs to 3/75 without asking the model to detect malicious text - strong evidence that agent security belongs in the dispatch layer, not the prompt.

Executive summary

CapScope is a harness-level authorization mechanism for coding agents that replaces ambient authority (naming a resource suffices to act on it) with typed, host-side capabilities: Read/Write over canonicalized path prefixes and Exec over parsed argument-vector prefixes. Before any repository content or tool output is read, a preflight LLM call over only the trusted user request plus the project file tree is compiled by deterministic host code into a frozen task-wide authority ceiling; each sub-agent then receives a separately stored, narrowed subset, and every tool call is checked against the issuing principal's store. Implemented on the Pi agent toolkit (v0.78.0) and evaluated over 300 runs (5 Python repair tasks x 5 injection surfaces x 4 conditions x 3 trials), the injected effect lands in 47/75 runs under ambient authority, 46/75 under a static denylist, 33/75 under a task-specific global policy, and 3/75 under CapScope, at 68/75 repairs completed versus 68-72/75 for the baselines.

The problem: ambient authority and the confused deputy

Coding agents read external content (repo files, AGENTS.md, skill files, source comments, tool output) where any text can act as an instruction. Model-side defenses make a probabilistic call about whether text is an instruction. The authors frame this as a classic confused-deputy problem: the harness holds the user's privileges while the model chooses the resource names those privileges act on.

  • Motivating example: a trojaned pytest fixture prints a fake CI note telling the agent to write an attacker-chosen signing key into an ordinary source path no denylist flags.
  • Cited prior evidence: attack-success rates up to 84% against production coding editors (Liu et al. 2025); CVE-2025-54135 (CurXecute) chained injection to Cursor MCP config creation and RCE.
  • CapScope is explicitly a host-side reference monitor, not an object-capability system - the model still designates string-named resources.

Design: mint, derive, invoke

A capability is a pair (effect type, scope predicate). Three formal rules govern authority. Mint is the only rule introducing new authority and runs a trusted host policy on trusted preflight input. Derive filters a model-requested candidate grant against the delegating ceiling, keeping only structurally contained capabilities. Invoke executes a tool call only when a held capability matches the effect type and its predicate accepts the arguments; otherwise the call is blocked and a refusal is returned to the model.

  • Read/Write scopes are canonicalized path prefixes, resolving relative segments and symlinks to block traversal.
  • Exec scopes are allowed argument-vector prefixes; the parser rejects substitution, splits compound commands, and strips redirections, so an Exec grant for pytest admits 'pytest -v' but not a chained network call.
  • By inspection of the three rules, all authority traces back to a trusted Mint and both compilation and Derive can only narrow - injected text can influence which in-ceiling scope is chosen but cannot expand the ceiling.
  • Explicit non-goal: not a confidentiality mechanism; navigation commands admitted by the wrapper can read outside a principal's Read prefix, so process sandboxing remains necessary.

Implementation on Pi

Built on Pi 0.78.0, an open-source TypeScript coding-agent toolkit, without modifying Pi internals. The tool_call event fires before dispatch and a blocking return aborts the call, satisfying the two host requirements (a blocking pre-dispatch interceptor and per-session state). Four components: a structured capability type, a preflight authorize() returning a ceiling plus orchestrator grant, scoped spawning and derivation for delegation via process-isolated sub-agents, and a per-principal hook closing over a distinct store.

  • Scopes are structured data, not opaque functions, so the host can check containment before installing a grant.
  • Grant completion first adds role-required reads/writes, then filters the result against the frozen ceiling.
  • The root orchestrator is special: its own calls are checked against the (possibly read-only) operational store, while its grants are bounded by the task ceiling.
  • Artifact with code, tasks, mutators and decision logs released on figshare.

Evaluation setup

Five small Python repair tasks, each with one bug and a failing pytest suite, run through a fixed four-principal pipeline (orchestrator, runner, patcher, verifier) so only the authorization model varies. The same payload is placed in five untrusted surfaces: README, AGENTS.md, a project-local skill file, a source comment/docstring, and pytest output. Conditions: ambient authority, a static task-independent denylist, a task-specific global policy generated before injection, and CapScope. All runs used qwen3.5-flash via an OpenAI-compatible endpoint, collected May 2026, preflight at temperature 0.

  • Metrics are read from the filesystem and are independent of logs and of each other: task success (suite passes) and attack executed (attacker-only sentinel exists on disk).
  • Interactive user approval of uncovered capabilities is implemented but disabled during evaluation to keep the protocol fixed.
  • Injected actions are deliberately plausible in-repo operations (run a project-local utility, write a project file), not obviously hazardous ones.

Results and costs

Per-principal scoping dominates: 47/75, 46/75, 33/75 and 3/75 attacks executed across the four conditions. A conventional denylist is effectively no better than no policy because the malicious actions are ordinary repository operations it never names. Under CapScope all three residual attacks came through AGENTS.md; the other four surfaces admitted none. Task success is 68/75 for CapScope versus 72/75 unconstrained. Latency rises to a 316 s mean (208 s median, five runs hitting the 900 s timeout) versus 145 s for ambient authority, driven largely by extra model turns after refusals.

  • Diagnostic: under CapScope the model proposed the injected action in 34/75 runs but only 3 runs recorded an allowed attack call - the model is still fooled; the harness stops it.
  • Of the 34 attack-proposing CapScope runs, 27 contained repeated attack-targeting calls, inflating latency.
  • CapScope's 7 task failures decompose as: 2 from a too-narrow preflight ceiling, 2 from failing to reroute an edit to the write-authorized patcher, 3 from session timeout despite passing tests.

Positioning vs. related work

CapScope is contrasted with model-side defenses (Instruction Hierarchy, PromptArmor), which remain probabilistic, and with runtime-policy systems. Progent is named the closest design but allows LLM-proposed policy updates during execution; CapScope instead freezes the ceiling before repository content is read and additionally gives each principal a distinct attenuated store.

  • Two distinguishing axes claimed: segment-by-segment parsed command scopes, and per-agent attenuation.
  • Other governance points surveyed: CaMeL (dual-LLM interpreter), Fides (information-flow labels), AgentArmor (IR type-checking), ToolGate (Hoare contracts), PACT (argument provenance).
  • Classical grounding: Saltzer & Schroeder, Dennis & Van Horn, Miller & Shapiro, Hardy's confused deputy.
  • Published at LMPL '26 (2nd ACM SIGPLAN Workshop on Language Models and Programming Languages).

Key findings

  • Per-principal capability scoping reduced executed injections to 3/75 runs, versus 33/75 for the strongest global baseline, 46/75 for a static denylist, and 47/75 for ambient authority.
  • A conventional static denylist (.env, .ssh, rm -rf, sudo, curl) gave essentially no protection over no policy at all (46/75 vs 47/75), because the malicious actions were ordinary in-repository file writes and utility executions.
  • Security came at a modest utility cost: CapScope completed 68/75 repairs versus 72/75 for unconstrained ambient authority, and matched the task-specific global policy's 68/75.
  • The defense works despite the model still being fooled: decision logs show the model proposed the injected action in 34/75 CapScope runs, but only 3 runs recorded an allowed attack call.
  • Residual failures concentrate in one surface: all three successful attacks under CapScope came through AGENTS.md (3/15), while README, skill file, source comment, and tool output were 0/15 each.
  • Latency roughly doubled (mean 316 s vs 145 s; median 208 s), mostly from retry turns after refusals - 27 of the 34 attack-proposing runs contained repeated attack-targeting calls - plus five runs hitting the 900 s timeout.

Notable quotes

CapScope does not stop the model from following an injected instruction; it stops the resulting tool call when that agent lacks the required capability.
The preflight LLM shapes how broad the initial policy is, but cannot place or alter capabilities once untrusted content is admitted—only host code can mint, narrow, or enforce them.
Each malicious action creates a unique sentinel or marker that benign repair never produces.

Limitations

  • Small, narrow corpus: five small Python repair tasks, a single model (qwen3.5-flash), and three trials per cell; no large refactors, dependency migrations, or long-running workflows.
  • Not a confidentiality mechanism: a permitted read followed by a permitted write can still exfiltrate, navigation commands bypass Read prefixes via the command wrapper, and allowed commands such as pytest transitively execute untrusted repository code.
  • Policy generation is a separate, unverified source of error from enforcement: a too-broad preflight scope caused the residual 3 attacks and a too-narrow one caused 2 of the 7 task failures; interactive approval was disabled.

Open questions

  • Why does AGENTS.md remain the one leaky surface under CapScope, and can grant completion be hardened so model-generated subtask text cannot steer which in-ceiling capability is selected?
  • Can the preflight ceiling be made both tighter and more complete - e.g. via incremental, user-approved minting - so the utility gap disappears without widening the attack surface?
  • How much of the 2x latency overhead survives in an interactive deployment, and does the approach hold on larger, multi-language repositories and other agent harnesses?
