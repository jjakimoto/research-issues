    WideSWE: Can Coding Agents Coordinate Changes Across Repositories?

    ← Go backSharpening Tax in Post-TrainingNextLiveOption: Evaluating LLM Agents in Structured Option… →
    📰 Latest · 2026-10-04
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-10-04

    Source: huggingface-daily-papers · 2026-09-27
    Link: https://arxiv.org/abs/2609.33382

    Even the best setup tested (Codex CLI + GPT-5.6-sol) fully completes only 42.5% of 120 real two-to-three-repo changes, and the main failure is edits that touch every target repo but still don't fit together correctly, not missing repos. That matters for any agent pipeline that spans several codebases, such as research code plus data and infra libraries. The scaffold matters as much as the model: the same GPT-5.6-sol scores 32.5% under Claude Code. Caveats: n=120, no variance or confidence intervals reported, and hidden tests were manually relaxed in 88 of the 120 tasks.

    Executive summary

    WideSWE is a benchmark of 120 real tasks (60 bug fixes, 60 features). Each task needs coordinated changes in 2-3 target repositories, inside a historical ecosystem workspace that also holds up to 20 non-scored context repositories. A task counts as solved only if every target repo passes all of its hidden fail-to-pass (F2P) and pass-to-pass (P2P) tests. Across seven scaffold/model configurations, full task success ranges from 10.83% to 42.50%. Codex CLI with GPT-5.6-sol is best, yet it fixes at least one target repo in 83.33% of tasks, a large gap between per-repo progress and finishing the whole change. A paired comparison on 89 tasks (one joint run over the whole workspace vs. a separate run per repo) shows independent runs mostly recover work the joint run skipped. They do not fix attempts that were made but wrong, and they lose cross-repo context that helps with feature work.

    Problem: single-repo benchmarks miss ecosystem coordination

    SWE-bench, DeepSWE and ProgramBench all score work inside one repository, but in real ecosystems one feature or fix often has to land in several repos. Examples: the same policy in the Sentry Go, Python and Ruby SDKs, or a PHP SDK change that two downstream integrations must adopt. The authors scanned 1,729,171 PRs across 103 ecosystems and found 109,233 PR records that explicitly reference another repo in the same ecosystem. Each task gives an agent a request and a historical workspace. The agent must work out which repos need changes (at least 2 targets) and deliver changes that work together.

    • Target repos determine scoring. Context repos (0-20 per task, median 3; 27 tasks have none) can be read and even edited, but are not scored.
    • Success(c) is the product of the per-target-repo pass indicators, so a task fails if any single target repo has a failing F2P or P2P test.
    • Coordination patterns: producer-consumer dependency in 96 tasks (80%), parallel propagation of the same behavior across repos in 24 tasks (20%).

    Benchmark construction pipeline

    Sources were the top-200 GitHub organizations by stars (Gitstar, June 5, 2026), narrowed to 103 active ecosystems. The authors took PRs merged since 2024-01-01 in non-archived repos and grouped linked changes into candidates. Deduplication plus checks for PR availability, test changes and Linux compatibility left 4,437 groups. Of the 2,188 groups whose latest PR merged on or after 2025-06-01, manual review kept 635 single-intent, multi-repo groups. Environment building made 240 runnable, and 192 had at least one F2P test per target repo. All 60 bug fixes were kept, plus 60 of the 132 features (including all 13 three-repo feature cases), giving 120 tasks over 41 ecosystems and 253 target repos with 2,815 F2P and 22,139 P2P tests.

    • Prompts reuse wording from the original issues and PRs, merge overlapping requirements, and add no implementation hints. One author wrote each prompt and two others reviewed it.
    • Context repos are snapshotted no later than the earliest target base commit, to avoid leaking future information. Gold patches and hidden tests are withheld.
    • Median reference patch: 13 files and 416 lines changed. Language mix: 86 single-family and 34 multi-family tasks.
    • Hidden tests run on clean Base snapshots and are installed separately from the agent's edits. Failures to inject a test patch can never count as a pass.

    Requirement-aligned hidden-test review

    Tests inherited from the reference PRs sometimes reject correct solutions. They may require specific private helper names, fixed file paths, or exact error-message text, or they may check extra functionality that the issue never asked for. The authors applied two rules: relax implementation-specific constraints, and remove checks for unrequested functionality. They then confirmed that the revised suites still fail on Base and pass with the Gold patch.

    • Revisions touched 88 of the 120 tasks: constraints were relaxed in 87, unrequested checks removed in 16, and 15 needed both.
    • Example: a TensorDict test keeps the TypeError check but drops the 'generator must be' message match.
    • Example: in a Nextcloud task, three new reminder presets in the reference patch were removed from the test expectations because the issue never requested them.

    Experimental setup

    Seven configurations pair a scaffold, a model and a reasoning effort. Codex CLI v0.147.0 runs with GPT-5.6-sol (high). Claude Code v2.1.139 runs with GPT-5.6-sol (high), Claude Opus 5 (high), Gemini 3.8 Flash (xhigh), DeepSeek V4 Pro (high), Qwen 3.8 Max (xhigh) and GLM 5.3 (xhigh). Every configuration gets one prompt, the full ecosystem workspace, and the same harness permissions, timeout policy and per-run resource limits. RQ3 compares Joint execution (one run over the whole workspace) with Independent execution (one full run per target repo, which sees only that repo). This uses Codex CLI + GPT-5.6-sol on the 89 tasks whose prompts apply unchanged in both settings (29 bug fixes, 60 features).

    • Metrics: case success (primary), repo success, F2P-complete and P2P-preserved repo shares, test-level pass rates, and mean API requests per task.
    • Failures were annotated in two stages (final diffs, then trajectories). Two annotators agreed 91.2% of the time (Cohen's kappa 0.86).
    • The joint-vs-independent comparison matches per-run limits, not total budget: Independent gets one full run per target repo.

    Results and failure modes

    Codex CLI + GPT-5.6-sol leads overall (42.50%). Qwen + CC is best on bug fixes (48.33%) but drops to 26.67% on features. Gemini + CC solves 0% of features. P2P preservation is high (84-96%), so agents rarely break existing behavior but often leave the requested behavior incomplete. In 48 of the best configuration's 69 failed tasks, one repo passes all F2P tests and another does not. Post-edit failure (every target edited, yet the required behavior is still wrong) is the most common category for every configuration except Gemini. Gemini mostly recognizes the needed work but never delivers it (52.34%), and 82.14% of those runs stay stuck in investigation or planning.

    • Scaffold effect: with GPT-5.6-sol fixed, Codex CLI scores 42.50% vs Claude Code 32.50%, while API requests rise from 86.7 to 134.8. In one Rails/Propshaft example, Codex revisited the request after tests passed and extended the fix to Rails.
    • Repo count: every configuration does worse on three-repo tasks. For Codex, repo success rises from 63.08% to 66.67% while task success falls from 42.99% to 38.46%. 87.50% of its failed three-repo tasks edited all targets.
    • A subtle failure (Sentry/Symbolicator): the producer and consumer were both changed to pass an exception-name string, and the agent's own tests used strings too, so local tests passed while the required structured contract was violated.
    • Delivery failures can be expensive: 769 API calls (DeepSeek, Prettier) and 562 (Gemini, Dify) without finishing the second repo.

    Joint vs independent execution (repo visibility)

    Joint execution solves 40.45% of the 89 paired tasks, vs 35.96% when every independent run must succeed. 22.47% of tasks flip outcome between the two settings. Independent runs help bug fixes (34.48% to 44.83%) but hurt features (43.33% to 31.67%), at 3.13x the API requests (296.6 vs 94.7). Independent runs mostly recover repos the joint run never touched: 60.00% of unmodified joint-failed repos pass vs 9.43% of modified ones. The joint workspace supplies implementation facts (Ansible: the agent read the service's actual table and field names) and behavioral references for checking work (Symfony: comparing native and PHP implementations fixed a discrepancy).

    • Paired cases: both succeed 26.97%, joint only 13.48%, independent only 8.99%, neither 50.56%.
    • MUI Strict Mode: the joint run fixed Base UI and its test setup, then forgot Material UI. Separate runs repaired both.
    • The authors warn that the opposite net directions for bug fixes vs features should not be generalized beyond this sample.

    Key findings

    • The best configuration (Codex CLI + GPT-5.6-sol) fully solves 42.50% of 120 tasks, and the others range from 10.83% to 37.50%. The best configuration still fixes at least one target repo in 83.33% of tasks, and in 48 of its 69 failures one repo passes all F2P tests while another does not.
    • The scaffold matters at a fixed model: GPT-5.6-sol scores 42.50% under Codex CLI vs 32.50% under Claude Code, and Codex uses fewer API requests (86.7 vs 134.8 per task).
    • Post-edit failure, where every target repo is edited but the change is still wrong, is the most common failure for 6 of 7 configurations (59.42%-73.33%). Gemini 3.8 Flash is the exception: in 52.34% of its failures it recognizes the needed work but never delivers it.
    • Agents largely avoid regressions (P2P-preserved 84.16%-95.93%) but leave requested behavior incomplete. Gemini's high P2P score (95.93%) mostly reflects how little it changes (16.60% F2P-complete).
    • Joint vs independent on 89 tasks: 40.45% vs 35.96% overall. Independent runs help bug fixes (+10.35 points) but hurt features (-11.66 points) at 3.13x the API requests, and 22.47% of tasks flip outcome.
    • Independent runs mainly recover omitted work: 60.00% of joint-failed repos that the joint run never modified pass independently, vs only 9.43% of repos it had modified.

    Notable quotes

    Our experiments show that agents do not reliably carry a shared requirement through all affected repositories.
    Despite using 3.13 times as many requests, independent execution does not improve overall task success.
    This suggests that a separate run offers much less improvement when an implementation has already been attempted but remains incorrect.
    Neither repository coverage nor agreement between edited components alone establishes coordinated completion.

    Limitations

    • The sample is small, with no variance or confidence intervals reported. With 120 tasks, a 5-point gap is 6 tasks, and the 89-task RQ3 comparison uses only one configuration. The authors themselves say the bug-fix vs feature reversal should not be generalized.
    • Joint vs independent is matched on per-run limits, not total budget: Independent gets one full run per repo, about 3.13x the requests. So it is not a clean test of scope versus compute.
    • Scope is limited to 2-3 target repos on Linux, built from public PRs. Hidden tests were manually revised in 88 of 120 tasks, a judgment call that shapes what counts as correct, and the model rankings depend on specific scaffold versions.

    Open questions

    • Would an explicit scope-enumeration and re-check step close much of the gap? For example: list the target repos up front, then re-read the request after local tests pass, as Codex did in the Rails/Propshaft case.
    • Does a hybrid setup work better at equal total budget? One option is a joint pass to read context and contracts, followed by focused per-repo runs, or cross-repo contract tests generated before editing.
    • How does performance degrade with more target repos (more than 3) or more distracting context repos? The paper does not test either.
