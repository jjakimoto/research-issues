A Jagged Frontier: Evaluating Robustness of Code Agents to Semantics-Preserving Transformations

📰 Latest · 2026-08-24 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-24

Source: arxiv · 2026-08-18
Link: https://arxiv.org/abs/2608.18389

The first systematic robustness study of repository-level coding agents shows that rewriting a repo into an equivalent form costs only ~0-6.7 points of resolve rate, but inflates token cost by up to 22.9% and completely scrambles which model looks most robust: rankings do not transfer across scaffolds or benchmarks. If you pick a model or scaffold from a SWE-bench leaderboard, that ranking says nothing about how it will hold up on your differently-written codebase.

Executive summary

Mahmud et al. (Colorado State, UIUC, CMU, Microsoft) build a library of 14 semantics-preserving transformations (SPTs) for whole Python repositories plus a non-adversarial random sampler that draws equivalent variants of a SWE-bench instance, then run two scaffolds (mini-SWE agent, OpenCode) x four models (Claude Opus 4.5, Kimi K2.5, MiniMax M2.5, Qwen 3.6-27B) x two benchmarks (28 SWE-bench Verified + 26 SWE-bench Pro instances), 20 unperturbed runs and 20 one-run variants per instance. Mean resolve-rate degradation is small (positive in 13/16 configurations, significant in 6/16, max 6.7 points), but effort overhead is broader and larger: cost rises in all 8 Verified configurations, up to 22.9%, even among runs the agent resolved. The headline result is a 'jagged robustness frontier': every model is among the most robust in one cell and the most brittle in another, while capability rankings by resolve rate are almost unchanged by perturbation — so a leaderboard cannot see this at all. Degradation is concentrated in a heavy tail of instance-configuration pairs, not spread across repos or models.

The 14 SPTs and how equivalence was actually established

Semantics preservation is defined as identical observable behaviour on every input and operationalized as 'functional test-suite equivalence'. The catalog splits into 9 rewrites of existing structure and 5 inert insertions. Applicability conditions are deliberately conservative because a repository, unlike a snippet, can shadow builtins, lacks type annotations (+ does not commute on str/list/custom __add__, so Astroid type inference gates the Commutative Operand Permuter), and can observe its own structure via locals(), frame introspection, metaclasses and framework base classes. Validation was differential testing on three SWE-bench projects: SymPy (12,994 tests), sqlfluff (10,060), xarray (19,917). Test-suite files are never perturbed, so the success oracle is identical before and after.

  • Rewrites: If Else Switcher, For Loop Rewriting, And Condition Splitter, Comparison Swapper, While Loop Unrolling, Double Negation Injector, Commutative Operand Permuter, Local Variable Renamer (WordNet synonyms), String Literal Splitter
  • Inert insertions: If True Wrapper, Try Except Injector (except Exception: raise, never bare except), Dead Code Injector, Dead String Assignment, Dead Method Injection
  • Dead String Assignment and Dead Method Injection are keyword-bound: keywords are extracted from the issue description by a single LLM call, so the decoy surfaces whenever the agent greps for that term
  • Dead Method Injection is skipped for custom metaclasses, attribute-dispatch overrides, property-only namespaces, and Pydantic BaseModel / Enum / NamedTuple / TypedDict / Protocol / ABC bases
  • Implementation: Python 3.10, LibCST v1.8.5, Astroid v3.3.0, NLTK v3.6.0 for WordNet

Sampler, perturbation magnitude, and the paired experimental design

Per variant the sampler makes four random draws: which transformations (3 of the 14, uniform), which files (a fresh inclusion probability per transformation, so variants range from a single localized edit to repo-wide perturbation), which sites (0.7 of candidate sites per included file), and which keywords. Files touched by the gold patch are always included and exempt from the file cap, so every variant hits the solution-relevant region rather than reaching it by chance. Magnitude is modest: a median of 6.9% of source lines on Verified and 7.7% on Pro. The protocol is 20 unperturbed runs plus 1 run on each of 20 fresh variants per instance, each in a freshly provisioned Docker container. Appendix E proves the degradation estimator is unbiased for any K runs per variant and that variance is minimized at K=1.

  • Statistics are fixed-population: 95% bootstrap percentile intervals from 20,000 resamples of runs within instances; per-instance degradation uses 95% Newcombe intervals for the difference of two proportions
  • The file and keyword caps were the only hyperparameters set from observation: without them, agents frequently detected the perturbation and reverted the repo outright (e.g. git reset), 'which destroys the measurement rather than making it harder'
  • Sampling is explicitly non-adversarial, so the reported numbers are lower bounds — 'A feedback-guided adversary can only do more damage'
  • No random seed is fixed and all models run at temperature 1.0; reproduction means drawing 20 fresh variants per instance, not replaying the same variants

What was evaluated

Two scaffolds x four models x two benchmarks = 16 configurations, each evaluated independently with a fixed agent setting shared by seed and variants. mini-SWE agent v1.17.5 is a single centralized agent with bash as its only tool and a continuous append-only context; OpenCode v1.18.4 dispatches subagents (Build, Plan, General, Explore) with a large tool set, per-role tool restrictions and multiple dynamic contexts. Instances: 28 of 500 SWE-bench Verified (stratified over repo-difficulty strata, restricted to instances Opus 4.5 resolves per the official leaderboard) and 26 of 731 SWE-bench Pro.

  • Models: Claude Opus 4.5, Kimi K2.5, MiniMax M2.5 via Bedrock; Qwen 3.6-27B served locally with vLLM and priced at OpenRouter rates for cost comparability
  • Hardware: 2x AMD EPYC 9554 (128 cores), 768 GB RAM, 6x RTX PRO 6000 Blackwell 96 GB, Docker 29.5.2; every run in its own container
  • Total agent runs: 16 configurations x ~54 instances x 40 runs per instance, which is why no hyperparameter grid search was attempted
  • Code, instance ID lists, prompts and an interactive results dashboard: github.com/CSU-TrustLab/jagged-frontier

RQ1 — degradation is small on average, jagged in structure, concentrated in a tail

Mean degradation is positive in 13 of 16 configurations and its bootstrap interval excludes zero in 6 of 16; no scaffold-model pair is significant on both benchmarks. The largest drop in the study is Opus under mini-SWE agent on SWE-bench Pro at 6.7 points — the same pairing degrades only 1.8 points on Verified, and Opus is the least degraded of the four models under OpenCode on Pro. The scaffold effect is the one consistent finding, and it survives a capability flip. Per-instance the design is underpowered: with 20 runs per condition only swings of roughly 25 points can exclude zero, and only 14 of 432 instance-configuration cells do so — yet the mass of point estimates is positive.

  • Non-transfer, concretely: Qwen degrades 0.2 pts under mini-SWE agent on Verified but 5.5 pts under OpenCode; MiniMax goes the other way, 2.7 -> 0.5; Kimi is at or below 1 point in three of four cells but is the worst OpenCode model on Pro at 4.2 pts
  • Heavy tail: three Pro instances (-50, -40, -35 pts) account for roughly two-thirds of the worst configuration's 6.7-point mean
  • Verified tail cells: scikit-learn-14983 loses 40 pts under OpenCode+Qwen, matplotlib-20859 loses 35 under mini-SWE+Qwen, sympy-12489 loses 30 under mini-SWE+MiniMax
  • Counter-swings exist: mwaskom__seaborn-3069 improves 55 pts under OpenCode+MiniMax and 35 under mini-SWE+Qwen, both intervals excluding zero
  • Brittleness is a property of instance-configuration pairs: no instance degrades under all eight configurations on either benchmark

RQ2 — the cost signal is bigger and broader than the resolve-rate signal

Restricted to runs the agent resolved in both conditions, cost rises in all 8 Verified configurations from 4.0% (mini-SWE+Opus) to 22.9% (OpenCode+MiniMax), with every interval excluding zero. On Pro the overhead concentrates in the richer scaffold: all four OpenCode configurations pay 8.8-12.6% more with intervals excluding zero, while mini-SWE agent configurations sit near zero. Steps and cost decouple — cost per step rises in 12 of 16 configurations and input tokens per step in 13 of 16. The most striking behavioural signature is Opus under mini-SWE agent on Verified, which responds to perturbation by taking fewer steps on every single instance (mean -19.8%) while output tokens per step more than double (median +101%).

  • Over all runs, Verified cost rises 4.5% to 25.4% with 7 of 8 intervals excluding zero; Pro rises in 7 of 8, up to 14.7%
  • Because the resolved-only and all-runs views agree, the overhead is not an artifact of long failing runs
  • Practical read: an outcome-only benchmark hides a 1-in-5 token-cost tax that a differently-written codebase can impose on the same agent

RQ3 — the failure modes, and what this says about benchmarking

20 trajectories (14 distinct instances, both scaffolds, both benchmarks, all 4 models) were manually reviewed. Four patterns emerge: (1) detection and reversion — MiniMax on qutebrowser checks the commit history, spots the transformations, and reverts the repo before patching; (2) localization degradation — Opus on openlibrary greps an issue keyword and is thrown off by noisy dead string assignments carrying the same keyword; (3) 'fixing' the perturbation — Opus resolves injected tautologies by hand and cleans them up in the final patch, enlarging the diff; (4) corrupted patch validation — Kimi misattributes a genuine test failure to a split string literal and submits the wrong patch. On the benchmarking question the paper is explicit that this is brittleness rather than a contamination detector.

  • Detection is highly variable — Opus on psf-requests repeatedly reads if-true-wrapped code and never acknowledges any SPT; double negation is the easiest to miss
  • MiniMax on qutebrowser avoids the transformed core files entirely and gathers information elsewhere, inflating localization time and file coverage
  • Qwen on matplotlib under OpenCode claims several times to have reset the repository without actually doing so, then finally does
  • Issue-description quality drives jaggedness independently: a NodeBB issue containing two conflicting instructions sends three models into patch-validate-debug loops
  • Prior robustness work (identifier renaming, dead-code insertion, docstring perturbation) was single-turn and non-agentic; the scaffold-interaction dimension is what is new here

Key findings

  • Perturbing a repo into an equivalent form costs little on average: mean degradation is positive in 13 of 16 configurations, significant in 6 of 16, and maxes out at 6.7 percentage points, with a median of only 6.9-7.7% of source lines touched.
  • Robustness rankings do not transfer: Qwen degrades 0.2 pts under mini-SWE agent on Verified but 5.5 pts under OpenCode; Opus degrades 1.8 pts on Verified but 6.7 on Pro under the same scaffold. Every model is most robust in at least one cell and most brittle in another.
  • The simpler scaffold is more robust on both benchmarks (1.34 vs 1.88 pp on Verified, 1.88 vs 3.65 on Pro) even though which scaffold is stronger in absolute terms flips between benchmarks (89.05% vs 81.20% on Verified, 76.35% vs 79.33% on Pro).
  • Cost is the more sensitive metric than resolve rate: among runs the agent resolved, cost rises in all 8 Verified configurations (+4.0% to +22.9%, every interval excluding zero) while step overhead never exceeds 9.9%.
  • Leaderboards cannot see this effect: in 3 of 4 scaffold-benchmark panels the model ranking by resolve rate is identical before and after perturbation, and the one change is a swap between two models separated by 0.2 points at baseline.
  • Agents actively fight the perturbation: the authors had to cap keyword-bound transformations because agents otherwise detected the SPTs and ran git reset on the repository, destroying the measurement.
  • Equivalence validation was empirical but broad: every test retained its outcome across SymPy (12,994 tests), sqlfluff (10,060) and xarray (19,917) for all 14 transformations applied one at a time at every applicable site.

Notable quotes

Across all three projects, every test retained its outcome under all 14 transformations.
Averaged over the four models, mini-SWE agent degrades less than OpenCode on both benchmarks: 1.34 points against 1.88 on SWE-bench Verified, and 1.88 against 3.65 on SWE-bench Pro.
On SWE-bench Verified, step overhead never exceeds 9.9% while cost overhead reaches 22.9%.
This shows that a leaderboard-style comparison would not register the impact of SPTs.

Limitations

  • Semantics preservation is only test-suite-validated on three projects, which the authors state 'is bounded by the coverage of the underlying test-suites and is therefore not a proof of equivalence'; composed transformation sequences are never re-verified per instance, only justified by transitivity.
  • Scale and power: 28 Verified + 26 Pro instances, all pre-filtered to instances Claude Opus 4.5 already resolves, Python files only; with 20 runs per condition only per-instance swings of roughly 25 points can exclude zero, so 418 of 432 instance-configuration cells are individually inconclusive.
  • The sampler is non-adversarial by design and its reach is deliberately capped so agents do not detect and revert the perturbation, so every number is a lower bound; Qwen's cost is imputed at OpenRouter prices rather than measured, and no random seed is fixed.

Open questions

  • How much worse does it get under a feedback-guided adversarial sampler, given that these lower bounds already reach 6.7 pp and +22.9% cost?
  • Why is the richer, subagent-based scaffold consistently the more brittle one — dynamic per-subagent contexts, tool-mediated localization being more easily diluted by decoys, or something else — and can a scaffold defend itself by canonicalizing the repository before the agent works on it?
  • Is the concentration in a few instance-configuration pairs evidence of memorization of specific benchmark repos, or generic distribution shift? The authors show capability rankings survive perturbation but do not separate these two explanations.
