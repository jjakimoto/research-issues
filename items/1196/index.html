FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution

📰 Latest · 2026-08-30 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-30

Source: huggingface-daily-papers · 2026-08-17
Link: https://arxiv.org/abs/2608.16157

FreeToken is an open-source, edge-native MoE serving engine that turns a single consumer GPU plus its host CPU into one elastic inference platform - serving Qwen3.6-35B-A3B at 39.3 tok/s on an 8 GB RTX 4060 laptop and the 753B GLM-5.2 on one RTX PRO 6000 at 2.0x llama.cpp. If you self-host open weights, this is the first system that decides at runtime, from two measured bandwidths, how much of each expert-cache miss goes over PCIe versus straight to the CPU, instead of freezing that split at load time.

Executive summary

FreeToken (UC Berkeley / UT Austin / MIT, including Kurt Keutzer, Song Han, Matei Zaharia and Ion Stoica) is an edge-native MoE serving system that co-designs model layout, expert residency, CPU-GPU execution, agentic state reuse and runtime memory management for a single personal machine. Its two core mechanisms are bandwidth-adaptive execution - a closed-form q* = m*B_P/B_H policy splitting each decode step's expert-cache misses between PCIe cache fills and in-place CPU execution using bandwidths profiled on the deployed machine - and semantic-aware caching, which anchors recurrent-state checkpoints at agent-harness token boundaries and keeps a shared LRU expert cache in VRAM. On an RTX 5090 it sustains 77-83 tok/s on Qwen3.6-35B-A3B (BF16) and 22-25 tok/s on DeepSeek-V4-Flash (native MXFP4), 1.5-2.3x the strongest of llama.cpp / Ollama / KTransformers / MoE-Infinity. Code is released at github.com/FlashML-org/FreeToken.

The problem: sparse activation makes edge MoE feasible, the full expert pool makes it slow

An MoE layer stores hundreds of experts but routes each token to a few, so a personal GPU can hold the active path even when it cannot hold the model. DeepSeek-V4-Flash activates 6 of 256 routed experts in each of its 43 layers, so only 13B of 284B parameters participate per token - a footprint that fits an RTX 5090's 32 GB. But the inactive experts must live in host memory and enter the execution path on demand. The authors frame the gap as economic, not physical: over 100M consumer machines already contain discrete GPUs, with the RTX 4060 Laptop the single most common at 3.81% of Steam's June 2026 survey.

  • Prefill destroys the sparsity: thousands of tokens per layer activate nearly the whole expert set. FP4 DeepSeek-V4-Flash moves about 140 GB of expert weights - roughly 2 s on an RTX 5090 (PCIe 5.0 x16), ~5 s on 4090/3090-class desktops, 10 s+ on the x8 links common in laptops.
  • Agentic harnesses re-prefill constantly: hybrid-attention and recurrent layers (gated DeltaNet in Qwen3.6-35B-A3B, Kimi Delta Attention in Kimi-K3) compress the prefix into a state that cannot be partially reused, so any context edit invalidates checkpoints after it.
  • Decode is the opposite regime: static placement (llama.cpp assigns MoE tensors at load, KTransformers pins a hot subset) misses most routed traffic, and consumer CPUs have only ~50 GB/s (dual-channel DDR4) or 80-90 GB/s (DDR5) against the 1-1.8 TB/s a 4090/5090 draws from VRAM.
  • Nothing on the edge is dedicated: the compositor, browsers and games claim VRAM mid-session, and reading the ~140 GB FP4 DeepSeek pool from a 7 GB/s NVMe alone takes ~20 s before any warmup.

System design: one elastic expert cache, prefill double-buffering, semantic anchors

FreeToken organizes serving around a two-level expert-memory hierarchy. The CPU-resident expert pool holds all routed-expert weights and is the source of truth; non-expert weights stay GPU-resident; all remaining GPU memory becomes a single elastic LRU expert cache shared by every MoE layer. Because the host pool is authoritative, GPU memory affects only performance, never correctness - which is what makes runtime resizing safe.

  • Prefill full-layer double buffering: while the GPU computes layer l, a dedicated transfer stream loads all of layer l+1, so the transfer can start before that layer's routing is known. Entries surviving prefill seed decode.
  • Semantic-aware state cache: full-attention KV uses a radix prefix tree, but recurrent layers need checkpoints. FreeToken anchors checkpoints at special-token boundaries - thinking segments, tool calls and outputs, conversation turns - precisely where harnesses edit. After an edit, only the genuinely new suffix is re-prefilled.
  • Decode-time semantic-aware expert caching: a shared global LRU whose contents follow the router rather than a workload-agnostic placement chosen at load time.
  • Elastic memory: at any scheduler safe point the GPU expert cache can be rebuilt for a revised VRAM budget without restarting the engine. GPU warmup is eliminated by construction, since the first request runs cold through the ordinary decode path.
  • Implementation: all routing-dependent control stays on the GPU inside a statically captured CUDA Graph. One kernel per MoE layer dedups routed experts, classifies them against the residency table, derives q, selects eviction victims in a single pass, and rewrites logical IDs into physical slot IDs or a CPU-assignment flag.

The bandwidth-adaptive q* policy

This is the paper's central contribution. Caching cannot eliminate misses, and the key observation is that prior work differs in how well it predicts misses but not in how it serves them - every miss is ultimately a PCIe transfer, so decode stays link-bound no matter how accurate prediction becomes, while host compute sits idle. A missed expert, unlike a missed KV page, can also simply be computed where it already lives.

  • Two bandwidths are profiled on the target machine at deployment: B_P, the pinned host-to-device expert-transfer bandwidth over PCIe, and B_H, the effective bandwidth of the CPU-side MoE expert kernel.
  • The m missing experts are partitioned into a cache-fill set of size q (transferred and executed on the GPU, staying resident for reuse) and a CPU-execution set (executed in place). The two run concurrently.
  • Because DMA and CPU execution draw from the same host-memory subsystem, a saturated PCIe link leaves residual bandwidth B_H - B_P. Balancing the two completion times yields q* = m*B_P/B_H.
  • The formula degenerates gracefully: as B_H approaches B_P, q* approaches m and the system becomes pure on-demand cache fill. At least one fill is always retained so the cache keeps warming.
  • No approximation: CPU and GPU compute partial sums and merge them, preserving the exact MoE output. This distinguishes FreeToken from HOBBIT (reduced-precision replicas), SiDA/SMoE (substitute or skip low-scoring experts) and Pre-gated MoE (fine-tunes the router).
  • Being closed-form is the point: it is cheap enough to stay device-resident inside a captured CUDA Graph, whereas host-side scheduling heuristics cannot maintain graph execution.

Evaluation setup: real models, real agents, real consumer boxes

Six discrete-GPU systems, three frontier open-weight MoE models, four agentic workloads, four baselines. Weight formats are aligned bit-exactly across engines, which matters for reading the speedups honestly. Metrics are per-request mean decode throughput and per-request mean TTFT; agent trajectories diverge across engines so wall-clock totals are deliberately not compared. Decode is single-stream / small-batch throughout.

  • Models: Qwen3.6-35B-A3B in BF16 (exact precision parity; the 8 GB laptop uses NVIDIA's official NVFP4 release), DeepSeek-V4-Flash (284B total / 13B active) with natively MXFP4-quantized routed experts, and GLM-5.2 (753B / 40B active, NVFP4, a 433 GB checkpoint).
  • Baselines: llama.cpp, Ollama, KTransformers, MoE-Infinity. Ollama and MoE-Infinity lack DeepSeek-V4-Flash support; MoE-Infinity provides no usable server for multi-turn agents.
  • Workloads: W1 AIME math with long CoT; W2 a SWE-bench issue through the OpenCode harness with real tool execution; W3 the same issue driven by Claude Code, spawning concurrent subagents and growing sessions to 56-65k tokens; W4 thirteen fixed turns of an email/calendar agent via OpenClaw with a ~24.5k-token system-context floor.
  • Honesty caveat the authors flag themselves: the 3090/4090/5090 servers are rented dual-socket machines whose CPUs far exceed any edge host, so every run and bandwidth measurement on them is capped at 6 CPU threads and NUMA-pinned. Capped, they deliver 56.7-77.3 GB/s of host bandwidth - the same scale the two genuine edge machines reach untiered.
  • All bandwidths are measured on the deployed tensor shapes, not taken from spec sheets.

Results

On the RTX 5090, FreeToken sustains 77-83 tok/s on Qwen3.6-35B-A3B and 22-25 tok/s on DeepSeek-V4-Flash - 1.8-2.3x and 1.5-1.9x the strongest baseline in each workload. Crucially it barely degrades as workloads become agentic (within 12% of the single-turn W1 rate across all three agent workloads), while KTransformers on DSV4-Flash has already lost 31% of its W1 rate by W2. The tail latency story is starker than the means.

  • Cross-hardware (W2, OpenCode+SWE, Qwen3.6-35B-A3B): 1.3x over the strongest baseline on RTX 3090 and 4090, 1.9x on the 5090 server, 2.1x on the 5090 desktop, 1.8x on the RTX 4060 laptop.
  • The 8 GB laptop result is the headline for self-hosters: the NVFP4 build sustains 39.3 tok/s on an 8 GB, PCIe x8 machine - 92% of the RTX 4090 rate, and above the 33 tok/s median decode speed of Codex measured in production traces.
  • Host sensitivity: the two 5090 columns share identical GPU silicon and differ only in the host. Moving from the many-channel server to a dual-channel consumer desktop costs FreeToken 4% of its decode rate; llama.cpp keeps only 80% of its rate.
  • Frontier tier: GLM-5.2 (753B) on one RTX PRO 6000 at 14.9 tok/s vs llama.cpp's 7.3 (2.0x), with bit-identical expert weights and comparable mean TTFT (7.5 vs 7.8 s). KTransformers has no servable path at all on that box.
  • Prefill ablation: with double buffering on, each 8,192-token chunk completes in 1.19-1.22 s - the time to stream the 64.4 GB expert pool once at 52.7 GB/s, i.e. the practical PCIe 5.0 x16 ceiling - reaching 6.7k tok/s at 16k tokens. Disabling the second buffer costs 19% at 4k, 25% at 8k and 26% at 16k tokens.

Why it matters for people who self-host

The practical claim is a shift in what a machine you already own can serve: 35B on an 8 GB laptop, 284B on a 32 GB gaming desktop, 753B on one workstation GPU - at speeds above the median production coding-agent decode rate. Two design choices are worth stealing conceptually even if you never run FreeToken.

  • The bottleneck is not prediction accuracy but what you do with an unavoidable miss, and a missing expert is work you can execute rather than only bytes you must move.
  • The right CPU/PCIe split cannot be read from spec sheets and must be measured on the actual box - which is why a formula parameterised by two profiled bandwidths generalises across an LPDDR5 laptop and a DDR5 desktop where fixed policies do not.
  • The comparison is apples-to-apples on quantization: every engine served Qwen3.6 in BF16 and consumed DSV4-Flash's native MXFP4 expert blocks bit-exactly, so speedups are not a quantization artifact.
  • Speedups are measured at small/single-stream decode against the strongest per-workload edge baseline - not against a datacenter engine, and not at high batch.

Key findings

  • A closed-form, measured-bandwidth split (q* = m*B_P/B_H) of decode expert-cache misses between PCIe cache fill and in-place CPU execution beats both pure-transfer and pure-CPU designs, and is cheap enough to live device-resident inside a captured CUDA Graph - 1.5-2.3x decode throughput over llama.cpp / Ollama / KTransformers / MoE-Infinity on an RTX 5090 with bit-exact weight parity.
  • A router-following global LRU expert cache cuts decode miss rate to 16% (Qwen3.6) and 39% (DSV4-Flash) at RTX 5090 capacity, versus 41%/59% for KTransformers' prefill-time placement and 62%/89% for llama.cpp's static split - same capacity, only a different policy.
  • An 8 GB RTX 4060 laptop on a PCIe x8 link serves Qwen3.6-35B-A3B (NVFP4) at 39.3 tok/s - 92% of the RTX 4090 rate and above the 33 tok/s median decode speed of Codex in production traces.
  • A single RTX PRO 6000 (96 GB) serves the 753B GLM-5.2 at 14.9 tok/s against llama.cpp's 7.3 with bit-identical NVFP4 expert weights; KTransformers cannot serve the model at all on that box.
  • Agentic stability, not peak speed, separates the engines: FreeToken stays within 12% of its single-turn rate across three agent workloads while KTransformers loses 31% by the second, and FreeToken's worst-case TTFT stays under 44 s where llama.cpp hits 232 s, Ollama 179 s and KTransformers 946 s.
  • Full-layer prefill double buffering makes prefill purely transfer-bound at the PCIe 5.0 x16 ceiling; removing the second buffer costs 19-26% and the penalty grows with prompt length.
  • Host memory matters more than GPU silicon for baselines: on identical RTX 5090s differing only in host, FreeToken loses 4% moving to a dual-channel consumer desktop while llama.cpp keeps only 80% of its rate.

Notable quotes

Because of this bandwidth gap, a CPU-only expert path caps decode speed at a small fraction of what the same weights would sustain from VRAM, regardless of how many cores are available.
A placement frozen at prefill time captures only a small fraction of the routed traffic.
Single-stream benchmarks therefore overstate baseline agentic performance.
Tail TTFT is therefore an availability boundary, not a latency statistic.

Limitations

  • Three of the six consumer systems (3090, 4090, 5090) are rented dual-socket servers emulated down to edge scale by capping runs at 6 CPU threads and NUMA-pinning; only the 5090 desktop and 4060 laptop are real consumer hosts.
  • Evaluation is single-stream / small-batch decode with a handful of scripted agentic trajectories per workload, and the authors explicitly decline to compare cross-engine wall-clock totals; per-workload variance and multi-user concurrency are not characterised.
  • The fast path depends on pinning/DMA-registering the whole expert pool; where the OS or driver forbids that, FreeToken falls back to a pure-CPU MoE backend. B_H and B_P are profiled once at deployment rather than re-measured as the machine's load changes.

Open questions

  • The q* derivation assumes both branches are memory-bandwidth-bound and contend on one host-memory subsystem; how does the policy hold up at larger decode batch sizes, where expert execution becomes compute-bound?
  • Elastic cache reconfiguration triggers at scheduler safe points under a revised memory budget - but who revises it, and how quickly does the system react to a game or browser suddenly claiming several GB of VRAM mid-session?
  • How much of the gain survives on non-NVIDIA edge hardware (Apple unified memory, AMD/Intel iGPUs, ROCm) where the CPU/GPU memory split and PCIe path that q* is built on do not exist in the same form?
