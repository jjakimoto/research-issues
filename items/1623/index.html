    The Other Half of the Memory Wall: Serving 35B MoEs from SSD with Trained Routing Prediction

    ← Go backHacker News — Front Page: Front page turns over almost…NextAgentGuard: Learning Execution Guardrails from Anomalous… →
    📰 Latest · 2026-09-19
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-19

    Source: huggingface-daily-papers · 2026-09-16
    Link: https://arxiv.org/abs/2609.18063

    Edge0 shows a 35B-parameter MoE can be served from SSD on a 24GB consumer desktop at 20 tok/s in under 3 GiB of active memory by training a per-layer head that predicts the next layer's routing one token ahead and then using that prediction AS the routing, so prefetched experts are never wrong and nothing is dropped.

    Executive summary

    Edge0 attacks the weights half of the memory wall: instead of holding a 19.5 GB int4 35B MoE checkpoint in RAM, it keeps expert weights on SSD and mmap-streams them on demand, bounding peak memory by the active expert set. The core trick is a trained 'prerouter' — a small per-layer head that predicts layer N+1's routing one token ahead — whose prediction is consumed as the routing itself, so the staged expert set equals the routed set by construction and disk reads overlap compute. An unmerged recovery LoRA, distilled on the student (prerouted) path, pays back the quality lost to int4 and routing replacement. On a Mac mini M4 Pro 24 GB the 35B tier decodes at 20.4 tok/s in 2.9 GiB (vs 3.9 tok/s in 18.2 GiB fully resident), within 3.9 average points of its fp16 teacher across five benchmarks.

    The problem: sparsity shrinks compute, not bytes

    A 35B-class MoE activates ~3B parameters per token but still stores 19.5 GB at 4 bits, three quarters of a 24 GB desktop before KV cache and the OS. Quantization bottoms out at 4 bits, and naive SSD offloading stalls because layer N+1's expert choice depends on layer N's output, serializing disk latency once per layer per token.

    • 40 layers x 256 experts = 453 MB of int4 expert weights per layer (1.77 MB per expert), 18 GB of routed experts inside a 19.5 GB checkpoint
    • Prior offloading work (llama.cpp --cpu-moe, PowerInfer, Mixtral-offloading, MoE-Infinity, FlexGen) moves the footprint rather than shrinking it
    • Edge0 mmaps quantized expert safetensors and reads byte ranges on demand; the OS page cache carries hot data

    The prerouter: prediction is the routing

    The head owned by layer N runs at token t on layer N's post-attention norm output and predicts layer N+1's routing at token t+1 — a double shift giving a full token of lead. Because the routed set IS the predicted set, the coverage-vs-quality trade-off that pre-gated systems handle at runtime with fallback loads and dropped tokens is eliminated by construction; the approximation is paid once in training.

    • Head: fc1, erf-gelu, fc2 plus a linear residual warm-started from the next layer's router weight
    • Input = hidden state concatenated with two top-k one-hots (this token's and the previous token's routed experts); 35B: 2048 + 2x256 = 2560 dims, hidden width 512
    • 35B tier carries 33 heads (owners 6-38), 8B tier 16 (owners 7-22); 32 of 40 and 16 of 24 layers stream from a prediction
    • Per-layer lead (Pre-gated MoE style) was measured to cost 30-100 ms per step of pipeline drain — more than the load time it hides

    Unmerged recovery LoRA

    The served model is int4 base + routing replacement + LoRA, trained on the student path with prerouter routing active. It is deliberately NOT merged: LoRA deltas (RMS 1e-3) sit below the 4-bit group step, so merging and re-quantizing erases most of the effect.

    • Only 34% of the effect survives merging on an attention projection, 2% on a dense projection, 18% at the logits level
    • Unmerged parallel delta costs 42 MB of adapter weights and no measurable decode time
    • LoRA attaches to attention, linear-attention and shared-expert projections — never to routed experts, whose weights must stay streamable/replaceable

    Three-phase training recipe

    All phases run on the dequantized bf16 reconstruction of the 4-bit deployment checkpoint, base frozen throughout. Order was not negotiable: heads first, SFT second, on-policy distillation last.

    • Phase 1: distill the prerouter heads to imitate the next layer's true router
    • Phase 2: SFT with prerouter routing active over ~2M rows of teacher-generated text; without it, distillation-only checkpoints produce repetitive, collapsed text
    • Phase 3: on-policy distillation with reverse KL on the teacher's top-k plus a tail term, converging on ~200k rows (one tenth of the SFT corpus)
    • Retraining for a different routing width is a file swap — which is how the 35B tier ships at K=4 instead of the base model's K=8

    Where the speedup actually comes from

    On a 16 GB MacBook M2 serving an 18.4 GiB checkpoint (weights do not fit), both arms read within a few percent of the same bytes at K=2 and K=8; the prerouter wins by moving load time off the critical path, not by reading less. Main-thread blocked time on expert loads falls from 244.0 to 101.9 ms per step at K=4.

    • No resource is saturated: disk read is at most 12% of the step, ~1 of 8 cores used, GPU at 35-41%
    • The prerouter reads the same cold pages in fewer, larger, colder loads (1.40 MiB/load at 90% cold vs 0.32 MiB at 20% cold at K=8)
    • Per-load cost fits 1.17 ms + 1.33 ms x cold fraction, reproducing every measured point within 0.13 ms
    • Price is unreclaimable residency: at K=8 the prerouter arm holds 1.43 GiB more MLX memory while page cache loses 1.15 GiB

    Key findings

    • On a 24 GB Mac mini M4 Pro, Edge0 decodes the 35B tier at 20.4 tok/s using 2.9 GiB peak active memory, versus a resident mlx-lm server at 3.9 tok/s occupying 18.2 GiB — roughly five times faster in one-sixth to one-seventh the memory.
    • The prerouter improves decode by +80%/+82%/+84% at K=2/4/8 (4.8 to 8.6, 3.5 to 6.4, 1.8 to 3.3 tok/s) on a 16 GB machine holding an 18.4 GiB checkpoint.
    • The gain is conservation of the critical path, not fewer bytes: both arms move within a few percent of the same bytes at K=2 and K=8; only at K=4 does the prerouter read 16% more (58.9 vs 50.9 MiB/step).
    • Main-thread time blocked on expert loads drops from 154.9 to 46.5 ms/step (K=2), 244.0 to 101.9 (K=4), and 575.0 to 211.6 (K=8).
    • Merging the recovery LoRA into the int4 base destroys it: only 34% of the effect survives on an attention projection, 2% on a dense projection, and 18% at the logits level — hence the unmerged 42 MB parallel delta.
    • Quality gap to fp16 teachers averages 3.9 points (35B) and 2.8 points (8B) across five OpenCompass benchmarks, concentrated in long-chain reasoning (AIME: -6.1 for 35B, -10.0 for 8B); the 8B tier actually beats its teacher by 4.3 points on MMLU-Pro.
    • Incremental sticky-slot stacking adds a further +34% decode in a separate A/B, and 44 ms/step of CPU-side graph building in the 40-layer forward is the remaining floor.

    Notable quotes

    Edge0 changes where the weights live. Expert weights stay on SSD and are mmap-streamed into memory on demand, and peak memory is bounded by the active set instead of the parameter count.
    Because the routed set is the predicted set, the staged slots map exactly and there is nothing to drop
    Moving a read off the critical path can hide it, but it cannot delete it: the advantage comes from the cold-read time that is exposed on that path today.
    Adjacent tokens agree on only about a quarter of a layer's expert set in our traces, so most prefetched experts are never read again, and a load that is issued and not used buys nothing.

    Limitations

    • Edge0 serves one request at a time, FIFO-serialized; batching changes the expert working set in ways the per-request profiles do not model.
    • Prerouter gains shrink on hot caches and fast storage and are bounded by reuse (~25% expert-set agreement between adjacent tokens); its price is unreclaimable residency taken from the page cache.
    • MLX on Apple silicon is the only implementation — the CUDA backend is architecture, not code — and the 16 GB measurement machine shows plus/minus 40% single-shot spread and up to 2.3x across sessions.

    Open questions

    • Can the two unpulled levers — dropping the duplicate bundle/stacked-tensor copy (~0.45 GiB at K=8) and moving the synchronous incremental fill off the main thread (62.5 ms/step at K=8) — be realized without new costs?
    • Does prediction-as-routing hold up on CUDA/NVMe hardware where storage is fast and the latency being hidden is much smaller?
    • Can the long-chain reasoning gap (6-10 points on AIME) be closed by a reasoning-heavy recovery corpus, or is it intrinsic to int4 plus routing replacement?
