LycheeMemory V2: Efficient Long-Term Memory for LLM Agents via Semantic Segment-Level Consolidation

📰 Latest · 2026-08-15
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-08-15

Source: arXiv · 2026-08-13
Link: https://arxiv.org/abs/2608.12990

Moves the write trigger from per-turn to per-semantic-segment using a purely embedding-based boundary detector, cutting construction tokens by 86% versus Mem0 and A-Mem while reaching 89.22% on LoCoMo and 92.20% on LongMemEval-S. The ablations are the real content: fusion/rerank/diversity is worth 22.6 points, and the whole advantage shrinks to ~2 points on a weaker backbone.

Executive summary

LycheeMemory V2 attacks the cost side of agent memory rather than its capability side. Instead of an LLM call per conversational exchange, exchanges are buffered and a boundary detector — built only from cosine similarity, cohesion drop, token-length and turn-count pressure — decides when a semantic segment closes; a single LLM pass then encodes that segment into typed, self-contained records with resolved coreference and normalized dates. Retrieval uses exactly one generative call: a planner emitting typed routes over four parallel recall channels, fused by reciprocal rank. The system leads both LoCoMo and LongMemEval-S with GPT-4.1-Mini while using 204.1K construction tokens against A-Mem's 1,459.9K, but the paper's own ablations show the retrieval stack, not the memory representation, carries most of the accuracy.

The write trigger is the contribution

Each exchange is embedded and compared against both the active segment centroid and the latest exchange embedding, giving a semantic-surprise signal; a cohesion-drop term measures how much adding the exchange would reduce topical coherence. These combine with length and turn pressure into a boundary probability, and a segment closes when it exceeds 0.50 or a hard token cap is hit. No LLM inference occurs mid-segment, so encoding calls scale with the number of segments rather than the number of turns.

  • On LoCoMo, segments average 5.8 turns — roughly a 6x reduction in encoding call frequency.
  • Boundary threshold is remarkably insensitive: sweeping 0.30 to 0.70 spans only 1.04 points of accuracy (88.18% to 89.22%).
  • Contrast with Mem0 (turn-granularity extraction and update) and A-Mem (per-turn Zettelkasten note evolution).

Records and indexes

One LLM pass per finalized segment extracts atomic units, resolves coreference and ellipsis, and normalizes relative dates against the session timestamp. Each record is a 7-tuple: identifier, memory type, self-contained statement, entities, topic tags, normalized event/validity times, provenance links to source turns. Continuity across segments comes from a forward-carried disambiguation state (aliases, canonical entity names, reference relations) truncated to a fixed budget so prompt size does not grow with history.

  • Type schema covers facts, preferences, events, constraints, procedures, failure patterns and tool affordances.
  • Five structured node classes — entity, topic, entity-topic co-occurrence, temporal (day/month), and event-frame — all derived from encoder metadata with no extra LLM calls.
  • The store is append-only: textually distinct statements are kept separate rather than merged.

Retrieval: one generative call, four channels

The planner emits a question type plus a set of routes, each with a goal, search queries, structured constraints and temporal constraints; the type sets channel weights, candidate caps and expansion depth. Four channels run in parallel — direct record vector search, evidence-node search expanded to linked records, temporal recall with date filters, and raw-turn recall over verbatim dialogue embeddings that catches evidence never consolidated. Results merge by reciprocal rank fusion with optional cross-encoder reranking, then diversity-aware selection.

  • Conflict handling is heuristic: the answer model is simply told to prefer the most recent supported information.
  • The raw-turn channel is the safety net for consolidation misses — an admission that segment-level encoding loses information.
  • The planner is a genuine trade-off, not free: dropping it nearly halves query tokens (4.01K to 2.26K) at a 5.8-point accuracy cost.

Key findings

  • Semantic segmentation beats both extremes: eager per-turn construction costs 316% more tokens and loses 7.3 points, while mechanical fixed windows are slightly cheaper but lose 6.8 points, concentrated in multi-hop and open-domain.
  • The retrieval stack dominates: removing fusion, reranking and diversity selection collapses accuracy from 89.22% to 66.62% — below several baselines — making this a retrieval paper as much as a memory paper.
  • On LongMemEval-S with GPT-4.1-Mini the system reaches 92.20% overall against 75.80% for the next best (TiMem), with temporal reasoning at 87.22% versus 72.93%.
  • Structured typed records beat summaries by 8.4 points overall and 12.8 points on temporal questions, at double the construction cost — the cheapest configuration is explicitly not the chosen one.
  • Boundary detection is robust: threshold 0.30 to 0.70 changes accuracy by only 1.04 points, so the write trigger does not need careful tuning.

Notable quotes

The only generative query-time operation is the planning call.
Each evidence node stores a searchable text representation, an optional embedding, and pointers to linked memory records.
This segment-level batching reduces construction frequency.
A larger drop indicates that adding the exchange would make the segment less topically coherent.

Limitations

  • The advantage largely evaporates on a weaker backbone: with GPT-4o-Mini the margin is +2.47 points on LoCoMo and +1.00 on LongMemEval-S, and the system does not lead on multi-hop, open-domain, knowledge update or temporal reasoning in that setting.
  • Token accounting excludes embedding computation, deterministic indexing, retrieval and filtering, reciprocal-rank fusion, the cross-encoder reranker and judge calls — so the reranker's real cost is invisible in the headline efficiency numbers.
  • Scope is text-only conversational QA on two benchmarks (LoCoMo has just 10 conversations), evaluation uses an LLM judge from the same family as one backbone, and the store is append-only with unbounded growth and heuristic recency-based conflict resolution.
  • No code release is announced in the paper; prompt templates and pseudocode support only partial reimplementation.

Open questions

  • How does embedding-based boundary detection behave on non-dialogue streams — agentic tool-use traces, long code sessions — where topical cohesion is a weaker signal?
  • Does the append-only store eventually need compaction, and at what history length does retrieval precision degrade?
  • Would the cross-encoder reranker dominate real-world latency once non-generative compute is accounted for, given it is excluded from all reported costs?
