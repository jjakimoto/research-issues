    AutoResearch at Production Scale: Failure Modes and a Multi-Agent Framework

    📰 Latest · 2026-09-28 Full Article
    Read full article →View on GitHub

    Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
    Date: 2026-09-28

    Source: arxiv · 2026-09-24
    Link: https://arxiv.org/abs/2609.30541

    This is a rare 12-week, 220+ experiment report from running Karpathy's AutoResearch keep-if-better loop in production at Amazon Books. It names five failure modes (infrastructure fragility, memory decay, stagnation, cost asymmetry, metric fixation) and maps each to a fix. The fixes are a pre-execution Code Fixer, durable cross-job memory, and a Criticizer that fires only on stagnation. The paper also gives a rule for choosing among them: prevent failures when iterations are expensive, revert them when iterations are cheap.

    Executive summary

    The authors ran Karpathy's AutoResearch loop for twelve weeks on two independent book-recommendation systems. In both, an LLM edits training code or configs and keeps a change only if a held-out metric scored by an immutable evaluator improves. The systems differ in per-iteration cost by about 760x. System A is code-level, with 9-19 hour multi-GPU iterations. System B is config-level, with 6-52 minute single-GPU iterations. Both showed the same four failure modes caused by cost and long horizons, and System B's multi-criteria evaluation added metric fixation. In System A, a three-agent extension (a Sonnet Researcher, an Opus Code Fixer, and an Opus stagnation-only Criticizer) reached 1.82x Recall@6 over a hand-tuned baseline. In System B, human-maintained program.md pivots plus automatic revert reached 2.11x weighted coherence.

    Setting: two systems roughly 760x apart in cost

    Both systems use the standard AutoResearch parts: an orchestrator with a program.md research program, a sandbox holding train.py, an immutable evaluator the agent can read but not modify, and a research log. System A learns 128-d purchase-optimized retrieval embeddings for 98% of the active catalog (tens of millions of books). It is scored by Recall@6 using a FAISS IVF+Flat index against each customer's held-out next purchase. System B learns hierarchical Semantic IDs with an RQ-VAE, scored by weighted coherence = 0.5*L1 + 0.3*L2 + 0.2*L3 plus secondary usability metrics.

    • System A: the agent rewrites the whole train.py each iteration; 9-19 hour multi-GPU iterations; 60+ iterations across 6 runs; baseline 3.79% R@6, the result of 4 engineer-weeks of manual work.
    • System B: the agent edits hyperparameters and encoder architecture only; 6-52 minute single-GPU iterations; 150+ iterations across 15 runs; baseline WC 0.348 after 2-3 days of prototyping (random assignment gives 0.26).
    • One System A iteration costs about 760x a System B iteration (instance price x GPU count x wall-clock).
    • Verifier grounding is execution-based throughout: a held-out metric computed by an immutable evaluator decides keep or discard. No LLM judges success.

    The five failure modes

    The authors group the modes by root cause: cost (A, D), long horizons (B, C), and evaluation design (E). Modes A-D appeared in both systems. Metric fixation needs multi-criteria evaluation, so it appeared only in System B.

    • Infrastructure fragility: in System A, 18% of iterations failed. One multi-GPU wrapper bug ran 70M text encodings on 1 GPU for over 10 hours. In System B, 11 of 30 iterations in one run (37%, the worst run) hit the evaluator's 600-second timeout, and 11 consecutive iterations were wasted before a human intervened.
    • Memory decay: in System B the agent re-tested 100-epoch training at least 6 times even though program.md forbade it. In System A the Researcher re-introduced a prohibited file-system operation 6 times across 4 iterations, and about 5 iterations were lost re-exploring configurations already recorded as failures.
    • Search-direction stagnation: in System B, 5 consecutive iterations all landed within +/-0.008 WC, and a sweep of commitment weight produced 4 results within 0.01 of each other.
    • Iteration-cost asymmetry: the agent treated a 15-hour run like a 30-minute ablation. In System B it spent 10 iterations on an auxiliary loss with negligible gain, and a single parameter change caused codebook collapse (WC 0.562 to 0.503).
    • Metric fixation: the agent gamed coherence by maximizing codebook size, which collapsed deep levels into singletons. The three usability criteria were never met at the same time in any of the 15 runs (150+ iterations).

    Framework: loop topology and grounding

    There are three principles: prevent (a pre-execution semantic gate), persist (durable cross-job memory), and redirect (reframing triggered only by stagnation). In System A each iteration runs Researcher (claude-sonnet-4-6), then Code Fixer (claude-opus-4-6), which rewrites the code before it runs, then Train, then Evaluator. A change is kept only if score > best_score*(1+tau_keep). If the relative gain over the last 5 iterations falls below tau_stag, the Criticizer (claude-opus-4-6) emits a 2-5 sentence directive, which is cleared on the next Keep. Context uses a sliding window of recent iteration summaries plus the current best train.py in full. In System B, a human plays the Criticizer and memory-keeper roles, and post-execution automatic revert replaces the pre-execution gate.

    • The Code Fixer rewrites the code in a single pass. It replaced an earlier Reviewer-then-Researcher design, whose Reviewer returned malformed JSON on 14 consecutive calls.
    • The Criticizer triggers at an 8% relative-gain threshold over a 5-iteration window. A 3-iteration window fired on noise; an 8-iteration window fired too late.
    • Persistence: System A stores program.md in S3 so each job inherits findings across 6 runs (about 10 weeks). In System B a human maintains program.md between runs.
    • Metric fixation is only partly mitigated, through multi-metric reporting, usability context in program.md, and human QA between runs. The agent never questions the metric.

    Results

    System A peaked at 6.90% Recall@6 at iteration 12. That is 1.82x the hand-tuned baseline and 2.45x the deployed baseline (2.82%). Across 11 evaluation dates the mean was 6.18% +/- 0.28 pp, still a 1.63x lift. The agent's own discoveries included cross-attention, sentence-transformer fine-tuning, hard-negative contrastive learning, a temperature curriculum, multi-hop neighborhood profiles, and dual mean+top-K aggregation. The Criticizer directive 'input representation problem' was followed by a jump from 5.48% to 5.98% within 3 iterations. Separately, the agent designed a text-only fallback on its own initiative that expanded catalog coverage 5.8x, taking the index from about 17% of items to all of them. System B reached WC 0.735 (2.11x) through four phases.

    • Validation relied on an immutable evaluator, re-evaluation on 11 purchase dates, and re-testing System B's architecture choices at full Phase 2 scale before locking them in.
    • About 65% of System B iterations were productive. The rest were lost to infrastructure failures, re-tests and marginal tweaks.
    • The authors estimate the loop saved about 8 engineer-weeks across both systems.
    • All results are offline; online A/B pilots are underway.

    Lessons and cost-dependence principle

    The authors' rule of thumb is 'when iterations are expensive, prevent; when iterations are cheap, react'. They present it as a two-data-point observation, not a proven principle. Paradigm shifts required outside redirection: automated in System A, human in System B. Humans move upstream to design evaluations, write programs and make pivots.

    • Pick the smallest self-contained loop (hypothesis, run, evaluation) that still produces meaningful signal.
    • Add a pre-execution semantic gate whenever iterations have non-negligible cost.
    • Persist findings to durable storage from day one.
    • Use a redirection signal that fires only on stagnation; one that fires every iteration produces noise.
    • Treat metric fixation as unsolved: budget human QA between runs.

    Key findings

    • Additional agents, not additional iterations, broke System A's ceilings. A single Researcher stalled at 4.17% (1.10x); adding the Code Fixer reached 5.48% (1.45x) and adding the Criticizer reached 6.90% (1.82x). The mean over 11 evaluation dates still gives 1.63x.
    • The Code Fixer caught 14 latent bugs in one pass on first deployment. Afterwards no iteration was lost to the agent-coordination layer; the DDP wrapper bug alone would have wasted 10+ hours of an 8-GPU job.
    • Infrastructure fragility wasted 18% of System A iterations and 37% of System B's worst run (11 of 30 iterations lost to a 600-second evaluator timeout before a human stepped in). Only about 65% of System B iterations were productive.
    • A persistent program.md reduces memory decay but does not stop it: the agent re-tested a forbidden 100-epoch setup at least 6 times.
    • The agent removed a structural limit without being asked: a text-only fallback MLP took catalog coverage from about 17% to 100% (5.8x) in one iteration, with no human direction.
    • Metric fixation remained unsolved: the three usability criteria were never met together in 150+ iterations, and the agent never questioned the metric, so fully hands-free operation was not possible.

    Notable quotes

    The Code Fixer eliminates this two-step authoring loop. In its first deployment, it corrected 14 latent bugs in a single pass
    The directive is cleared on the next Keep, so the Criticizer never accumulates an authoritative voice across the campaign—it acts only as a stagnation breaker.
    The revert is cheap to use because System B's iterations cost on the order of dollars; the same approach is impractical for System A where a single iteration costs hundreds.
    The relative-gain threshold (8%) and window size (5 iterations) were chosen empirically: 3 iterations was too frequent (firing on noise); 8 iterations was too late (compute already wasted).

    Limitations

    • The component ablation is observational: the rows in Table V are natural campaign transitions, not controlled runs, so accumulated iterations may have contributed to the gains.
    • Everything comes from one domain (book recommendation) at one organization. Recall@6 and weighted coherence are offline proxies not yet checked against customer outcomes; online pilots are still pending.
    • The paper gives no total GPU-hours, total dollar cost, or systematic human-intervention rate. Costs appear only as relative (about 760x) or qualitative ('hundreds' vs. 'dollars' per iteration), and the 8 engineer-weeks saved is an estimate.

    Open questions

    • Can agents do metric self-evaluation, that is, question whether the metric is the right one? The authors call this the most fundamental open problem.
    • How can cost-aware iteration planning (information gain vs. compute) and parallel exploration hedge multi-hour bets?
    • Does the prevent-vs-react rule hold beyond two data points and outside recommendation, for example in agentic software engineering or wet-lab experimentation?
