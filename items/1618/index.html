SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

📰 Latest · 2026-09-19 Full Article
Read full article →

Topic: Quantitative trading; machine learning for quant & trading; agentic coding techniques; LLMs & multimodal LLMs; and autonomous research (autoresearch / AI-scientist) systems — methods, papers, tools
Date: 2026-09-19

Source: huggingface-daily-papers · 2026-09-17
Link: https://arxiv.org/abs/2609.20519

An RSI-style auto-research loop (propose, implement, review, gated evaluation, run as ~500 disposable isolated lineages over executable environments) discovers four harness mechanisms that cut agent token traffic 44.7-49.0% and API cost by about a third at comparable task score — and the search's own topology (frozen metrics outside the optimizer's control, execution-grounded verifiers, held-out results that never feed back) is a directly reusable blueprint for anyone building an autonomous-research system.

Executive summary

NVIDIA/NTU/MIT scale an AI-led auto-research loop over harness design: a research agent reads execution traces from a base harness (Pi), proposes candidate changes, implements and reviews them in isolated lineages, and passes them through two fixed gates (capability within predeclared tolerance, plus improvement on at least one efficiency metric). Across ~152 proposed directions, 535 executable environments, 3,000+ runs and 60,000+ agent-environment interactions, four mechanisms survive: Action Fusion, Online Context Compact, ObservationPack, and Evidence-Preserving Reducer. On the 51-task EdgeBench held-out set the combined stack keeps 93.7% (GPT-5.6 Sol) / 94.3% (Opus 5) of Pi's score while cutting token traffic 44.7-49.0% and cost about a third, and transfers to Opus 5 with no re-search. Gains are narrower elsewhere: on Terminal-Bench 4 it solves 15/63 vs Pi's 18 while costing 26.3% less.

Search topology: a broad-to-deep funnel of disposable lineages

The outer stage enumerates hypotheses; the inner stage develops each one independently in its own throwaway instance of a shared skill template. Breadth comes from running more isolated loops, depth from repeated refinement inside one. Failures cannot propagate between candidates because each lineage is isolated and disposable, and the modified orchestration code is discarded after each experiment (only the candidate and its evidence are retained).

  • 152 proposed directions across six proposal families: context, progress, tools, delegation, prompt and policy, improvement and evaluation.
  • An 'Oracle Analysis' pass mines existing development trajectories for avoidable work before rollout budgets are assigned.
  • Inner loop = the conventional autoresearch cycle (propose, implement, run fixed experiment, inspect, retain/revise/discard) extended with an iterative implementation loop based on the Ralph Loop; an independent reviewer gates each candidate and failed reviews trigger revision.
  • Per-iteration analysis is fanned out: independent analyzers each examine ONE trajectory (for repeated actions, context growth, large observations, sparse diagnostics) and a reducer merges their findings into a candidate-level summary — a map-reduce over traces, not one giant context.

Verifier grounding: execution-grounded, with the metrics held outside the optimizer

Nothing here is LLM-as-judge at the acceptance layer. Every environment has an executable pass/fail signal, and the acceptance metrics are frozen before search starts and are explicitly out of the optimizing agent's reach so it cannot game them. Two sequential gates apply, and the nondominated survivors are kept.

  • 535 search environments: 495 repository tasks built from GitHub issue/PR pairs (pre-fix repo state, offline deps, PR and regression test hidden from the agent, kept only if the test fails before the patch and passes after) plus 40 synthetic tasks with executable success verifiers in a Terminal-Bench-2-style interface.
  • Gate 1: every capability metric within its predeclared tolerance. Gate 2: improvement on at least one declared efficiency metric.
  • Held-out EdgeBench is isolated: the harness, config, metrics, tolerances and acceptance rule are frozen before evaluation, and a failed validation rejects the candidate rather than triggering further optimization. 11 of the 51 public tasks are used for one-way acceptance, 40 reserved for final generalization measurement.
  • Even the one LLM-in-the-loop component is verifier-wrapped: the Evidence-Preserving Reducer's summary receipt is checked deterministically (schema, source hash, exit status, exact quotes, size) and falls back to the original log on failure or suspected credentials.

The four surviving mechanisms

Each targets a distinct point in the agent-environment loop, and the paper's ablation shows every one of them lowers total tokens under both backends.

  • Action Fusion: bundles a file mutation and its follow-up command into one tool request, removing an intermediate model round trip (3 API calls to 2). Commands that must inspect the mutation result stay separate.
  • Online Context Compact: at plan-step completion boundaries, projects remaining requests and compacts only when projected input savings beat the estimated prompt-cache rewrite cost; later compactions must clear a larger margin to cover unrecovered rewrite cost.
  • ObservationPack: outputs over 10 KiB are archived locally, sent in full for the next two provider requests, then replaced by a stable handle + size + head/tail excerpt, with exact pages retrievable on demand.
  • Evidence-Preserving Reducer: build/test logs of at least 4 KiB are compacted by a cheaper model (GPT-5.6 Luna at high) into a verified receipt; file reads and search results bypass it, and ObservationPack skips receipts to preserve the verified evidence.

Cost and reliability numbers

All costs use API prices as of August 17, 2026. The headline EdgeBench result is a score-for-cost trade, not a free win, and the paper is careful about where it does not hold.

  • EdgeBench / GPT-5.6 Sol: total 1.0990 B tokens vs Pi's 2.1538 B (49.0% fewer), $894 vs $1,339 (33.2% lower), score 42.003 vs 44.833, token efficiency $0.4174 vs $0.5855 per score point.
  • EdgeBench / Opus 5 (held-out backend, no re-search): 44.7% less traffic and 33.5% less cost than Pi, retaining 94.3% of its score.
  • A 'Performance' operating point (best single mechanism per backend — ObservationPack on Sol, Action Fusion on Opus 5) beats Pi outright: 47.208 vs 44.833 on Sol, 50.482 vs 44.756 on Opus 5.
  • Terminal-Bench 4 (63 CPU-only tasks): SoL-Pi solves 15 vs 18 for both Codex and Pi, but at $211.12 total vs Pi's $286.45, and it still has the lowest cost per solved task ($14.07 vs $15.13 Codex, $15.91 Pi).
  • IMO 2026 (Lean 4-verified, GPT-5.6 Sol xhigh, 150-min cap per problem): 3/6 passed at $62.69 total, $20.90 per passed problem vs $22.89 (Codex, 5/6) and $25.32 (Pi, 3/6).

Swarm result and the Action Fusion case study

A 20-worker Codex-coordinated swarm on a kernel-optimization task shows the harness savings compound across agents, and one mechanism's full 27-iteration lineage is traced end to end.

  • Two-hour kernel-optimization runs from a frozen 147,734-cycle starter: SoL-Pi swarm 1,127 cycles at $60.11; Pi baseline swarm 1,366 cycles at $82.12; single Codex agent 1,333 cycles at $39.20 — 26.8% cost reduction vs the Pi swarm under the same budget.
  • Swarm topology: five groups of four workers, independent workspaces, a shared evidence board per group, a coordinator relaying findings; the shared best updates only on an immutable candidate snapshot plus independent verification of a strict improvement.
  • Action Fusion's lineage spans 27 recorded iterations over four stages (oracle analysis, baseline construction, prompt/tool-schema optimization with 18 explorations, held-out validation); oracle analysis projected an 11.5% token reduction under full triggering.
  • Prompt-only triggering proved unreliable, so the agent extended the tool schema to expose the fused action directly — and invented 'trigger rate' as an intermediate acceptance metric alongside task score.

Key findings

  • Search scale: ~152 proposed directions, 535 executable environments (495 repo-derived + 40 verifier-driven), 3,000+ runs and 60,000+ agent-environment interactions yielded exactly four retained mechanisms.
  • Full stack on EdgeBench cuts token traffic 44.7-49.0% and API cost ~33% while keeping 93.7% (GPT-5.6 Sol) and 94.3% (Opus 5) of Pi's average score; cost per score point drops from $0.5855 to $0.4174 (Sol) and $0.7625 to $0.5376 (Opus 5).
  • Zero-adaptation transfer to an unseen backend works but is weaker: mechanism trigger rate and intensity are both lower under Opus 5 than under the Sol trajectories the harness was optimized on.
  • The cache trade-off is explicit and measurable: cache-read traffic falls 2.1326 B to 1.0605 B while cache-write rises 0.0141 B to 0.0316 B, and total cost still falls from $1,339 to $894 — arguing against optimizing for prompt-cache reuse alone.
  • Efficiency is not free on harder agentic benchmarks: Terminal-Bench 4 solve count drops from 18 to 15, though total cost falls 26.3% ($211.12 vs $286.45).
  • Swarm-level: 20 SoL-Pi workers reached 1,127 cycles at $60.11 vs the Pi swarm's 1,366 cycles at $82.12 (26.8% cheaper) in matched two-hour runs.

Notable quotes

Held-out results never feed back into the Auto-Research Loops: a failed validation rejects the candidate without triggering further optimization.
We run each independent search as a disposable instance of a shared skill template containing a minimal research loop and operating instructions. Each experiment copies the template, sets its parameters, and runs to completion, retaining the candidate and evidence while discarding modified orchestration code.
Independent analyzers examine one trajectory each for repeated actions, context growth, large observations, or sparse diagnostic signals. A reducer combines their findings into a candidate-level summary that guides the next proposal.

Limitations

  • The harness was searched using trajectories from a single backend (GPT-5.6 Sol); on Opus 5 the mechanisms trigger less often and less intensively, so cross-model transfer is called only 'preliminary evidence'.
  • Running complete auto-research loops is expensive enough that the authors could not run controlled comparisons of search breadth vs depth under a fixed budget — the stated counts 'do not establish a scaling law'.
  • Complementarity between mechanisms is descriptive only: gains are measured on each configuration's own triggered-task subset, which does not isolate interaction effects, and the Terminal-Bench 4 solve-count regression (15 vs 18) is not explained away.

Open questions

  • Does 'recursive efficient improvement' actually compound — i.e. does using SoL-Pi as the starting harness for the next search cycle buy proportionally more environments and ideas per dollar? The authors call this a vision, not a demonstrated effect.
  • Would training and validating the harness across multiple LLM backends simultaneously close the trigger-rate gap seen on the held-out backend?
  • How far does 'pretraining the harness' scale — is there a point where more executable environments and more idea diversity stop yielding transferable mechanisms?
