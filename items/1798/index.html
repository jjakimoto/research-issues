    Rufus-Air: An Open LLM Post-Training Recipe

    ← Go backMILO: Efficient Many-shot In-Context Learning with…NextReasoning Instructions Can Break Answer Decoding in… →
    📰 Latest · 2026-09-26 Full Article
    Read full article →View on GitHub

    Topic: large language models
    Date: 2026-09-26

    Source: arxiv · 2026-09-24
    Link: https://arxiv.org/abs/2609.29421

    Amazon documents a complete, reproducible 8-stage post-training pipeline on the public GLM-4.5-Air-Base MoE (106B-A12B). It uses only public data and open components (Slime/Megatron-LM/SGLang, a self-hosted E2B/Firecracker sandbox fleet), runs each RL stage on 8-32 H200 nodes, and beats the vendor's own post-trained release on every reported benchmark except creative writing. The useful part for practitioners is the concrete knobs and costs: learnability filtering, ordering stages by how reliable each reward is, token-in/token-out agent rollouts, Rollout Routing Replay for MoE, about 832 node-days of SFT, and about $10K/month for sandboxes.

    Executive summary

    Rufus-Air is an open post-training recipe run as one serial pipeline on GLM-4.5-Air-Base: SFT, Reasoning RL, Coding RL, Instruction-Following RL, General Agent, Coding Agent, Search Agent, then RLHF. Each stage trains on the checkpoint the previous stage produced. It uses 17 public SFT datasets as released (no response regeneration, no new human annotation), public or synthetic RL prompt sets, and an open reward model. The authors argue four points: a broad SFT stage sets the capability floor; difficulty/learnability filtering keeps RL prompts in a productive band; stages should run in order of how hackable their reward is; and infrastructure choices are part of the recipe. The final model leads the official GLM-4.5-Air release on every reported benchmark except Arena-Hard v2 Creative Writing, and is competitive with Nemotron-3-Super and INTELLECT-3.

    Problem and framing

    Open base checkpoints are widely available, but post-training recipes are usually reported at system-card depth, and the details a team needs are the ones left out. The paper describes itself as sitting between a research paper and an engineering experience report. It flags which conclusions come from training experience rather than full ablations.

    • Base model: GLM-4.5-Air-Base MoE, 106B total / 12B active, used unchanged (architecture, tokenizer, native <think> chat format).
    • Baselines measured under the same harness: GLM-4.5-Air (the vendor's post-train), INTELLECT-3 (same base), Nemotron-3-Super (different base, similar active size).
    • Stated aim: specific enough that a team with tens of nodes can follow it stage by stage, or lift out a single stage or infrastructure component.

    Pipeline and stage order

    Stages go from basic to advanced capability and from hard, verifiable rewards toward softer judge- or model-based rewards. The goal is to shorten the time a gameable reward is under optimization pressure. The order tracks exposure to reward hacking rather than reward format. IF RL uses a rubric LLM judge but still runs early, because instruction following is close to what the policy already does. RLHF, the most gameable stage, runs last.

    • Reasoning RL and Coding RL (deterministic verifiers) run first. IF RL gains more when it starts from the Reasoning RL checkpoint than from the SFT checkpoint.
    • Agent stages: General Agent (synthetic MCP environments from AgentWorldModel), Coding Agent (Harbor-format terminal/SWE tasks with a single execute_command tool), Search Agent (web search + scrape + Python, rewarded by an LLM judge).
    • RLHF means on-policy RL against the open Skywork-Reward-V2-Qwen3-8B reward model, not RL on new human labels.
    • The order does not protect earlier gains, since every stage updates the same parameters. Each stage is therefore measured against the checkpoint it started from.

    SFT: breadth as the capability floor

    SFT is treated as a capability-building stage, not a warm-up. The mix has 9.01M samples and 44.5B raw tokens, of which 27.0B loss-bearing assistant tokens come from 17 public datasets. Agent trajectories use interleaved thinking supervision, and sequences are capped at 120K tokens after applying the chat template. Decontamination uses a chained 8-gram screen plus exhaustive n-gram and dense-retrieval checks for math/knowledge benchmarks, and removed 4,187 samples.

    • Share of samples vs. share of loss tokens: General Agent is 39.6% of samples but only 14.2% of tokens; Math plus Coding Agent are 18.8% of samples but 49.1% of tokens.
    • Training: 3 epochs on 64x8 H200 nodes (512 GPUs), batch 4096, 128K packed context. About 13 days, or roughly 832 node-days, the largest single expense.
    • Held-out scores flatten within the first epoch while the loss keeps stepping down at each epoch boundary. They shipped mid-plateau checkpoint 3799 instead of the final step.

    RL stages: data filtering, rewards, algorithms

    Across the outcome-reward stages, the choices that mattered were data curation and reward design rather than a new objective. The recurring tools are a teacher-solvability (correctness) filter plus a learnability filter that drops prompts the policy always or never solves. Some stages add online dynamic sampling (DAPO-style), which advances the difficulty frontier automatically.

    • Reasoning RL: 121K prompts (math/science/puzzles), GSPO, 256 prompts x 16 samples, 30K-token budget, and a length penalty measured against the shortest correct rollout in each group. The online filter keeps only groups whose mean reward falls inside a fixed window.
    • Coding RL: 29,405 Python problems, binary all-tests-pass reward using at most 50 SHA-256-seeded tests per problem. The response budget was raised from 64K to 128K mid-run after 11-28% of samples were being truncated.
    • IF RL: 14K verifiable multi-constraint prompts plus 13K adversarial multi-turn conversations. Binary reward only when all rubrics pass. 'Optional' rubrics were excluded because they caused a length bias.
    • Search Agent: GRPO with mean-only group advantages, a positive reward only after at least 2 successful tool calls, and no unconditional format bonus (the policy had learned to collect it with tool-free guesses).
    • Coding Agent: rollouts that fail because of infrastructure (sandbox boot failure, verifier timeout) are tagged as aborted and removed from the group before computing advantages.

    Infrastructure: Rufus-Slime and Rufus-Gym

    All stages run on Rufus-Slime, an adaptation of Slime with Megatron-LM training and SGLang rollouts. The stack is pinned by a container image and specific commits. Rufus-Gym adds a gym-like environment interface on top of a Strands Agents ReAct loop for multi-turn agent rollouts.

    • Large rollout batches (4,096-8,192 responses per step) for lower-variance group-relative advantages. Rollout Routing Replay replays MoE expert routing from rollout in the training pass.
    • FP8 rollouts (first three layers kept in BF16) with fully BF16 updates, corrected with truncated importance sampling.
    • Token-in/token-out rollouts: exact sampled token IDs, log-probs, loss masks, and routed experts are passed unchanged to the trainer. This avoids retokenization drift and silent rewriting of earlier turns by the chat template.
    • Each coding trajectory gets its own Firecracker microVM on a self-hosted E2B runtime on bare-metal EC2, restored from a snapshot in seconds. Commands are retried only if execution provably never started.
    • Environment actors are distributed with Ray. General Agent needs 3,072 CPU-heavy MCP rollouts per training step.

    Results and significance

    Every stage moved its own target benchmarks, and the benchmarks each stage monitored as guardrails mostly stayed within about a point. Against the two models built on the same base, Rufus-Air leads on every row except Arena-Hard v2 Creative Writing. Against Nemotron-3-Super, it leads on instruction following, search, MCP-Atlas, SWE-bench Verified, and LiveCodeBench, and is close on math and science. The authors read this as the recipe moving most where it spends the most training signal.

    • Largest single-stage moves: Multi-challenge +24.7 under IF RL, Arena-Hard v2 Creative Writing +14.4 under RLHF, Tau2-Retail +9.8 under General Agent.
    • Agentic RL has costs outside the GPU cluster: the sandbox service is sized for about ten thousand concurrent sandboxes and costs on the order of $10K per month. One BrowseComp evaluation pass costs a few hundred dollars in search/extraction API calls.
    • The choice of Tau2-Bench user simulator alone moves a score by up to 23.7 points, so cross-paper agent comparisons need matched simulators.

    Key findings

    • SFT alone (checkpoint 3799) already beats the RL-included GLM-4.5-Air release on IFEval (88.33 vs 83.00), IFBench (57.75 vs 33.60), and AIME 25 (90.83 vs 84.20), and trails only on GPQA (68.18 vs 73.90). Held-out scores plateau within the first of three epochs.
    • IF RL produced the largest single-stage gain: Multi-challenge rose from 31.1 to 55.8 and IFBench from 63.8 to 77.8. Adding optional rubrics (about ten per instance) instead caused a pronounced length bias.
    • In Coding RL, raising the response budget from 64K to 128K cut truncation from 11-28% to about 0.1% of samples. Training reward rose from 0.34 to 0.42, and LiveCodeBench v6 peaked at 75.9 (from 68.6).
    • For the judge-rewarded Search Agent, dropping standard-deviation normalization in GRPO advantages beat the normalized run at every matched evaluation (55.8-64.8 vs 49.7-58.7 held-out). A small KL anchor held policy entropy at 0.94 instead of drifting to 1.12.
    • The final model leads GLM-4.5-Air everywhere except Arena-Hard v2 CW (53.0 vs 60.3), e.g. Tau2-Telecom 93.0 vs 32.7, SWE-bench Verified 65.6 vs 50.6, BrowseComp 37.1 vs 22.7. It ties Nemotron-3-Super on Terminal-Bench 2.1 (42.7).
    • The Coding Agent's SWE-bench Verified gain (65.6 to 67.8) did not survive to the shipped checkpoint (65.6). The choice of Tau2-Bench user simulator alone shifts scores by up to 23.7 points.

    Notable quotes

    The takeaway we would carry forward is that, on a strong SFT base, verifier-based Reasoning RL is reliable and largely curation-bound: the gains track the quality of learnability and correctness filtering more than the details of the policy-gradient objective.
    The practical finding from this run is that extending the response budget removed truncation masking, after which both reward and LiveCodeBench kept rising.
    The textual transcript is kept for inspection and evaluation, but the token trajectory is the authoritative training artifact.
    A team planning the RL stages on 8–32 nodes should budget these stages separately rather than by a per-stage average.

    Limitations

    • The serial stage order was shaped by earlier experiments and compute budget: it is one order that worked, not one shown to be optimal. Several conclusions rest on training experience rather than full ablations, and no single benchmark suite was tracked across every stage, so some movements cannot be attributed to a specific stage.
    • The Coding Agent stage was trained on the compute available rather than to convergence (4K tasks). Its SWE-bench Verified gain was lost by the final checkpoint, which shows a serial pipeline does not protect earlier gains.
    • Tau2-Bench and MCP-Atlas harnesses were reimplemented on the authors' own stack, Tau2 scores depend heavily on the user simulator, and the six developer-reported baseline columns come from mixed harnesses. Creative Writing still trails GLM-4.5-Air and Nemotron-3-Super.

    Open questions

    • Would training domain-specific experts and merging them with multi-teacher on-policy distillation beat this serial pipeline? The authors explicitly did not explore it.
    • Which later stage (Search Agent or RLHF) eroded the Coding Agent's SWE-bench gain, and how can a serial pipeline protect earlier stage gains cheaply?
    • Would a style-tuned reward model close the Arena-Hard v2 Creative Writing gap without costing the instruction-following and agentic gains?
